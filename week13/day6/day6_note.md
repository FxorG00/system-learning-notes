### 数据不存在

```text
如果我们大量请求 114514，但是缓存 miss，那么就会都去查 MySQL 看看有没有。这样会给下游（也就是 MySQL）带来很大的流量。

我们可以，在第一次请求 114514，缓存 miss 且 MySQL 也找不到的时候，把 "MySQL 中没有这个 114514" 这个结论给缓存一小段时间。这样后续的一部分请求就会被缓存挡住。
```

### 单个热点失效

```text
热点 114514 缓存到期之后。一堆请求 114514，但是缓存都 miss 了，所以都去查 MySQL，发现存在于 MySQL 当中，就会执行重建（重建就是，把 MySQL 里查到的信息重新写入缓存，并且设置有效期）

但是这样会有大量请求同时重建它，造成(cache breakdown)

保护：同一时刻只让一个请求负责查询 114514 并且进行重建。其余请求 114514 等待。
```

### 大范围失去缓存

```text
如果 0 点向缓存加入 10w 个商品，它们 TTL 都是一小时，也就是在 1 点全部到期。
然后在 1 点的时候，有针对这 10w 个商品的大量请求，他们查到缓存 miss 了之后，就会去查数据库，这样让数据库的流量突然增大。并且，查数据库查到对应信息后，会进行重建，这样也会有大量重建同时发生。

保护：给 TTL 加入随机差异，jitter(抖动)，让他们错开到期，这样 1 点的时候，还是有部分缓存是有效的，也就是让 1 点的缓存 miss 和重建次数尽量减少一些。这样，能摊开重建时刻。
以及保护数据库，加一个限流。

```

## R3

### RR

```text
repeateable read
在同一个事务中，重复地做普通查询，所有查询查到的值都一样。
也就是都与第一次查询一样。
其实就是在事务内，第一次普通查询时，建立视角。
```

### RC

```text
Read Committed
就是在事务内，看不到别的事务还没提交的修改；别的事务提交了，我的普通查询就能看得到新值。
也就是每次普通查询前都会建立一次新的视角。
```

### MVMC 总结

```text
B修改账户1：1000 -> 1200
-> 保存这次修改的撤销信息U1
-> 当前行记录修改者B和U1的位置

A普通查询：
-> 找到账户1，检查1200这份内容的修改者B
-> 按本次Read View判断能不能采用
-> 能采用就返回1200；不能采用就借助U1重建1000，再检查

undo log 里的信息，让我们能找到 1000 这个旧的版本。
undo log 记录：
能够定位到表，定位到具体信息。
被修改字段的旧值。
修改前的旧值，是来自哪个事务的修改。
修改前的回退位置（就怎么再回溯到更早）

read view 里的信息，能够让我们去选择应该返回哪一个版本。
建立视角的时候，哪些读写事务尚未提交。
当前的事务编号分配到哪里。（我们可以识别出来，之后才取得编号的事务，那肯定是要排除他们的修改）
```

### locking read

**读取当前记录并取得修改锁；在本事务结束前，其他事务的冲突修改先等待。** 这就是`SELECT ... FOR UPDATE`，也叫**locking read（锁定读）**

锁是从成功取得开始，到事务结束才释放。

```text
A：读取并锁住账户1 -> 判断余额 -> 完成扣款
B：想修改同一账户 -> 等A释放锁
A：COMMIT或ROLLBACK -> 释放锁
B：取得所需锁后，才能继续修改
```

### 超时

```text
A 开启事务，并且读取并锁住账户1。

B 尝试修改账户 1，需要拿到锁，所以等待 A 释放锁。

但是 A 一直不释放，所以 B 等待确定时间后会超时。

然后我们对 B rollback; 结束这次失败的尝试。

再让 A 结束事务，释放锁。
```

### deadlock

```text
A 开启事务，读取并且锁住账户 1

B 开启事务，读取并且锁住账户 2

A 想要修改账户 2，所以等待账户 2 的锁。

B 想要修改账户 1，所以等待账户 1 的锁。

双方互相等待，并且事务都没结束，所以 A 的 lock1，B 的 lock2 都不会释放。
造成 deadlock。

所以需要让一个事务结束。
InnoDB 检测到死锁后，会选一个事务整体回滚，释放它的锁。
```

### ACID

第一，两条修改应该一起成功；中途放弃就一起撤销。第二，金额要转对，总额仍然守恒。第三，其他事务同时查或改账户时，结果也要遵守清楚的规则。第四，提交成功后，数据应该按系统承诺保存下来。

**这四个要求对应事务的ACID四项性质。** 它们不是四个新接口，而是给刚才的动作和后续恢复问题各起一个名字：

| 这笔转账需要什么                     | 名称                | 当前怎样理解                                       |
| ------------------------------------ | ------------------- | -------------------------------------------------- |
| 两边修改共同保留或撤销               | Atomicity，原子性   | 不能留下半笔已提交转账                             |
| 完成后仍满足业务与数据约束           | Consistency，一致性 | 例如总额守恒、余额非负；需要正确逻辑及约束共同维护 |
| 别的事务同时读写时，行为仍有明确规则 | Isolation，隔离性   | 本课用RR/RC解释普通读取，用锁解释冲突修改          |
| 成功提交的数据按系统保证恢复保留     | Durability，持久性  | 涉及日志、刷盘配置与硬件；今天没有做崩溃证明       |
