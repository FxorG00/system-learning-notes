## 三、Week13 真正完成了什么

### 3.1 TTL 不再只是一个 deadline 字段

Week13 Day2 已经让 `KvStore` 的记录拥有 value 和 deadline。最近五个单元把这份组件能力真正接成了一条系统链：

```text
客户端发送 EXPIRE / PTTL
-> dispatcher 解析参数
-> 同一条命令取得一次时间
-> KvStore 按同一个时刻判断多个 key
-> 逻辑过期的记录对 GET / EXISTS 不再可见
-> sweep_expired 分批检查并物理删除
-> owner 即使没有网络事件，也定期获得维护机会
```

这条链里最重要的不是 API 数量，而是你已经能区分四个不同对象：

1. **记录保存的 deadline**：某个 key 何时失效。
2. **命令临时取得的时间快照**：一条多 key 命令怎样看到一致的“现在”。
3. **维护 cursor**：下一轮从排序空间的哪个位置继续检查。
4. **owner 的 `next_sweep_at`**：下一次何时允许做维护。

它们都和“时间”有关，却属于不同生命周期。你在 Day7 口述中已经能把它们分开，而不是把所有时间状态都归到 `KvStore` 或 event loop 里。

### 3.2 `Complete` 不等于命令成功，命令成功也不等于回复已经送达

Day3 延续了你在 HTTP/RESP parser 中建立的责任边界：

```text
parser Complete
-> 只证明 RESP frame 合法且完整

dispatcher 执行成功
-> 才证明命令语义被接受，状态可能已经改变

Connection output 排空
-> 才证明待发送 bytes 已经交给后续传输路径
```

`SET k` 可以是合法 frame，却因参数不足返回命令错误。`EXPIRE` 的数字文本可以被解析，却仍可能在秒转毫秒或 deadline 相加时越界。

你已经能沿下面这条边界逐层判断失败：

```text
string
-> seconds integer
-> milliseconds duration
-> absolute deadline
```

每一层都可能拥有不同的错误条件。这是系统代码里很有价值的习惯：不要因为第一层输入合法，就默认后面的表示和运算都安全。

### 3.3 主动清理第一次引入了“有预算的后台工作”

`sweep_expired(max_examined)` 的关键不是“找到多少就删多少”，而是：

```text
一次最多检查多少条记录
```

即使本轮检查两条、删除零条，它仍然完成了有意义的工作，并把 cursor 推到后面。这样维护成本才不会由“有没有碰巧找到过期记录”决定。

Day4 还暴露了一个真实生命周期问题：把 `std::map` iterator 长期保存在成员里，外部 `DEL` 可能删除它借用的 node。最终方案改为保存自己拥有的 key 值，再用 `upper_bound(previous_key)` 在当前树中重新定位后继。

你后来把它理解成排序轴上的位置，这是一个很好的第一层直觉：

```text
不依赖旧 node 继续存在
只保留“上次停在这个排序位置”
下一轮在当前 map 里找它后面的第一项
```

当前方案每检查一项会重新做树查找。它满足正确性和当前课程的有界维护目标，但是否成为性能瓶颈，要留到 Week15 用工作负载和数据证明。

### 3.4 空闲维护把组件真正接回了 owner

只有 `sweep_expired()` 还不够。如果 event loop（事件循环）永久阻塞在 `poll_once(-1)`，而客户端也没有继续发送请求，维护函数就永远得不到执行机会。

Day5 完成的是：

```text
无限等待网络事件
-> 有限等待
-> owner 定期返回
-> 到达 next_sweep_at 时执行一次 bounded sweep
-> 维护完成后再安排下一个时刻
```

这里的两个数字承担不同职责：

- `50ms` 限制一次网络等待最多睡多久。
- `16` 限制一次维护最多检查多少条候选。
- `100ms` 表示两次维护机会之间的目标间隔。

它们都不是“服务器最大响应延迟”的证明。

已有正式记录包括 Debug 和 ASan/UBSan 构建下各 `124/124` CTest、空闲和活跃维护场景、37 条记录按 `16/16/5` 回收、异常传播和 fd 回到基线。这里引用旧验收，不冒充本次小结重新运行，也不把它写成 QPS、公平性或实时性结论。

### 3.5 Week13 还补上了两个暴露出来的基础缺口

Day6 没有新增 Mini Redis 代码，而是补了 MySQL 事务和缓存问题的第一层。

你现在能先用行为理解两种隔离级别：

```text
RR：
同一事务里的同类普通读取，别人中途提交后，仍保持原来的读取视角

RC：
别人未提交时看不到；别人提交后，下一次普通读取可以看到新值
```

理解行为以后，再用 Read View、undo/version chain 和 MVCC 解释数据库怎样提供旧版本。这比先背内部字段更稳定。

Day7 则补上了类、继承和虚函数：普通成员调用按当前基类接口选择；虚调用在运行时依据完整对象的实际类型选择重写入口；`override`让编译器检查重写签名；通过基类拥有指针销毁派生对象时，基类析构函数需要是虚函数。

这两部分目前都属于扎实的第一层。它们足以支撑项目理解和后续追问，但不应包装成 MySQL 深度面试题或完整 C++ 对象模型已经全部掌握。

## 四、理论线：从“会算模型”走到了“会认识框架状态”

### 4.1 T9 让 Tensor 不再只是 NumPy 的另一个名字

T9 最终 `99/100`。你已经能把 Tensor 拆成几层观察：

```text
逻辑索引
-> shape / stride / storage_offset
-> 怎样找到 storage 中的元素

对象关系
-> transpose / slice 是否共享底层存储
-> clone / contiguous / reshape 何时可能产生新数据

执行位置
-> CPU Tensor 的 storage 位于主机内存
-> CUDA Tensor 的 storage 位于 GPU 可访问的显存
```

这为后面的 AI Infra 提供了真正需要的对象语言：同样的逻辑数值，可能拥有不同 layout、不同设备位置和不同搬运成本。

当前只做了布局、共享和复制的正确性观察。没有 profiler 和 benchmark，所以不能说已经证明某种布局更快，也不能把 payload bytes 当成完整进程内存峰值。

### 4.2 T10 把模型从几个数组变成了可恢复对象

T10 最终 `99/100`。这一课没有提前引入 MLP，而是继续使用你 T8 已经会的线性多分类器。

真正新增的是：

```text
一个模型对象
├─ 子模块
├─ parameter：训练得到、需要保存的权重
├─ buffer：不由优化器更新，但需要随模型保存的状态
└─ forward 临时值：只服务于本次计算
```

你也已经区分两组容易混在一起的开关：

- `train()` / `eval()` 改变 Dropout 等模块本次采用的行为规则。
- `inference_mode()` 决定这次计算是否记录反向求导所需的来路。

最后的 checkpoint 主线回答了一个具体问题：**旧进程和原模型对象都消失以后，怎样用类定义、尺寸配置和状态文件构造一个新对象，并恢复同一输入的预测。**

这和 Week14 即将做的 AOF 有一个很好的共同点：文件里保存的是状态数据，不是仍然活着的 C++ 或 Python 对象。恢复需要先有能够承载状态的新对象，再把保存的内容按约定装回去。

## 五、学习方式本身也在进步

最近最明显的变化，是你越来越少被“术语听起来很专业”糊弄过去。

你会直接指出：

- RR 先要说明对外表现，再讲 Read View 和 undo。
- `grad_fn` 不能只给定义，要先看实际打印结果和它指向什么。
- `load_state_dict` 那一串动作要先说明共同证明什么。
- 保存 cursor key 和调用 `upper_bound` 必须先用一轮具体数据说明用途。
- 一个实验要告诉你操作什么、预期看到什么、结果证明什么。

这说明你已经在主动检查知识链：

```text
我现在面对什么对象？
它解决什么问题？
我执行什么动作？
会看到什么结果？
这个结果为什么足以支持结论？
```

这种能力对 AI 时代尤其重要。AI 可以快速给出代码、术语和测试框架，但你需要判断它有没有偷换对象、跳过状态建立、把没测的性能写成结论，或者用一堆 API 掩盖主问题。

测试分工也更成熟了：核心状态模型、设计选择和性能结论由你掌握；你能口述 oracle 后，重复 correctness test 和脚手架可以交给 Codex。这样省下的是机械工作，不是判断能力。

还有一条需要继续执行：**每完成一个 AI Theory，先把自己的理解写进笔记。** Codex 的检阅和补证不能替代这份个人模型。

## 九、接下来只抓三件事

### 9.1 系统主线进入 Week14 Day1

先实现独立的可重放 RESP 记录编码器，并能解释：

```text
为什么只记录状态变化？
为什么 SET 必须按 bytes 保存？
为什么 DEL 要保留参数顺序？
为什么相对 EXPIRE 要规范化为绝对期限记录？
```

当前不碰文件故障、恢复流程或 server 接线。先把记录对象做对。

### 9.2 理论线进入 T11

从已经会手算的标量链开始，观察普通 forward 留下什么关系，`grad_fn` 实际打印什么，`backward()` 怎样把同一个梯度算回来。

本课重点是理解三份东西：

```text
parameter 当前数值
leaf 上累计的 .grad
本次 forward 为 backward 保存的关系与中间值
```

不要提前把 MLP、optimizer 或 attention 混进来。完成后自己记笔记。

### 9.3 控制教程返工成本

讲解质量需要继续守住，但进入学习后发现局部断点时，优先做定向修订，不把整篇反复推倒。每份新教程仍做三遍不同目的的检查：技术、教学顺序、全局对齐。

真正需要你投入的时间，应当更多落到代码、实验、口述和自己的笔记，而不是持续替教程猜“作者到底想让我做什么”。

## 十、最后的评价

这九天最重要的变化，不是累计数字从 86 变成 91。

更重要的是，你已经能把一个时间功能拆成：

```text
记录自身的期限
命令的一致时间视角
有限物理回收
跨轮位置状态
owner 的维护调度
网络连接仍然独立存活
```

你也开始用同一种眼光看 PyTorch：哪些是模型长期状态，哪些只属于一次 forward，哪些行为由模式决定，进程消失后怎样恢复。

这说明系统线和 AI 理论线并没有各学各的。它们正在汇合到同一类能力上：**辨认对象、状态、所有者、生命周期、恢复边界和证据。**

当前最准确的判断是：

> Mini Redis V2 已经扎实收口，简历项目还差持久化、故障/性能和项目表达；AI 理论已经进入 PyTorch，但还没有进入深度学习与推理系统核心。节奏相比上一阶段恢复，11 月完成仍可能但偏紧，按真实证据推进比守日历更重要。

继续拿下 Week14。你现在面对的已经不是“Mini Redis 能不能跑起来”，而是“它能不能在进程消失后，把状态可靠地带回来”。
