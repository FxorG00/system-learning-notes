## 三、这 19 天新增的能力是什么？

### 3.1 HTTP 从单个 parser 变成了完整服务器

9 月 21 日，你只有 request-line 的边界解析。现在已经完成：

```text
request line / headers / Content-Length body
-> structured request
-> application route
-> response encoding
-> Connection.send
-> output flush / connection lifecycle
```

已经形成受限 HTTP/1.1、keep-alive、pipelining、partial request 保留、错误响应和关闭流程的实际证据。Week11 最终通过，出口评分为 `95/100`。

重要的不是“支持了多少 HTTP 功能”，而是你开始理解：**TCP 负责字节传输，application protocol（应用层协议）负责解释字节；业务处理与 Connection 的传输职责需要分开。**

### 3.2 你已经亲手复用底座，而不是重写第二套网络程序

你主动发现了 HTTP Server 和 Mini Redis 的共同结构：

```text
同一套 Buffer / Channel / EventLoop / Acceptor / Connection
-> 更换 application parser
-> 更换业务处理与 reply encoding
-> 接入 server-owned application state
```

这个认识很重要。它说明你已经在看组件的责任和复用边界，而不只是把各天代码分别写完。

Mini Redis 当前使用 **server 拥有的一份 `std::map<std::string, std::string>`**；每条 Connection 各自拥有 input/output。多客户端共享数据，半帧和待发送回复仍彼此隔离。

### 3.3 RESP 与命令语义已经形成完整链

Week12 Day1~Day6 已通过，当前链路是：

```text
客户端发送 RESP bytes
-> Connection 累积 input
-> parser 证明一条 frame 完整并给出 consumed_bytes
-> dispatcher 检查命令与参数数量
-> 访问共享 KvStore
-> encoder 生成 reply bytes
-> Connection 发送或保留待续传 output
```

当前已有 `PING / ECHO / SET / GET / DEL / EXISTS`。

更有价值的是你能区分三种结果：

- **NeedMore**：当前帧不完整，保留 bytes，等待后续。
- **合法帧中的命令错误**：返回命令错误，连接仍可继续。
- **协议格式错误**：返回协议错误，待回复发送完成后关闭坏连接。

你能解释 `SET k` 为什么是 parser 的 Complete、却是 dispatcher 的参数错误，也能解释下一条 PING 为什么可以继续。这比只把 SET/GET 跑通更接近真实协议工程。

### 3.4 多客户端验证开始围绕“状态是否真的建立”展开

最近的两个代表场景是：

**半帧隔离：** A 的 SET 尚未到齐，B 仍能 GET 旧值和 PING；补齐 A，并收到成功回复后，B 才检查新值。

**有限慢读：** A 发送很多请求但不读回复；用共享 KV 标记确认 A 的前序命令已执行，再验证 B 能 PING；之后 A 恢复读取，核对全部回复。

完整的缓冲链是：

```text
服务器 Connection output
-> 服务器内核发送缓冲
-> TCP
-> A 的内核接收缓冲
-> A 调用 recv
```

**A 不读时，它的内核仍能暂时接收数据。** 接收受限后，TCP 流量控制才会逐渐限制服务器发送；服务器遇到 `EAGAIN` 时，将未发送部分保留在 output，并等待 `EPOLLOUT` 继续发送。

你现在能够把“命令已执行”“回复尚未取走”“发送受阻”“其他客户端继续工作”分开理解。这里已经出现了系统工程的状态判断，而不只是协议模拟。

### 3.5 AI 理论线也有进展，但还没有进入 PyTorch

相较上一份小结，正式新增通过的是：

- **T4**：计算图、链式法则、解析梯度与有限差分检查；知道参数扰动、复制和异常恢复会影响验证是否可信。
- **T5**：概率对象、分类采样、频率与随机种子的实际代码验证；修复后最终 `100/100`。

ML 自学已经覆盖多变量线性回归、gradient descent（梯度下降）、feature scaling（特征缩放）、正规方程、logistic regression（逻辑回归）和 L2 regularization（L2 正则化）。这些理解应当复用，不能到 T7/T8 再完整重讲一遍。

但 **Ex1 尚未提交可运行证据，T7 尚未等价通过，PyTorch、attention 和 KV Cache 的代码证据也尚未形成**。理论理解和工程产出分开记账，既不漏掉你学过的，也不提前把后面的模块算完成。

## 六、接下来的学习方式要怎样变化？

### 6.1 两次 parser 训练已经有价值，下一阶段不靠继续写大模拟证明自己

HTTP 和 RESP 的核心状态判断由你亲手完成，已经训练了边界、长度、部分输入和错误分类。继续前进时，新增量应逐渐转到：

```text
数据什么时候失效
状态怎样持久化
失败后能够恢复到哪里
性能瓶颈到底在哪
怎样用实验支持一个优化
```

你提出了 HTTP 反复 find/扫描可能有较大常数、RESP 更直接推进 cursor 的观察。这是值得验证的性能假设；**没有固定输入、版本和 benchmark 之前，不能把它写成已经证明的加速结论。**

### 6.2 把精力留给需要你独立判断的地方

既定分工继续有效：

- **你负责**核心设计、状态模型、修复决定；性能阶段还要亲自理解 workload（工作负载）、测量、瓶颈和最终结论。
- **Codex 可以协助**重复 correctness cases、测试脚手架、构建配置、资料检索和机械记录；按你口述的 oracle（判断结果是否正确的依据）落成测试。
- **关键状态建立不能省略**。A 请求已执行、队列确实有 pending、发送确实到 EAGAIN，都需要具体证据，不能只靠测试名字或“跑过了”。

委托重复测试代码不损害学习。真正需要避免的是：连“这个测试为什么应该通过、失败意味着什么”也一并交出去。

### 6.3 让已有成果变得可复述，而不是只向前生成教程

不要求补写每一道验收题。Week12 Day7 适合用你自己的代码恢复一次完整请求链，并把代表证据接到结论上。

之后每个里程碑只保留少量真正有内容的故事：一个边界 bug、一段生命周期判断、一条故障实验或一项性能发现。这样到 Week16 时，简历和讲稿是在整理已有素材，而不是重新回忆一个月前写过的代码。
