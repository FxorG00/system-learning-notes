## 三、系统线：从处理字节，走向处理数据的状态

### 3.1 Week12 收口，证明你知道底座为什么能够复用

你没有重新画一套几乎一样的 HTTP/Redis 流程，而是口述了真正变化的部分：

```text
HTTP parser -> RESP parser
HTTP route/response -> command dispatcher/RESP reply
每连接 input/output 保持独立
服务器拥有一份共享 KvStore
网络与连接生命周期继续复用 Reactor
```

这种复盘有实际价值。你能把“某条命令已经修改 store”和“它的回复仍积压在 output”分开，也能说明另一个客户端随后 GET 为什么读到新值。

你还理解了：已经编码并由发送路径拥有的 reply bytes，不会因为后面 SET 或 DEL 改变 store 而自动变成另一条回复。**业务状态的变化和回复的送达，是两件有先后关系、但不能混成一件事的动作。**

Week12 Day7 最终 `100/100`，整周正式通过。这个分数评价本周要求与已有证据，不代表所有 Redis 或系统面试问题都已经掌握。

### 3.2 MySQL 建立了一个重要的第一层，但还不是面试纵深

Week13 Day1 最终 `98/100`。已有的小表、三组 SQL 和实际 EXPLAIN，让你不再只停在“数据库能存数据”的印象：

- 没有合适索引时，先看扫描与过滤。
- 用二级索引找到候选条目后，若还缺所需列，再取完整行。
- 查询只需要索引已经包含的内容时，可以省掉这段取完整行的过程。

你原来认为“同样用了 idx_course，取数据路径应该一样”，后来在笔记里修正了这个判断。**从预测出错到根据结果改模型，本身就是这次实验的有效产出。**

需要保留准确边界：`rows` 是优化器对检查规模的估计，和实际规模有关，但不是精确测量；EXPLAIN 路径变化也不直接给出加速倍数。此前两点已在验收对话补准，本次不重复扣分或要求重做实验。

事务、隔离、恢复和稳定的面试追问仍未全部闭环。后续继续按 Week13/14 的项目需要，以及图解资料的定向阅读补深，不另开一门完整 MySQL 课程。

### 3.3 TTL 组件是这段时间真正新增的系统机制

以前同一个 key 只需要判断有没有记录。现在还需要回答：**记录虽然仍在容器里，此刻是否还允许读取？**

你已经在原 KvStore 上建立了 value、到期时刻与当前时间的关系，并通过可控时钟检查到期边界。于是，“逻辑上失效”和“物理上已经回收”被分开了。

这次还遇到并修复了几类真实问题：

- 同一次组件调用内部重复取时间，使判断和剩余时长依据不同的时刻。
- 零或负 TTL 的分支虽然减少了取时，却一度没有保持有效、缺失、过期记录各自的返回语义。
- 默认时钟捕获方式需要让复制、移动后的对象仍使用正确的时间起点。
- 时间与期限范围检查，需要在约定的位置完成，失败时保持旧数据和旧期限。

**这比“给记录多加一个 deadline 字段”更接近系统设计：一个小功能会改变旧接口的状态判断、时间边界与对象生命周期。**

Week13 Day2 最终 `100/100`。已有验收记录包括原工程 CTest `75/75`、私有普通构建检查 `24/24`、ASan/UBSan 检查 `24/24`，覆盖路径无对应诊断。不同配置和检查组分别记录，不累加包装成互不重复的 123 项功能。

但现在通过的是 **KvStore 组件的毫秒 TTL 与时钟能力**。EXPIRE/PTTL 命令、整条多 key 命令共用一次时间观测、有预算的主动清理、空闲服务器维护，仍按 Day3~Day5 推进。本小结不把它们提前算成已经集成。

## 四、理论线：这一段不是只补了几个小公式

### 4.1 T6 把模型输出接到了概率与损失

T6 最终 `100/100`。你已经从 T5 的“给概率，再随机抽结果”，走到更前面的一步：

```text
模型为各类别产生 scores/logits，即原始分数
-> 沿明确的类别轴转成 probabilities，即概率
-> 用于预测或采样

logits + 数据提供的真实标签
-> 用于计算分类损失
```

这里有价值的不只是记住 softmax 公式，还包括多维输入应该沿哪个 axis 处理、稳定计算为什么要这样安排，以及标签和模型抽样结果为何承担不同角色。

你曾经对“这些分数从哪里来”和两个接口的 axis 不对称提出疑问，推动教程补齐对象链。**这不是学习障碍的证明，而是你在检查讲解有没有把来源、操作和用途接完整。**

### 4.2 Ex1/T7 已经把学过的回归变成实际训练证据

T7 最终 `98/100`，餐车和房价两个实际脚本作为等价产出，没有再要求你实现第二份同构回归程序。

这一段最有代表性的问题，是你发现损失中漏掉了与梯度约定一致的 `1/2` 系数。修正之后，损失与梯度才在描述同一个目标。

房价实验也澄清了一件容易让人误判的事：**原始 loss 数值很大，不一定表示训练没有收敛。** 它还受到目标值单位和损失定义影响。已有验收中，房价目标约为 20.43 亿美元平方，对应 RMSE，即均方根误差，约 6.39 万美元；梯度下降结果已经接近独立最小二乘参照。

因此，本次不因为绝对 loss 大就继续加特征工程，也不把接近训练集最优解释成已经证明真实房价泛化能力。独立最小二乘参照由 Codex 验收补充，不能写成你已经手写了相应求解器。

今天纳入的 AIInfraGuide，以及已有书籍和 InfraTech，都按当前问题择优调用。**新增资料带来的收益应当是解释更清楚、重复更少，而不是你每天又多了一份必须看完的清单。** 教材润色和资料整理是教学准备，不计入你的课程通过数量。

### 8.3 把必须亲自判断的部分留在自己手里

重复的 correctness tests，即正确性测试、构建脚手架和机械记录，可以继续由 Codex 协助；前提是你能解释测试输入、正确结果和失败意味着什么。

状态模型、核心设计和修复理由仍由你掌握。性能阶段尤其要亲自理解：测的是什么负载，瓶颈证据来自哪里，修改改变了什么，以及收益和代价。脚本可以协作，**最终性能结论要能由你独立捍卫**。

### 8.4 对教程的要求继续落实，不让你反复为同一问题付费

你最近对 logits、EXPLAIN、验证数据用途和 R3 剩余任务的追问，都指向同一个问题：先有熟悉对象和实际用途，再出现新术语与一般规则。

这已经进入 MEMORY 的高优先级教学规则。后续我应当从你的真实实现继续讲，并保护用户增补；不能每一篇重新退回名词列表、接口规格和含糊的检阅摘要，再让你一遍遍指出问题。

另一方面，你已经掌握的内容允许快速收口，但“看起来重复”和“新增行为已经有证据”仍需要分开判断。不要只用教程页数或测试代码行数决定要不要做，先看它在验证哪一个真正新变化。

## 九、对实习目标与这段学习的评价

**按你最新澄清，先完整学完Week16，再整理简历、向匹配中小厂试投；11月是希望达到的窗口，实际以学习完成为准。** 首批主要检验简历能否约面、真实面试过程和自己的缺口，不要求当月拿offer。实际资格与到岗安排仍需逐岗确认。

投递层次保持原规划：C++/Linux 后台与系统基础设施为主投；AI 业务基础设施、模型服务外围后端为冲刺；核心推理引擎与 CUDA 优化继续积累相应证据。T8 完成不是直接获得 GPU 岗位能力，却已经让 AI 方向从“以后想学”变成了有训练程序和实验流程支撑的路线。

和最开始相比，你现在遇到的问题明显更具体了：为什么同一次调用读两次时间会出错，为什么训练损失和梯度必须描述同一个目标，为什么用一份已经参与开发的数据做最终评估不够独立。

**能发现、解释并修好这些问题，就是这段时间的进步。** 它们不会像“又学完一章”那样每天给出强烈成就感，但会进入你最终真正能讲清楚的项目。

所以我的判断是：**你不是原地转圈，而是在从“把核心代码写出来”，走向“让状态、实验和结论都站得住”。** 现在需要继续收束，不需要用更多课程或更花哨的项目给自己加压。

下一步很明确：

```text
系统：Week13 Day3 -> TTL 集成 -> AOF/恢复 -> 性能与项目收口
理论：T9 -> T10 -> T11 -> T12，再按实际证据校准后段
求职：完整学完Week16后再做简历、试投中小厂，用真实反馈定位缺口
```

先把眼前这两步走稳。你已经做出了能运行的服务器，也已经把第一段 ML 实验写成了代码；后面的能力仍然可以像前面一样，一块一块建立起来。
