# Part 1：同一批 values，为什么 operator 还在乎 layout

## 0. 从一个 transpose 开始

```python
base = torch.arange(24, dtype=torch.float32).reshape(2, 3, 4)
transposed = base.transpose(1, 2)
```

`base` shape 是 `(2,3,4)`，`transposed` shape 是 `(2,4,3)`。看上去像生成了一个新三维数组，但 PyTorch 通常没有移动 24 个 values；它只换了“怎样用 indices 找到 storage 中元素”的描述。

于是出现三个问题：

1. `transposed` 如何在不复制 data 的情况下读出正确 values？
2. 为什么某些 `view(...)` 在它上面失败，`reshape(...)` 却可能成功？
3. 为什么这会影响 hidden copy、kernel choice 与 inference latency？

今天要建立的对象模型是：

```text
Tensor
= storage + dtype + device + shape + stride + storage_offset
```

Tensor 不只是“有 shape 的数组”。它是对一块 typed storage 的带 layout 视图。

## 1. Shape 只回答“有哪些 indices”

`base.shape == (2,3,4)` 表示合法 index：

```text
i in [0,2)
j in [0,3)
k in [0,4)
```

Shape 没说明 `(i,j,k)` 对应 storage 的哪个位置。这个映射由 stride（步幅）与 storage offset（存储起始偏移）完成：

$$
\operatorname{offset}(i,j,k)
=
\operatorname{storage\_offset}
+i\,s_0+j\,s_1+k\,s_2
$$

其中 $(s_0,s_1,s_2)$ 是 stride。

## 2. Base stride 为什么是 `(12,4,1)`

在标准 row-major contiguous layout 中：

```text
最后一维前进一步 -> 跨 1 个 element
中间维前进一步 -> 跨 4 个 elements
第一维前进一步 -> 跨 3*4 = 12 个 elements
```

所以：

```python
base.stride() == (12, 4, 1)
```

例如 `base[1,2,3]` 对应：

$$
1\cdot12+2\cdot4+3\cdot1=23
$$

因此它读 storage 中第 23 个 element。

Stride 单位是 elements，不是 bytes。若要估算 byte displacement，还要乘 `element_size()`。

## 3. Transpose 只交换 metadata

`transpose(1,2)` 交换第二、第三个 dimension：

```text
shape  (2,3,4) -> (2,4,3)
stride (12,4,1) -> (12,1,4)
```

Storage 不变，index-to-offset formula 变了。因此 `transposed[0,1,2]` 访问的是：

$$
0\cdot12+1\cdot1+2\cdot4=9
$$

它与 `base[0,2,1]` 指向同一个 element。

这种多个 Tensor objects 引用同一 storage 的关系叫 aliasing（别名/共享底层存储）。修改一个 alias，另一个可能观察到变化。

## 4. Contiguous 到底表示什么

Contiguous（连续布局）不是“这块 storage 在内存里存在”，也不是“Tensor values 没有间隔”。它表示当前 shape 与 strides 满足某个连续 memory format 的规则，使逻辑遍历顺序能直接映射到顺序 storage。

```python
base.is_contiguous()        # True
transposed.is_contiguous()  # 通常 False
```

Non-contiguous Tensor 仍然合法，很多 operators 能直接处理。问题是某些 operations 需要特定 layout；它们可能拒绝、选择慢路径，或先 materialize 一份 contiguous copy。

Materialize（实体化）表示真正分配新 storage 并写入重新排列后的 values。

## 5. Slice 为什么还需要 storage offset

```python
sliced = base[1:]
```

`sliced` 可继续共享 base storage，但它的第一个逻辑 element 不再是 storage 第零项。`storage_offset()` 记录当前 Tensor 从 storage 的哪个 element 开始解释。

比较：

```python
base.untyped_storage().data_ptr()
sliced.untyped_storage().data_ptr()
```

它们可显示相同 storage base address；而 `Tensor.data_ptr()` 指向各自第一个逻辑 element，可能因 offset 不同而不同。

Pointer 只能作为当前实验的一条证据。不要仅凭一个地址比较推断全部 alias relation；还要结合 mutation、stride 与 storage offset。

# Part 3：Layout 改变时，各 API 承诺什么

## 9. `view`：只允许 metadata 能表达的重解释

`view(new_shape)` 要求新 shape 可以在不重排 values、不分配新 storage 的条件下表达。

```python
flat = base.view(-1)
```

对 contiguous base 通常成立。对 transpose：

```python
transposed.view(-1)
```

可能抛 `RuntimeError`，因为当前 strides 无法表示所需的一维逻辑顺序。

`view` 的价值正是 contract 清晰：成功时共享 data；无法只改 metadata 时拒绝。

## 10. `reshape`：优先 view，必要时允许 copy

```python
reshaped = transposed.reshape(-1)
```

`reshape` 会尽量返回 view；若 layout 不允许，可分配新 storage 并复制。调用者不能把它承诺成 zero-copy。

因此性能敏感代码若依赖“这里没有 copy”，不能只看到 API 名叫 `reshape`。要检查 profiler、storage relation 或更强的 layout contract。

## 11. `contiguous`：按目标 memory format 物化

```python
packed = transposed.contiguous()
```

若 input 已符合目标 memory format，它可以返回自身；否则分配新 storage 并按逻辑顺序复制。

典型链：

```python
flat = transposed.contiguous().view(-1)
```

这条链明确接受一次 materialization cost。

## 12. `clone` 与 `contiguous` 不同

`clone()` 的核心承诺是复制 values 到独立 storage，并保留 autograd relation。它不等价于“无条件变成默认 contiguous format”；memory format 还受 input layout 与参数影响。

因此：

```text
需要独立 storage -> clone
需要特定 contiguous layout -> contiguous
两者都需要 -> 写清两个目标，不凭名字猜
```

T9 只观察 storage/layout；autograd relation 留到 T11。

## 13. Dtype 同时改变数值范围与 memory

```python
x32 = torch.arange(8, dtype=torch.float32)
x64 = x32.to(dtype=torch.float64)
```

Payload：

```text
float32: 8 * 4 bytes
float64: 8 * 8 bytes
```

`to(dtype=...)` 返回 Tensor；不要忘记接住返回值。转换通常需要新 storage 与 value conversion。

Dtype 不只是打印后缀。它影响：

```text
可表示范围
精度
memory bytes
memory bandwidth
operator support
kernel choice
```

后续 FP16/BF16/INT8 仍沿同一条成本链，只是数值与 kernel 边界更复杂。

## 14. Device：storage 在哪里、谁能执行

Device（设备）描述 storage 与 computation 所在位置，例如 CPU 或 CUDA GPU。

CPU baseline：

```python
device = torch.device("cpu")
tensor = tensor.to(device=device)
```

Guarded accelerator path：

```python
if torch.cuda.is_available():
    cuda_tensor = tensor.to("cuda")
```

同一 operation 的 operands 通常必须在兼容 device 上。Device transfer 可能引入：

```text
allocation
host-device copy
synchronization
latency
```

没有 CUDA 时记录 CPU path 并继续；不要伪造 GPU evidence。

## 15. NumPy bridge：copy 还是 share

### `torch.tensor(array)`

通常复制 input data，得到独立 Tensor。

### `torch.from_numpy(array)`

CPU 上通常与 NumPy array 共享 memory。修改任一侧，另一侧可能观察到变化。NumPy dtype 必须是 PyTorch 支持的类型。

### `tensor.numpy()`

满足 CPU、可转换 dtype/layout、无需要梯度等条件时，可共享 storage。训练 Tensor 常写：

```python
array = tensor.detach().cpu().numpy()
```

这条链中 `detach` 处理 autograd relation，`cpu` 处理 device，`numpy` 处理 object bridge；是否最终 copy 仍取决于前面是否真的发生 device/layout conversion。

不要把三种 API 统一记成“Tensor 与 NumPy 可以互转”。它们的 ownership 和 copy contract 不同。

## 16. In-place operation 的第一层风险

带 `_` 的 operation 通常原地修改，例如：

```python
tensor.add_(1.0)
```

若存在 aliases，所有共享 storage 的 views 都可能观察到变化。T11 还会看到另一个风险：autograd 可能需要旧 value 计算 backward，in-place mutation 会破坏保存的 version。

当前纪律：

```text
做 in-place 前先问谁 share storage
证据实验使用专用 clone
不要为了“省一次 allocation”提前牺牲 correctness
```

# Part 4：综合实验与 AI Infra

## 17. Round3 的五段短实验

在同一 `tensor_layout.py` 顺序组织：

1. **Metadata**：base/transpose/slice 的 shape、stride、offset。
2. **Reshape boundary**：展示 `view` failure、`reshape` result 与 `contiguous().view(...)`。
3. **Aliasing**：`from_numpy` 共享、`torch.tensor` copy。
4. **Dtype bytes**：float32/float64 payload 与 value tolerance。
5. **Device branch**：CPU 必做，CUDA available 时只做一次 transfer round trip。

每段以 exact assertion 或明确 observation 收口，不需要另写 pytest suite。

## 18. 高价值 failure contracts

程序应主动识别：

```text
输入不是 Tensor
unexpected shape/stride prediction
view failure 没有发生
alias mutation 与预期不符
non-finite value
device branch 产生 mismatch
```

Expected failure 要捕获具体 exception 并继续；unexpected failure 要 non-zero exit。不要仅打印红字后仍输出 PASS。

## 19. 与 AI Infra 的直接连接

### Hidden copy

Model 收到 non-contiguous input，某个 operator 内部先 pack 成 contiguous storage。Functional output 正确，但 latency 与 memory peak 增加。Profiler 中突然出现的 copy/contiguous kernel 往往来自这里。

### Memory estimate

Tensor payload first-order estimate：

$$
\text{bytes}
=
\prod_d\text{shape}_d
\times
\text{bytes per element}
$$

它是 planning estimate，不是 allocator/process/GPU peak。后续 activation、workspace、fragmentation、cache 与 framework objects 还会增加。

### Serving input contract

Inference API 除了 logical shape，还可能要求：

```text
dtype
device
layout/stride
contiguity
alignment
```

若 boundary 不明确，cost 会藏在 model 前处理里。

### Operator dispatch

Framework 根据 dtype、device、layout 与 operator 选择 kernel。相同 shape/value，不同 metadata 可能走不同实现。

## 20. 通过标准

```text
能从 shape/stride/offset 手算 storage position
能解释 transpose 为什么通常 zero-copy
能区分 view、reshape、contiguous、clone
能用 mutation + metadata 建立 alias evidence
能说明 dtype/device/layout 对 memory 与 kernel 的影响
CPU 全流程通过；CUDA 不可用不阻塞
```

不要求读取 PyTorch allocator/source，不做 CUDA benchmark，不把实验扩成 Tensor 工具库。
