# Part 1：同一批 values，为什么 operator 还在乎 layout

## 0. 今天先解决一个地址问题

**今天写一个观察程序：同一批数经过转置、切片和复制后，数放在哪里，程序又怎样找到它们？** T8中你已经能写对矩阵计算，这一课把目光移到矩阵背后的存储与访问。

先接上熟悉的NumPy写法。PyTorch中的Tensor（张量）也是带shape的多维数值对象；本课先在CPU上使用它，不涉及自动求导或训练。

```python
import torch

small = torch.arange(6, dtype=torch.float32).reshape(2, 3)
print(small)
print(tuple(small.shape))  # (2, 3)
print(small[1, 2].item())  # 5.0
```

`torch.arange(6)`产生0到5，`reshape(2,3)`按两行三列解释它们，`.item()`把单元素Tensor中的数取成Python数值。索引和矩阵乘法的基本读法沿用你已经掌握的NumPy经验，PyTorch矩阵乘法同样写`@`。

T8用float64做数值对照，本课固定float32观察布局和字节数；这不是要你回改T8。环境沿用[统一环境说明](../ENVIRONMENT.md)，不新建venv或重复安装。

先别背 Tensor 的字段。看一个最小矩阵：

```text
[[0, 1, 2],
 [3, 4, 5]]
```

它的 shape 是 `(2,3)`。但真实内存不会长成一个画出来的方格；可以先把底层数据想成一条连续 storage（存储区）：

```text
storage position: 0  1  2  3  4  5
value:            0  1  2  3  4  5
```

现在问：程序收到逻辑 index `[1,2]` 时，怎样在这条 storage 中找到 value `5`？

Shape 只能告诉我们：第一维可以取 `0~1`，第二维可以取 `0~2`。它还没有告诉我们每个 index 前进一步要跨过多少个 storage elements。

## 1. 为了算地址，我们需要两个步长

从 `[0,0]` 走到 `[0,1]`，storage 向后移动 `1` 个 element。

从 `[0,0]` 走到 `[1,0]`，要跨过完整一行，storage 向后移动 `3` 个 elements。

因此 `[1,2]` 的 storage position 是：

$$
1\times3+2\times1=5
$$

刚才自然出现的 `(3,1)`，就是这个 Tensor 的 stride（步幅）：**每个 axis 的 index 增加 $1$ 时，底层 storage position 要增加多少个 elements。**

二维情况的一般写法是：

$$
\operatorname{offset}(i,j)
=
\operatorname{storage\_offset}
+i\,s_0+j\,s_1
$$

当前 Tensor 从 storage 第零项开始，所以 `storage_offset=0`；$s_0=3,s_1=1$。

Stride 的单位是 **elements**，不是 bytes。若 `float32` 一个 element 占 `4` bytes，byte displacement 还要再乘 `4`。

## 2. Transpose 为什么可以不搬 data

现在对矩阵做 transpose：

```text
[[0, 3],
 [1, 4],
 [2, 5]]
```

最直接的做法是分配新 storage，再把六个 values 按新顺序复制一遍。但 PyTorch 通常可以只改变解释规则：

```text
原 Tensor：shape (2,3)，stride (3,1)
转置后：  shape (3,2)，stride (1,3)
storage：  仍然是 [0,1,2,3,4,5]
```

例如转置后的 `[2,1]`：

$$
2\times1+1\times3=5
$$

它仍然找到原 storage 中的 value `5`。**Transpose 改的是 index-to-storage mapping，不一定改 storage 本身。**

两个 Tensor objects 因而可以引用同一块 storage。这种关系叫 aliasing（别名/共享底层存储）；其中一个原地修改 value，另一个可能立刻看见变化。

## 3. 多一个维度，只多一项寻址

二维地址已经能算，推广到三维时，每个axis（维度轴）各贡献一项：

$$
\operatorname{position}(i,j,k)
=\operatorname{storage\_offset}+i s_0+j s_1+k s_2.
$$

这里的$s_0,s_1,s_2$依次表示三个维度各前进一步要跨过多少个元素。先从最内层有多少元素，再看跨完整一层需要走多远，就能自己得到这些步长。

R1会换成一份三维数据，让你先算再运行。这里保留方法，具体对象的stride与切片offset留给你的首次预测；R1通过后再在§9核对推导。

## 4. 现在再给 Tensor 一个完整对象模型

为了正确解释“某个 index 对应哪个 value”，一个 Tensor 至少需要这些信息：

```text
storage：values 实际存放在哪里
dtype：每个 element 怎样解释、占多少 bytes
device（设备）：storage 位于 CPU 还是其他计算设备
shape：有哪些合法 logical indices
stride：各 axis 前进一步怎样改变 storage position
storage_offset：当前 Tensor 从共享 storage 的哪一项开始
```

所以可以把对象模型压缩成：

```text
Tensor
= storage + dtype + device + shape + stride + storage_offset
```

这些描述对象的信息合称metadata（元数据）。它们说明怎样解释和访问数据，本身不是另存一份元素。上面的对象模型是本课普通稠密Tensor的理解模型，完整Tensor还可能有自动求导等其他信息，T11再展开。

## 5. Contiguous 表示当前布局能顺序走完

原始 `(2,3)` Tensor 的 stride `(3,1)` 与标准 row-major（按行优先）顺序一致：逻辑上从左到右、从上到下遍历时，storage 也依次读取 `0,1,2,3,4,5`。这种 layout 是 contiguous（连续布局）。

Transpose 后 stride 变成 `(1,3)`。逻辑遍历顺序对应的 storage positions 是：

```text
0, 3, 1, 4, 2, 5
```

它仍然是完全合法的 Tensor，但不再符合刚才的默认连续布局。继续使用 §0 已创建的二维 `small`，直接运行：

```python
small_t = small.transpose(0, 1)
print(small.is_contiguous())    # True
print(small_t.is_contiguous())  # False
```

Operator（算子）就是对Tensor执行的一项计算，例如矩阵乘法。某些算子能直接沿这些stride读取；另一些需要连续输入，于是可能拒绝、选择另一种底层计算实现，或复制成一份连续存储。最后这种动作叫materialize（物化）：为逻辑上的数据真正分配并填充一份存储。它会产生分配与复制成本，后面做推理服务时还会遇到。

### 5.1 Slice 为什么还需要 storage offset

继续在二维 `small` 上只取第二行：

```python
small_slice = small[1:]
```

`small_slice` 继续共享 `small` 的 storage，但它的第一个 logical element（逻辑元素）已经是原来的 `small[1,0]`。`storage_offset()` 记录当前 Tensor 从共享 storage 的哪一个 element 开始解释；本例是从第 3 项开始，编号从 0 算。

比较：

```python
small.untyped_storage().data_ptr()
small_slice.untyped_storage().data_ptr()
```

本例两者返回相同的 storage 起点；而 `Tensor.data_ptr()` 指向各自第一个逻辑元素。small_slice 从下一行开始，所以它的第一个元素地址比 small 前进 $3\times4=12$ bytes。

地址比较是观察存储关系的一条证据。再修改一个具体位置，看另一个对象是否看到同一处变化，才能把“两个对象关联哪份数据”与实际动作接起来。

## 7. 需要读哪些信息，每组回答一个问题

不用先背八个 API。按用途分三组，写程序时用到哪组就查哪组。

| 要回答的问题 | 使用的调用 | 怎样读 |
|---|---|---|
| 一个索引怎样找到元素？ | `tuple(t.shape)`、`t.stride()`、`t.storage_offset()` | 合法索引范围、各轴步长、在 storage 中的起点 |
| 两个对象关联同一份数据吗？ | `t.untyped_storage().data_ptr()`、`t.data_ptr()`，再做一次元素修改 | 前者是存储区起点，后者是当前对象第一个元素地址；修改检验对应位置是否共享 |
| 逻辑顺序是否连续，当前对象表示多少数据？ | `t.is_contiguous()`、`t.numel()`、`t.element_size()` | 默认布局下是否连续、元素总数、每个元素占几个字节 |

这里 `t` 就是你传入的 `base`、`transposed` 或 `sliced`。这些调用读取已有属性，不要求你手算出属性再填给 PyTorch。

为了少写重复打印，可以自行写一个辅助函数：

```python
def describe(name: str, tensor: torch.Tensor) -> None:
    ...
```

`name` 是打印时的标签，`tensor` 是要观察的对象；函数只显示信息，返回 `None`。`describe` 是你自己的函数名，不是 PyTorch API，也不是本课考察函数设计的重点。直接分开打印同样可以。

先看一条已经会读的小例子：

```python
print(tuple(small.shape), small.stride(), small.numel(), small.element_size())
# (2, 3) (3, 1) 6 4
```

再把同样的读取方式用到本轮三个对象。当前 Tensor 的 **payload（逻辑元素数据量）** 按下面计算：

$$
\text{payload bytes}
=
\text{numel}\times\text{element size}
$$

它回答“当前对象的所有逻辑元素合计多少字节”。切片可以只覆盖共享存储的一部分，几个共享对象的这个数字也不能直接相加当成实际分配量；Python 对象和分配器自身还有额外开销。

地址只比较关系，不把某次运行的整数地址硬编码进脚本。本课对象都在同一个进程、CPU 上，并且保持存活，适合做这组地址与修改对照。

## 8. 具体检查什么，怎样开始运行

### 8.1 先检查同一个数的两种索引

转置交换的是后两个维度。因此对合法索引，有：

```python
transposed[i, j, k] == base[i, k, j]
sliced[i, j, k] == base[i + 1, j, k + 1]
```

这两行是索引对应关系，不是让程序直接执行的比较循环。切片第一维从 1 开始，最后一维也从 1 开始，所以回到 base 时这两项各加 1。

先把一对具体位置写成检查：

```python
assert transposed[1, 2, 0].item() == base[1, 0, 2].item()
assert sliced[0, 1, 2].item() == base[1, 1, 3].item()
```

之后可以用短循环遍历各自的合法索引，按同一关系比较所有元素。这里的预期来自转置/切片的定义，不是拿两次相同计算互相证明。

### 8.2 再验证一次修改是否传回原对象

另建专用数据，避免改坏前面还要检查的 0～23：

```python
probe_base = torch.arange(24, dtype=torch.float32).reshape(2, 3, 4)
probe_transposed = probe_base.transpose(1, 2)
probe_transposed[1, 2, 0] = -99.0
assert probe_base[1, 0, 2].item() == -99.0
```

观察到的是同一 storage 位置被改了；另一个 Tensor 只是用自己的索引读到了它。再把 `base/transposed/sliced` 的 storage 起点与各自 `data_ptr()` 放在一起看，解释地址关系是否与索引、offset 一致。

# Part 3：Round2，继续展平与复制这些数据

## 9.0 我的 api 总结

### view

> 能否在共享原来的 storage 的情况下，换一个 shape。也就是只改变 shape 和 stride。
>
> .view(-1) 就是尝试展开成一维。

### reshape

> 换一个 shape。但是允许在没办法共享原来的 storage 的情况下，去把原来的数据按逻辑顺序，连续排在新 storage。只保证改变形状，不保证之后一定连续。

### contiguous

> 保持 Tensor 形状和数值，把数据按当前逻辑顺序放进连续布局后返回。（保证之后在 storage 上连续）但是不保证一定会复制到独立副本。

### clone

> clone 保证独立存储

### Dtype

> 每个元素是什么类型，占几个字节

### device

> CPU 有自己那一侧的内存，就是 host/system memory（主机内存）。
>
> GPU 也有自己的 VRAM(显存)。
>
> Tensor 用 device 来区分自己这份数据位于 cpu 那一侧的内存/gpu 那一侧的内存。
>
> device 为 cpu/gpu 会影响底层调用的算子。

### numpy 与 torch

#### torch.tensor(array)

> 从 numpy 的 ndarray 复制数据，得到独立存储的 Tensor

#### torch.from_numpy(array)

> 返回的 Tensor 与 array 共享 cpu 内存。也就是共享 storage

#### tensor.numpy()

> 返回共享数据的 numpy 的 ndarray


## 9. `view`：换一个 shape，共享原来的数据

**你的 R1 已经把索引和共享关系跑通了。后半继续维护 `t09/tensor_layout.py`，保留 `describe()`、两组索引循环和专用的 `probe_base/probe_transposed`，不重新写一套观察程序。**

### 9.1 先解释你这次真正算错的一项

手绘预测里，base 的 `(12,4,1)`、转置后的 `(12,1,4)` 和切片起点 `13` 都正确。你最初把 sliced 的 stride 写成 `(9,3,1)`，随后在 note 中根据实际结果改成了 `(12,4,1)`。这次值得弄清的是：**少了几列，为什么跨到下一行仍要走 4 个位置？**

切片后的三行显示为 `13,14,15`、`17,18,19`、`21,22,23`，但原 storage 中的 `16` 和 `20` 并没有被搬走。切片只是跳过它们；从第一行的起点走到第二行的起点，仍沿原来的存储跨 4 个元素。本例恰好用 `arange` 让值等于存储位置，所以 `17-13=4` 能帮助你看见这段距离；一般数据的数值之差不能用来求 stride。

你在 note 中说“slice 没改变相对顺序，所以 stride 不变”，方向对，再补一个条件就准确了：**本例是步长为 1 的基础切片，它改变范围和起点，沿各轴前进一步仍走原来的距离。** 例如 `base[:, :, ::2]` 沿最后一维每前进一步，都对应原轴前进 2 个位置，最后一维 stride 就会变成 `2`；仅凭“相对顺序没变”还推不出步长不变。

再核对你已运行的三个对象：

| 对象 | shape | stride | storage offset | 默认连续布局 | 元素数 | 逻辑 payload |
|---|---|---|---:|---|---:|---:|
| `base` | `(2,3,4)` | `(12,4,1)` | 0 | 是 | 24 | 96 bytes |
| `transposed` | `(2,4,3)` | `(12,1,4)` | 0 | 否 | 24 | 96 bytes |
| `sliced` | `(1,3,3)` | `(12,4,1)` | 13 | 否 | 9 | 36 bytes |

base 从内向外数得到 `(12,4,1)`；转置交换后两个轴，也交换对应步长。你手绘中从原索引 `(1,0,1)` 算出 $1\times12+0\times4+1\times1=13$，这正是切片起点。sliced 第一维长度只有 1，运行时没有下一层可供比较；这里的第一维 stride 仍由基础切片保留，不是把新 shape 相乘重新算出的 9。

你修后的 `describe()` 已在两处正确调用 `data_ptr()`，能打印真正的整数地址。现在比较三次调用的结果：storage 起点相同，sliced 的 `data_ptr()` 则比 base 前进 $13\times4=52$ bytes。

现有 helper 已显示 `numel` 和 `element_size`，接下来只再显示它们的乘积。三个对象依次是 `96 / 96 / 36 bytes`：**sliced 表示 36 bytes 的逻辑元素，但仍关联原来那块 96 bytes 的 storage。** 这是本轮输出的小补项，不要求重做已有循环。

例如`transposed[0,1,2]`的存储位置是：

$$
0\times12+1\times1+2\times4=9.
$$

它对应`base[0,2,1]`，就是你第一组循环验证的关系。原手绘预测和 note 继续保留，不需要用正确表格覆盖它们。

### 9.2 先看 `view` 做什么，返回什么

**现在想做的事很简单：把一个两行三列的 Tensor 看成一条六个数的一维 Tensor，并继续使用原来的数据。**

先用前面已经会读的二维 `small`。这组小例子可以加在现有 `main()` 的后半；保留 R1 的三维 `base`，另用下面的变量名：

```python
small = torch.arange(6, dtype=torch.float32).reshape(2, 3)
small_flat = small.view(-1)

print(small_flat)               # tensor([0., 1., 2., 3., 4., 5.])
print(tuple(small_flat.shape))  # (6,)
print(tuple(small.shape))       # (2, 3)
```

**`small_flat` 是 `view()` 返回的另一个 Tensor 对象。它的 shape 是 `(6,)`，与 small 共享 storage；small 自己仍然是 `(2,3)`。** 之后读取 `small_flat[4]`，就是通过这个一维对象访问数据。

```text
small：shape (2,3)       ─┐
                        ├─ 同一块 storage：[0,1,2,3,4,5]
small_flat：shape (6,)   ─┘
```

这里新建的是描述这份数据的 Tensor 对象，六个元素没有另复制一份。你在 R1 已经观察过这种关系：两个对象用不同索引，访问同一份存储。

**`-1` 表示这一维的长度交给 PyTorch 推断。** 本例只要求一维，原来有 6 个元素，所以推断结果是 `(6,)`；写成 `small.view(2, -1)` 则是固定第一维为 2，第二维推断为 3。一处调用至多让一个维度使用 `-1`。

#### 这一次为什么只改描述就够了

small 原来逐行读出的数是 `0,1,2,3,4,5`，新的 small_flat 也按这个顺序读。数据本来就这样排在 storage 中：

```text
small_flat 的索引 n： 0  1  2  3  4  5
对应 storage 位置：   0  1  2  3  4  5
```

所以 small_flat 只需用 `shape=(6,)`、`stride=(1,)`、`storage_offset=0` 描述。每次索引加 1，就在原存储中前进一个元素，完全不用搬数据。

#### 再把同一个需求交给转置结果

现在仍用这六个数，只交换 small 的两个轴：

```python
small_t = small.transpose(0, 1)
print(small_t)
# tensor([[0., 3.],
#         [1., 4.],
#         [2., 5.]])
```

从使用者眼里按“每行从左到右，再到下一行”读取，顺序已经变成：

```text
small_t 的逻辑顺序：0, 3, 1, 4, 2, 5
原 storage 的排列： 0, 1, 2, 3, 4, 5
```

**想把 small_t 展成一维，目标结果就应是 `[0,3,1,4,2,5]`。** 换 shape 要保留当前 Tensor 的逻辑元素顺序；直接返回 `[0,1,2,3,4,5]`，就变成了另一份结果。

**`view` 给同一 storage 建立的是一套新的 shape/stride/offset 描述；以后访问返回的 Tensor 时，仍由这套描述计算位置。** 它不会额外保存一张 `[0,3,1,4,2,5]` 的逐元素位置表，所以不能靠“按表依次跳到这些位置”完成本次展平。

这次还要坚持共享原 storage，所以一维对象访问的 storage 位置也必须依次为 `0,3,1,4,2,5`。一维 Tensor 只有一个 stride，寻址公式是：

$$
\operatorname{position}(n)
=\operatorname{storage\_offset}+n\times s.
$$

$n$ 是新的一维索引，$s$ 是这一个维度的 stride。索引每增加 1，位置都必须增加相同的 $s$。但这里实际要求的跳跃是：

```text
位置：  0 -> 3 -> 1 -> 4 -> 2 -> 5
变化：    +3   -2   +3   -2   +3
```

**没有一个固定的步幅能同时等于这些变化。** 因而在原 storage 上，无法用一维 shape 和一个 stride 表达所需顺序；`small_t.view(-1)` 就会抛出 `RuntimeError`。

到这里再概括 `view(new_shape)` 的约定：**保留当前逻辑元素顺序，尝试只调整 shape/stride 等描述，返回共享原数据的 Tensor；所要求的形状无法这样表达时，抛出错误。** 原对象的 shape 保持不变。

### 9.3 回到你 R1 的三维对象

你的 `base.view(-1)` 可以按 `0～23` 得到 shape 为 `(24,)` 的一维 Tensor；原 base 仍是 `(2,3,4)`。换成 `transposed`，展平应保留你第一组循环已经验证过的逻辑顺序，开头是 `0,4,8,1,5,9,...`。

这次同样无法用一个固定的一维 stride 访问原 storage。二维例子已经把原因走通，不必再重抄一整张三维地址表；在现有脚本中用这一次具体调用验证它：

```python
view_failed = False
try:
    transposed.view(-1)
except RuntimeError:
    view_failed = True
assert view_failed, "expected this transpose to reject view(-1)"
```

这个检查只捕获本课固定 `transposed.view(-1)` 的预期失败。它确认的是当前目标形状无法共享原存储来表达；某些非连续 Tensor 的其他形状变换仍然可以满足 stride 条件。

检查完成后，接下来的问题很自然：**所需的一维结果并没有不合理，只是原存储不能那样解释。如果允许重新存一份数，能不能完成？** [官方查证：Tensor.view](https://docs.pytorch.org/docs/2.14/generated/torch.Tensor.view.html)

## 10. `reshape`：同一个需求，允许必要时复制

**需求不变：仍然把当前 Tensor 按逻辑顺序展成一维。现在只放宽一项条件：共享原数据做不到时，允许复制（并且如果复制的话，会按当前逻辑在 storage 上排成连续）。** 这就是接下来使用 `reshape` 的原因。

回看二维 small_t，需要的结果一直是 `[0,3,1,4,2,5]`。
允许分配新 storage 后，就可以把数按这个顺序重新排好：

```text
原 storage：[0,1,2,3,4,5]
新 storage：[0,3,1,4,2,5]
新对象：shape (6,)，stride (1,)
```

回到你实际的三维 transposed，执行：

```python
reshaped = transposed.reshape(-1)
```

`reshaped` 是返回的一维 Tensor。原 transposed 保持不变，shape 仍为 `(2,4,3)`。

**`reshape` 能共享就共享，必要时复制。** 它保证目标形状和逻辑值，不保证零拷贝。本例的展平需要复制。

先确定要比较什么：按 `transposed[i,j,k]` 读取，就是按 `base[i,k,j]` 读取。
所以开头应是 `0,4,8,1,5,9,...`。

继续用你已有的 `i/j/k` 关系构造参考值：

```python
expected_flat = torch.tensor(
    [base[i, k, j].item()
     for i in range(2) for j in range(4) for k in range(3)],
    dtype=base.dtype,
)
assert torch.equal(reshaped, expected_flat)
```

`torch.equal(a,b)` 检查 shape 和逐元素值是否相同。本例的小整数可以直接精确比较。

然后比较 reshaped 与 base 的 storage 起点。**本例应得到独立存储**，但其他布局的 `reshape` 也可能共享。

最后调用 `describe("reshaped", reshaped)` 显示新结果。
保留原来两组索引循环；它们继续验证转置和切片的对应关系。

## 11. `contiguous`：先按逻辑顺序排紧，再换 shape

> **保持 Tensor 形状和数值，把数据按当前逻辑顺序放进连续布局后返回。（变在 storage 上连续）**

刚才让 `reshape` 决定是否复制。现在把这件事拆成两步：**先排紧，再换 shape。**

```python
packed = transposed.contiguous()
```

返回的 packed 与 transposed 形状、数值相同。
本例会新建 storage，按当前逻辑顺序排好数据；原 transposed 不变。

这里采用默认的连续格式。memory format（内存格式）描述的就是这类布局要求。

接着把 packed 展成一维：

```python
packed_flat = packed.view(-1)
```

packed_flat 与 packed 共享刚才排好的 storage。
这两步连写，就是 `transposed.contiguous().view(-1)`。

现在做两项比较：

- packed_flat 与 §10 的 expected_flat：形状和逐元素值一致。
- packed 与 transposed：形状和数值一致，但 packed 已是连续布局。

**本例的成本是先复制并排紧，再用 view 共享新存储。**

再看 `base.contiguous()`：base 原本就满足要求，所以返回 base 自身。
`contiguous()` 保证布局；是否复制取决于输入。[官方查证：Tensor.contiguous](https://docs.pytorch.org/docs/2.14/generated/torch.Tensor.contiguous.html)

也观察一次 `sliced.contiguous()`。本例会得到 stride `(9,3,1)`，正好对应你最初设想的“九个元素紧挨着排好”。

原 sliced 没有进行这次复制，因此仍是 `(12,4,1)`。
两个对象的逻辑值相同，存放方式不同。

## 12. `clone` 与 `contiguous` 不同

如果希望修改副本时不影响原数据，需要的是**独立存储**。

对同一个 transposed 调用 `cloned = transposed.clone()`。
它返回一份独立副本，原 transposed 保持不变。

先验证两件事：cloned 与 transposed 的 shape/value 相同，storage 起点不同。
再观察 stride 和连续性。

本课的转置完整覆盖原来的 24 个位置，每个位置只访问一次。
默认 clone 会保留这份转置 stride，因此副本仍然非连续。

这与 §11 的 packed 不同：packed 已经按默认连续布局排紧。

**独立存储与连续布局是两个问题：clone 保证前者，contiguous 处理后者。**

你已有的 probe 证明了共享修改：改变转置 view 的 `[1,2,0]`，原对象 `[1,0,2]` 会变成 `-99`。
这次沿用同一对索引，只把修改目标换成 cloned：

1. 保存 `base[1,0,2].item()`。
2. 修改 `cloned[1,2,0]`。
3. 确认 base 仍保留原值。

这样就得到对照：**view 的修改会传回，clone 的修改不会传回。**
保留原 probe，不用新实验替换它。[官方查证：clone 的默认保留格式规则](https://docs.pytorch.org/docs/2.14/generated/torch.clone.html)

补充一个后续边界：clone 的布局受输入和参数影响，不能一概当成默认连续布局。
原对象若参与自动求导，clone 也会保留相应求导关系；T11 再展开。

现在把四个接口放回具体需求中：

| 现在想做什么 | 对应操作 | 返回结果的关键关系 |
|---|---|---|
| 换 shape，并坚持共享原数据 | `view` | 返回共享 storage 的 Tensor；当前布局无法表达目标形状时失败 |
| 换 shape，必要时可以复制 | `reshape` | 返回所需形状的 Tensor；可能共享，也可能使用新 storage |
| 得到目标连续布局 | `contiguous` | 已满足时可返回自身；本课转置输入需要复制并排紧 |
| 得到可以**独立修改**的数据副本 | `clone` | 返回独立 storage 的 Tensor；布局是否默认连续另行判断 |

**先走通 §9～§12 的主线，再进入 §13～§16。**
接下来仍在同一个脚本中，分别观察 dtype、device、NumPy 共享与原地修改，不新增一套程序。

T9 只观察 storage/layout；autograd relation 留到 T11。

## 13. Dtype：每个元素怎样解释，占多少字节

R1 的三个对象都是 float32。你的 `describe()` 已读出：每个元素占 4 bytes。

现在保持元素个数不变，只换类型：

```python
x32 = torch.arange(8, dtype=torch.float32)
x64 = x32.to(dtype=torch.float64)
```

`to(dtype=...)` 返回转换后的 Tensor。本例需要新存储，原 x32 仍是 float32。

**若目标dtype/device本来就相同，`to`可以返回原对象。**

接住返回值后再检查，不能只根据“调用过 to”判断原对象已经改变。

逻辑数据量直接算：

```text
float32: 8 * 4 bytes = 32 bytes
float64: 8 * 8 bytes = 64 bytes
```

复用 `describe()` 的字节数乘积显示，再断言 x64 的 payload 是 x32 的两倍。

数值是否保留，也有明确的比较方法：把 x64 转回 float32，再与 x32 比。

```python
assert torch.equal(x64.to(dtype=torch.float32), x32)
```

本例的 0～7 都能精确表示，所以应当相等。

**dtype 决定元素的解释方式和每项字节数，因此影响 payload。**
它也影响范围与精度；其他浮点值转换时可能有误差，低精度推理的取舍以后再展开。

## 14. Device：主机内存、GPU显存与执行设备

本节先接回你已经学过的 C++ 内存模型，再看 GPU 增加了什么。
这里使用常见的“主机 + 独立 NVIDIA GPU”作为例子。

### 14.1 从 C++ 数据到 Tensor 的 device

#### 第一步：普通 C++ 数据仍在主机内存这一侧

你用 `std::vector<float>` 保存数值时，程序通过进程虚拟地址访问它们。
普通主机内存中的这些数据通常由 RAM 支撑，CPU 读取它们并计算。

```text
程序中的数组
-> 通过进程虚拟地址访问
-> 主机内存中的数据
-> CPU 读取并计算
```

这一侧内存叫 **host/system memory（主机内存）**。

PyTorch 的 CPU Tensor 沿用这幅图景。
**“CPU Tensor”表示数据属于主机内存这一侧，不是永久放在 CPU 芯片内部。**

#### 第二步：GPU 增加了另一侧内存

常见独立 GPU 有自己的 **device memory（设备内存）**，通常也叫 **VRAM（显存）**。

```text
CPU 一侧                         GPU 一侧
host memory                     device memory
主机 RAM                         GPU 显存
```

现在，同样一组数可能在主机内存，也可能已经有一份位于 GPU 显存。
因此计算前需要知道：**这份数据到底在哪一边？**

#### 第三步：Tensor 用 device 记录所属设备

`device`（设备）就是 Tensor 记录这件事的信息。

- `device="cpu"`：这份数据属于 CPU/主机一侧。
- `device="cuda:0"`：这份数据属于编号 0 的 CUDA 设备。

**CUDA** 是 NVIDIA 的 GPU 计算平台。
你在 PyTorch 中使用 `cuda`，就是进入对应的 GPU 设备路径。

普通 CPU 算子使用 CPU 一侧的数据。CUDA 算子则使用相应 GPU 一侧的数据。
所以 device 会影响接下来怎样准备输入、由哪一侧执行计算。

#### 第四步：先搬数据，再交给 GPU 算子

假设 cpu_tensor 已在 CPU 上，执行 `cuda_tensor = cpu_tensor.to(device="cuda")`。

这个调用解决的是**取得 GPU 侧数据**的问题。
它返回 CUDA Tensor；原 cpu_tensor 仍留在 CPU 侧，不会原地变成 CUDA Tensor。

```text
cpu_tensor 的主机侧数值
-> 复制到 CUDA 设备
-> cuda_tensor 的 GPU 侧数值
-> 后续 CUDA 算子使用它计算
```

**搬运与计算是两个动作。**
`to("cuda")` 先取得设备侧数据，之后调用算子才是在这份数据上做计算。

### 14.2 用你的 base 做一次设备往返

保留 R1 的 base。它已经在 CPU 上，dtype 也没有变，所以本例的 `to("cpu")` 返回原对象。
这正好接上你在 §13 加粗的说明。

然后在 CUDA 可用时，做一次 CPU → CUDA → CPU 的往返：

```python
cpu_tensor = base.to(device="cpu")
assert cpu_tensor.device.type == "cpu"
if torch.cuda.is_available():
    cuda_tensor = cpu_tensor.to(device="cuda")
    returned = cuda_tensor.to(device="cpu")
    assert returned.device.type == "cpu"
    assert torch.equal(returned, cpu_tensor)
    print("CUDA ROUND TRIP PASS")
else:
    print("CUDA SKIP")
```

`tensor.device` 返回的是 `torch.device` 对象。
这里读它的 `type`，再与字符串 `"cpu"` 比较。

这项实验检查的是：**数据往返后，形状和数值是否保持。**
它没有执行新的 GPU 数值计算，也没有测搬运性能。

没有 CUDA 时打印 SKIP，CPU 检查照常完成。
如果 CUDA 已可用，但搬运发生意外异常，应保留错误，不能改印 SKIP。

#### 补充边界，先认识到这里

- 上面的箭头表示数据关系。CPU 读取时可以命中缓存，不要求每次都重新读取 RAM。
- Python 层的 Tensor 对象仍由当前进程管理；放到 GPU 一侧的是它关联的数值 storage。
- 普通非标量 Tensor 一起计算时通常需要兼容设备。统一内存、复制操作和部分标量有专门规则，以后遇到再展开。

当前先掌握主机内存、GPU 显存、device 和显式搬运这条链。

[官方查证：PyTorch device](https://docs.pytorch.org/docs/2.14/tensor_attributes.html#torch.device)、[Tensor.to](https://docs.pytorch.org/docs/2.14/generated/torch.Tensor.to.html)、[CUDA计算语义](https://docs.pytorch.org/docs/2.14/notes/cuda.html)、[NVIDIA主机与设备内存](https://docs.nvidia.com/cuda/cuda-programming-guide/02-basics/understanding-memory.html)。

## 15. NumPy bridge：copy 还是 share

刚才的 probe 在两个 Tensor 之间验证共享。现在把其中一侧换成你已经熟悉的 NumPy array，仍问同一个问题：**改这一侧，另一侧会不会读到变化？** 下列小数组独立于 main 中的 base，避免污染原来的索引检查。

### `torch.tensor(array)`

从本课的NumPy数组复制数据，得到**独立Tensor**。

### `torch.from_numpy(array)`

在支持的NumPy数组上**共享CPU内存**。本课使用可写的float32数组，修改任一侧，另一侧会看到对应位置变化。

```python
import numpy as np

array = np.array([1.0, 2.0], dtype=np.float32)
shared = torch.from_numpy(array)
copied = torch.tensor(array)
array[0] = 9.0
print(shared[0].item(), copied[0].item())  # 9.0 1.0
assert shared[0].item() == 9.0
assert copied[0].item() == 1.0
```

这正好承接你在T1/T4处理过的共享与独立快照：先看实际修改传到哪一侧，再确认存储关系。

再做一次反方向修改：给 `shared[1]` 赋一个新值，检查 `array[1]` 跟着变化。这样验证共享关系的两个使用方向，不把打印两个数当成完整检查。

### `tensor.numpy()`

本课的 CPU float32 Tensor **可返回共享数据的 NumPy 数组**。下面先保留一条训练时常见的调用示意，**它不加入今天的实验脚本**；`training_tensor` 代指训练过程中已有的 Tensor：

```python
training_array = training_tensor.detach().cpu().numpy()
```

在本课已创建的 shared 上，直接执行 `back = shared.numpy()`，修改 `back[0]` 并查看 `shared[0]`，便能观察 CPU Tensor 返回 NumPy 后的共享。它不需要上面的训练 Tensor 写法。

那条训练用链中，`detach` 处理自动求导关系，`cpu` 处理设备，`numpy` 返回数组；是否发生复制取决于实际转换。`detach` 的机制留 T11，不列为今天的新实现任务。

不要把三种 API 统一记成“Tensor 与 NumPy 可以互转”。它们的 ownership 和 copy contract 不同。

## 16. In-place operation 的第一层风险

你写的 `probe_transposed[1,2,0] = -99.0` 已经是一次原地修改。带 `_` 的 operation 通常也原地修改；下面只是换一种写法观察相同的共享关系，单独运行这组小数据即可：

```python
inplace_data = torch.tensor([1.0, 2.0])
inplace_alias = inplace_data[:]
inplace_data.add_(1.0)
assert torch.equal(inplace_alias, torch.tensor([2.0, 3.0]))
```

`add_` 改的是原来的存储，同一位置的 alias 因而读到加一后的值。T11 还会看到另一个风险：自动求导可能需要旧 value 计算反向传播，原地修改会与这些保存值冲突。

当前纪律：

```text
做 in-place 前先问谁 share storage
证据实验使用专用 clone
不要为了“省一次 allocation”提前牺牲 correctness
```

### 18.2 真正运行失败时怎样处理

| 具体情况 | 程序动作 |
|---|---|
| §9 那一次 `transposed.view(-1)` 抛 RuntimeError | 只在该调用周围捕获，确认这次预期拒绝发生，再继续 |

## 19. 为什么推理服务会在乎今天的实验

假设服务收到的输入有三个轴：批次、序列位置、特征。
预处理交换后两个轴，得到下一步需要的 shape；底层 storage 却仍按旧方式排列。

后续算子可以沿现有 stride 读取，也可能选择另一种实现，或复制出所需布局。
**非连续不等于一定复制，具体行为由算子与实现决定。**

沿需要复制的路径继续：

```text
预处理交付转置后的 Tensor
-> 后续计算需要另一种布局
-> 内部创建并填充一份临时数据
-> 计算结果仍正确
-> 多一次搬运，并有原输入与临时数据共存的阶段
```

只看输出数值，程序仍然正确。
要解释额外的内存和耗时，就需要今天的布局与存储观察。

### 19.1 先确认是不是多存了一份数据

本课 `transposed.reshape(-1)` 得到了正确结果，也使用了新存储。
如果只看到“换 shape”，就容易漏算这次复制。

调用处没有显式写复制，操作内部却发生数据搬运，这类成本叫 **hidden copy（隐式复制）**。

它与你 R1 的转置形成对照：两者都能值正确，但存储关系不同。
值比较回答“数算对了吗”；storage 起点和专用 mutation 帮助判断“是不是同一份数据”。

### 19.2 再把逻辑数据量与实际峰值分开

payload 仍按前面的方法计算：

$$
\text{bytes}
=
\prod_d\text{shape}_d
\times
\text{bytes per element}
$$

你的三个对象逻辑字节数是 `96 / 96 / 36`，但共享一块 storage。
因此不能把它们相加，当成 228 bytes 的独立分配。

sliced 只表示 36 bytes，却仍关联整块原存储。
若再创建副本，原数据与副本还可能同时存活。

**内存峰值要看哪些存储同时存在，不只看最终输出多大。**
分配器与其他临时状态也会影响实际占用。

### 19.3 在计算入口说清楚接受哪种输入

假设一个推理入口要求 float32、CPU、默认连续布局。
调用者需要知道这些条件，也需要知道转换由自己完成，还是由入口完成。

这些要求叫 **serving input contract（推理服务输入约定）**。
它把输入准备和转换成本的责任说清楚。

输入准备好以后，框架还要选择执行计算的底层实现。
选择会受到算子、设备、类型和布局等因素影响，这个动作叫 **operator dispatch（算子分派）**。

底层计算实现通常叫 **kernel（计算内核，这里不是操作系统内核）**。
因此相同 shape 不保证走同一条执行路径。

这些是未来工作的连接，不是新增作业。
T9 仍只证明布局与存储关系；以后遇到性能问题，再用 profiler（性能分析工具）检查复制、分配和耗时。

**本课的地址观察不能直接当成性能优化结论。**
