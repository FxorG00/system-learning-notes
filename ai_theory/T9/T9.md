# Part 1：同一批 values，为什么 operator 还在乎 layout

## 0. 今天先解决一个地址问题

**今天写一个观察程序：同一批数经过转置、切片和复制后，数放在哪里，程序又怎样找到它们？** T8中你已经能写对矩阵计算，这一课把目光移到矩阵背后的存储与访问。

先接上熟悉的NumPy写法。PyTorch中的Tensor（张量）也是带shape的多维数值对象；本课先在CPU上使用它，不涉及自动求导或训练。

```python
import torch

small = torch.arange(6, dtype=torch.float32).reshape(2, 3)
print(small)
print(tuple(small.shape))  # (2, 3)
print(small[1, 2].item())  # 5.0
```

`torch.arange(6)`产生0到5，`reshape(2,3)`按两行三列解释它们，`.item()`把单元素Tensor中的数取成Python数值。索引和矩阵乘法的基本读法沿用你已经掌握的NumPy经验，PyTorch矩阵乘法同样写`@`。

T8用float64做数值对照，本课固定float32观察布局和字节数；这不是要你回改T8。环境沿用[统一环境说明](../ENVIRONMENT.md)，不新建venv或重复安装。

先别背 Tensor 的字段。看一个最小矩阵：

```text
[[0, 1, 2],
 [3, 4, 5]]
```

它的 shape 是 `(2,3)`。但真实内存不会长成一个画出来的方格；可以先把底层数据想成一条连续 storage（存储区）：

```text
storage position: 0  1  2  3  4  5
value:            0  1  2  3  4  5
```

现在问：程序收到逻辑 index `[1,2]` 时，怎样在这条 storage 中找到 value `5`？

Shape 只能告诉我们：第一维可以取 `0~1`，第二维可以取 `0~2`。它还没有告诉我们每个 index 前进一步要跨过多少个 storage elements。

## 1. 为了算地址，我们需要两个步长

从 `[0,0]` 走到 `[0,1]`，storage 向后移动 `1` 个 element。

从 `[0,0]` 走到 `[1,0]`，要跨过完整一行，storage 向后移动 `3` 个 elements。

因此 `[1,2]` 的 storage position 是：

$$
1\times3+2\times1=5
$$

刚才自然出现的 `(3,1)`，就是这个 Tensor 的 stride（步幅）：**每个 axis 的 index 增加 $1$ 时，底层 storage position 要增加多少个 elements。**

二维情况的一般写法是：

$$
\operatorname{offset}(i,j)
=
\operatorname{storage\_offset}
+i\,s_0+j\,s_1
$$

当前 Tensor 从 storage 第零项开始，所以 `storage_offset=0`；$s_0=3,s_1=1$。

Stride 的单位是 **elements**，不是 bytes。若 `float32` 一个 element 占 `4` bytes，byte displacement 还要再乘 `4`。

## 2. Transpose 为什么可以不搬 data

现在对矩阵做 transpose：

```text
[[0, 3],
 [1, 4],
 [2, 5]]
```

最直接的做法是分配新 storage，再把六个 values 按新顺序复制一遍。但 PyTorch 通常可以只改变解释规则：

```text
原 Tensor：shape (2,3)，stride (3,1)
转置后：  shape (3,2)，stride (1,3)
storage：  仍然是 [0,1,2,3,4,5]
```

例如转置后的 `[2,1]`：

$$
2\times1+1\times3=5
$$

它仍然找到原 storage 中的 value `5`。**Transpose 改的是 index-to-storage mapping，不一定改 storage 本身。**

两个 Tensor objects 因而可以引用同一块 storage。这种关系叫 aliasing（别名/共享底层存储）；其中一个原地修改 value，另一个可能立刻看见变化。

## 3. 多一个维度，只多一项寻址

二维地址已经能算，推广到三维时，每个axis（维度轴）各贡献一项：

$$
\operatorname{position}(i,j,k)
=\operatorname{storage\_offset}+i s_0+j s_1+k s_2.
$$

这里的$s_0,s_1,s_2$依次表示三个维度各前进一步要跨过多少个元素。先从最内层有多少元素，再看跨完整一层需要走多远，就能自己得到这些步长。

R1会换成一份三维数据，让你先算再运行。这里保留方法，具体对象的stride与切片offset留给你的首次预测；R1通过后再在§9核对推导。

## 4. 现在再给 Tensor 一个完整对象模型

为了正确解释“某个 index 对应哪个 value”，一个 Tensor 至少需要这些信息：

```text
storage：values 实际存放在哪里
dtype：每个 element 怎样解释、占多少 bytes
device（设备）：storage 位于 CPU 还是其他计算设备
shape：有哪些合法 logical indices
stride：各 axis 前进一步怎样改变 storage position
storage_offset：当前 Tensor 从共享 storage 的哪一项开始
```

所以可以把对象模型压缩成：

```text
Tensor
= storage + dtype + device + shape + stride + storage_offset
```

这些描述对象的信息合称metadata（元数据）。它们说明怎样解释和访问数据，本身不是另存一份元素。上面的对象模型是本课普通稠密Tensor的理解模型，完整Tensor还可能有自动求导等其他信息，T11再展开。

## 5. Contiguous 表示当前布局能顺序走完

原始 `(2,3)` Tensor 的 stride `(3,1)` 与标准 row-major 顺序一致：逻辑上从左到右、从上到下遍历时，storage 也依次读取 `0,1,2,3,4,5`。这种 layout 是 contiguous（连续布局）。

Transpose 后 stride 变成 `(1,3)`。逻辑遍历顺序对应的 storage positions 是：

```text
0, 3, 1, 4, 2, 5
```

它仍然是完全合法的 Tensor，只是不再符合这套连续 memory format：

```python
base.is_contiguous()        # True
transposed.is_contiguous()  # 通常 False
```

Operator（算子）就是对Tensor执行的一项计算，例如矩阵乘法。某些算子能直接沿这些stride读取；另一些需要连续输入，于是可能拒绝、选择另一种底层计算实现，或复制成一份连续存储。最后这种动作叫materialize（物化）：为逻辑上的数据真正分配并填充一份存储。它会产生分配与复制成本，后面做推理服务时还会遇到。

### 5.1 Slice 为什么还需要 storage offset

```python
sliced = base[1:]
```

`sliced` 可以继续共享 `base` 的 storage，但它的第一个 logical element 已经不是 storage 第零项。`storage_offset()` 记录当前 Tensor 从共享 storage 的哪一个 element 开始解释。

比较：

```python
base.untyped_storage().data_ptr()
sliced.untyped_storage().data_ptr()
```

它们可以显示相同 storage base address；而 `Tensor.data_ptr()` 指向各自第一个 logical element，可能因 offset 不同而不同。

Pointer comparison 只是一条 evidence。判断是否共享 storage 时，还应结合 mutation、stride 与 storage offset，而不是只看一个地址数值。

## 7. Metadata helper

可自行设计输出格式，至少包含：

```python

    ...
```

使用：

```python

tensor.numel()
tensor.element_size()

```

这些调用各自读什么：

| 调用 | 当前用途 |
|---|---|
| `tuple(tensor.shape)` | 每个维度有多少个位置 |
| `stride()` / `storage_offset()` | 沿各轴怎样走，以及从共享存储的哪里起步 |
| `is_contiguous()` | 是否符合默认连续内存格式 |

| `untyped_storage().data_ptr()` | 共享存储区的起始地址 |
| `data_ptr()` | 当前Tensor第一个元素的地址 |

例如只打印前面的`small`：

```python

```

`describe`只负责把已有信息显示出来；输出排版由你决定，不需要写成通用Tensor检查库。

Selected Tensor payload：

$$
\text{payload bytes}
=
\text{numel}\times\text{element size}
$$

这个值不包括 Python object、allocator metadata、shared storage 中未被当前 view 覆盖的部分，也不是 process peak memory。

# Part 3：Layout 改变时，各 API 承诺什么

## 9. `view`：只允许 metadata 能表达的重解释

先核对R1的地址：连续`base`的shape是`(2,3,4)`，从内向外数得到stride`(12,4,1)`；交换后是shape`(2,4,3)`、stride`(12,1,4)`。`sliced=base[1:,:,1:]`的shape为`(1,3,3)`，stride仍为`(12,4,1)`，offset为`1*12+1=13`，并非连续布局。

例如`transposed[0,1,2]`的存储位置是：

$$
0\times12+1\times1+2\times4=9.
$$

它对应`base[0,2,1]`。如果预测不同，先找出是轴交换还是切片起点算错，保留你的原预测作为学习轨迹。

现在有一个新需求：把转置后的逻辑顺序摊成一维。对二维例子，这个顺序是`0,3,1,4,2,5`；原存储却仍为`0,1,2,3,4,5`。只靠一个固定的一维步长，能沿这个顺序读取吗？这就是`view`要检查的问题。

`view(new_shape)` 要求新 shape 可以在不重排 values、不分配新 storage 的条件下表达。

```python
flat = base.view(-1)
```

对 contiguous base 通常成立。对 transpose：

```python
transposed.view(-1)
```

对本课固定的`transposed`，这次摊平会抛`RuntimeError`，因为当前stride无法表示所需的一维逻辑顺序。它不是说所有非连续Tensor都不能`view`；有些其他形状变换仍满足stride条件。

`view` 的价值正是 contract 清晰：成功时共享 data；无法只改 metadata 时拒绝。

## 10. `reshape`：优先 view，必要时允许 copy

```python
reshaped = transposed.reshape(-1)
```

`reshape` 会尽量返回 view；若 layout 不允许，可分配新 storage 并复制。调用者不能把它承诺成 zero-copy。

因此性能敏感代码若依赖“这里没有 copy”，不能只看到 API 名叫 `reshape`。要检查 profiler、storage relation 或更强的 layout contract。

## 11. `contiguous`：按目标 memory format 物化

```python
packed = transposed.contiguous()
```

若 input 已符合目标 memory format，它可以返回自身；否则分配新 storage 并按逻辑顺序复制。

典型链：

```python
flat = transposed.contiguous().view(-1)
```

这条链明确接受一次 materialization cost。

## 12. `clone` 与 `contiguous` 不同

`clone()` 的核心承诺是复制 values 到独立 storage，并保留 autograd relation。它不等价于“无条件变成默认 contiguous format”；memory format 还受 input layout 与参数影响。

用刚才的`transposed`分别调用`clone()`和`contiguous()`：前者要独立拥有一份数，后者要让当前逻辑顺序变成连续布局。对于本课转置对象，默认`clone`可以保留转置stride；因此“是否独立”和“是否连续”需要分别检查。再改变副本中的一个元素，确认`base`没有跟着变，这次才完成独立副本的对照。

因此：

```text
需要独立 storage -> clone
需要特定 contiguous layout -> contiguous
两者都需要 -> 写清两个目标，不凭名字猜
```

T9 只观察 storage/layout；autograd relation 留到 T11。

## 13. Dtype 同时改变数值范围与 memory

```python
x32 = torch.arange(8, dtype=torch.float32)
x64 = x32.to(dtype=torch.float64)
```

Payload：

```text
float32: 8 * 4 bytes
float64: 8 * 8 bytes
```

`to(dtype=...)`返回转换后的Tensor，本例从float32变float64时需要新存储；原`x32`仍是float32。若目标dtype/device本来就相同，`to`可以返回原对象。接住返回值后再检查，不凭“调用了to”推断原对象已改变。

Dtype 不只是打印后缀。它影响：

```text
可表示范围
精度
memory bytes
memory bandwidth
operator support
kernel choice
```

后续 FP16/BF16/INT8 仍沿同一条成本链，只是数值与 kernel 边界更复杂。

## 14. Device：storage 在哪里、谁能执行

Device（设备）描述 storage 与 computation 所在位置，例如 CPU 或 CUDA GPU。

CPU baseline：

```python
device = torch.device("cpu")
tensor = tensor.to(device=device)
```

Guarded accelerator path：

```python
if torch.cuda.is_available():
    cuda_tensor = tensor.to("cuda")
```

同一 operation 的 operands 通常必须在兼容 device 上。Device transfer 可能引入：

```text
allocation
host-device copy
synchronization
latency
```

没有 CUDA 时记录 CPU path 并继续；不要伪造 GPU evidence。

## 15. NumPy bridge：copy 还是 share

### `torch.tensor(array)`

从本课的NumPy数组复制数据，得到独立Tensor。

### `torch.from_numpy(array)`

在支持的NumPy数组上共享CPU内存。本课使用可写的float32数组，修改任一侧，另一侧会看到对应位置变化。

```python
import numpy as np

array = np.array([1.0, 2.0], dtype=np.float32)
shared = torch.from_numpy(array)
copied = torch.tensor(array)
array[0] = 9.0
print(shared[0].item(), copied[0].item())  # 9.0 1.0
```

这正好承接你在T1/T4处理过的共享与独立快照：先看实际修改传到哪一侧，再确认存储关系。

### `tensor.numpy()`

满足 CPU、可转换 dtype/layout、无需要梯度等条件时，可共享 storage。训练 Tensor 常写：

```python
array = tensor.detach().cpu().numpy()
```

这条链中 `detach` 处理 autograd relation，`cpu` 处理 device，`numpy` 处理 object bridge；是否最终 copy 仍取决于前面是否真的发生 device/layout conversion。

不要把三种 API 统一记成“Tensor 与 NumPy 可以互转”。它们的 ownership 和 copy contract 不同。

## 16. In-place operation 的第一层风险

带 `_` 的 operation 通常原地修改，例如：

```python
tensor.add_(1.0)
```

若存在 aliases，所有共享 storage 的 views 都可能观察到变化。T11 还会看到另一个风险：autograd 可能需要旧 value 计算 backward，in-place mutation 会破坏保存的 version。

当前纪律：

```text
做 in-place 前先问谁 share storage
证据实验使用专用 clone
不要为了“省一次 allocation”提前牺牲 correctness
```

## 18. 高价值 failure contracts

把“有意展示API拒绝”和“实验程序写错”分开：

| 场景 | 程序怎样处理 |
|---|---|
| 本课`transposed.view(-1)`抛`RuntimeError` | 捕获这一次具体调用的错误，确认发生后继续 |
| 这次`view`意外成功 | 让检查失败，不能继续宣称已观察到拒绝 |
| 实际metadata与事前预测不同 | 保留原预测，找出差别；修改错误理解后再做最终检查 |
| 应共享的修改没有传过去，或独立副本反而改变base | 检查失败，程序非零退出 |
| dtype转换或可选设备往返结果不符 | 使用明确容差检查，失败则非零退出 |

这里没有接收任意外部请求的服务，不新增通用输入验证层。只捕获实验刻意制造的异常；其他异常保留原错误和非零退出码。此前T8的入口检查已完成，本课不重复一套非法输入工程。

## 19. 与 AI Infra 的直接连接

### Hidden copy

Model 收到 non-contiguous input，某个 operator 内部先 pack 成 contiguous storage。Functional output 正确，但 latency 与 memory peak 增加。Profiler 中突然出现的 copy/contiguous kernel 往往来自这里。

### Memory estimate

Tensor payload first-order estimate：

$$
\text{bytes}
=
\prod_d\text{shape}_d
\times
\text{bytes per element}
$$

它是 planning estimate，不是 allocator/process/GPU peak。后续 activation、workspace、fragmentation、cache 与 framework objects 还会增加。

### Serving input contract

Inference API 除了 logical shape，还可能要求：

```text
dtype
device
layout/stride
contiguity
alignment
```

若 boundary 不明确，cost 会藏在 model 前处理里。

### Operator dispatch

Framework 根据 dtype、device、layout 与 operator 选择 kernel。相同 shape/value，不同 metadata 可能走不同实现。

## 20. 通过标准

```text
能从 shape/stride/offset 手算 storage position
能解释 transpose 为什么通常 zero-copy
能区分 view、reshape、contiguous、clone
能用 mutation + metadata 建立 alias evidence
能说明 dtype/device/layout 对 memory 与 kernel 的影响
CPU 全流程通过；CUDA 不可用不阻塞
```

不要求读取 PyTorch allocator/source，不做 CUDA benchmark，不把实验扩成 Tensor 工具库。
