# Part 1：Round1，让模型与状态有名字

## 0. 从一个部署问题出发

**今天把模型的计算和参数装进一个对象，保存它，再让一个全新对象加载后算出同样的结果。** 这份程序叫`module_inference.py`，本课验证“模型能被重新使用”，不再训练一遍T8分类器。

T9里，你已经用`describe()`读出三个Tensor的信息，用`view(-1)`观察预期失败，再用NumPy修改看见共享与复制的区别。你现在能区分：**拿到另一个对象，不一定拿到独立数据。** 这些实验不重做。

今天把问题向前推一步：几个Tensor共同组成一个模型，怎样把它们作为一份有名字的状态管理？

T8的`train()`返回W、b，`predict()`再使用选中的参数。另一个进程要接着预测时，首先得保存这组数，还得知道各自的名字、shape，以及怎样接回计算。

本课再加一层计算，让这种管理需求更明显。**先看为什么要管理状态，再看PyTorch怎样替你登记它们。**

先想象不用 `nn.Module`。一个两层 network 完全可以写成普通 function：

```python
import torch

def forward(inputs, w1, b1, w2, b2):
    hidden = torch.relu(inputs @ w1 + b1)
    return hidden @ w2 + b2
```

数学计算没有问题。可训练结束以后，我们准备把它交给另一个 process 做 inference，立刻要回答：

```text
w1、b1、w2、b2 中哪些是必须保存的 state？
每个Tensor在checkpoint（保存模型状态的文件）中叫什么名字？
加载时怎样知道它应回到哪一层？
把 model 移到另一个 device 时，哪些 Tensors 要一起移动？
```

只有四个 Tensors 时可以手工维护。真实 model 有成百上千个 layers 和 state，继续靠调用者传递一张无名 Tensor 清单，很快就会失控。

因此我们需要一个对象同时保存两类信息：

```text
计算结构：forward 应按什么顺序执行
持久状态：哪些 Tensors 属于这个结构、叫什么、怎样保存和移动
```

PyTorch把这个对象叫`nn.Module`（可组合的模型单元）。State（状态）在这里首先指W、b这些需要跨多次调用保留的数。把名字和Tensor登记到模型，才能统一找到、保存和移动它们；写进磁盘文件则是后面的保存步骤。

`nn.Module`把这些状态组织成有名字的对象树。今天沿一个具体模型，看它怎样登记参数、保存数值，再交给全新对象使用。每一步的名字在实际用到时解释。

今天造一个小 Module，然后完整走一遍：

```text
构造模型
-> 查看已登记的参数与其他状态
-> 输入算出分数
-> 观察训练/评估行为
-> 取出按名字组织的状态并存盘
-> 构造全新对象并加载
-> 同一输入的输出对照
```

分三轮完成同一份`module_inference.py`：

| 读到哪里 | 本轮得到的能力 | 何时暂停 |
|---|---|---|
| R1，§0～§6 | 创建模型，运行forward，分清哪些Tensor属于模型状态 | 对象、名字和共享关系能解释后，先检阅 |
| R2，§7～§9 | 用四种组合区分模型行为与求导记录 | 两个开关各自控制什么已经验证后，暂停核对 |
| R3，§10～§18 | 保存状态、重建对象、恢复后比较输出，再对照Module.to | 完成同一程序的最终收口 |

**这是三个能力闭环，不是三份程序。** 先走通当前一层，再加入下一层需要的角色；不会为了分轮隐藏必要语法，也不要求你独立发明PyTorch的登记机制。

## 1. 最小 Module 先长什么样

先把新的计算接口接回T8。`nn.Linear(D,C)`创建一个持有权重和偏置的线性层对象。

给它一行D个特征，会返回C个分数。数学仍是你会的线性映射，但它把权重存成`[C,D]`，计算时转置：

$$
Z=X A^T+b,
\qquad X:[B,D],\quad A:[C,D],\quad Z:[B,C].
$$

T8的`weights[D,C]`与这里的`linear.weight[C,D]`排列不同，数学作用相同。

```python
import torch
from torch import nn

layer = nn.Linear(2, 3)
inputs = torch.tensor([[1.0, 2.0]], dtype=torch.float32)
print(tuple(layer.weight.shape), tuple(layer(inputs).shape))
# (3, 2) (1, 3)
```

接下来的示例使用4个输入特征、6个中间值、3个类别分数。3只是本课固定样例，类本身仍接收`class_count`。

中间6个数称为hidden representation（隐藏表示）。这次调用产生的中间Tensor也叫activation（激活值）。ReLU把负数置零、保留非负数；它为何增加表达能力，T12再推导。

```text
4个输入特征 -> 6个中间值 -> ReLU -> 3个类别分数
```

先只造能计算的最小模型。本课重点在运行和解释状态，不要求先独立设计一套模型。

Python的`self`是当前对象。`super().__init__()`先初始化父类的登记机制。
`self.linear1`等成员跨调用保留；局部变量`hidden`每次调用重新产生。

```python
import torch
from torch import nn


class TinyClassifier(nn.Module):
    def __init__(self, input_dim: int, hidden_dim: int, class_count: int) -> None:
        super().__init__()
        self.linear1 = nn.Linear(input_dim, hidden_dim)
        self.activation = nn.ReLU()
        self.linear2 = nn.Linear(hidden_dim, class_count)

    def forward(self, inputs: torch.Tensor) -> torch.Tensor:
        hidden = self.activation(self.linear1(inputs))
        return self.linear2(hidden)
```

现在就创建它，并给一份固定输入。后面的片段都接着使用这两个对象，最后再合到§14的同一个脚本中。

```python
torch.manual_seed(2026)
input_dim, hidden_dim, class_count = 4, 6, 3
model = TinyClassifier(input_dim, hidden_dim, class_count)
inputs = torch.tensor(
    [
        [1.0, 2.0, 3.0, 4.0],
        [-1.0, 0.5, 2.0, -0.5],
    ],
    dtype=torch.float32,
)
outputs = model(inputs)
assert tuple(outputs.shape) == (2, 3)
```

`model`是持有计算结构与状态的对象。`outputs`是本次调用返回的分数Tensor。
一次调用不会训练这些参数；参数更新仍需要后续训练流程，本课不做训练。

Forward shape：

```text
inputs [B,input_dim]
-> linear1 [B,hidden_dim]
-> ReLU [B,hidden_dim]
-> linear2 [B,class_count]
```

先看到 concrete object，再命名：

- 整个 `TinyClassifier` 是 module（可组合模型单元）；
- `linear1` 等是 submodules（子模块）；
- `weight/bias` 是 parameters（由训练更新的注册 Tensor）；
- forward 中的 `hidden` 是 activation（本次执行产生的中间值）。

先把两件事看清：这个对象持有哪些层和参数；调用它时，数据怎样得到分数。
§4和§7会继续修改**同一个类**，当场说明新增角色的用途。每次改类后从头重新运行脚本，让`model = TinyClassifier(...)`创建新版对象，不保留多个同名类，也不靠交互环境给旧实例补状态。

## 2. Module 是一棵注册树

回看构造函数中的这一行；它在`__init__`内使用，不是单独执行的脚本片段：

```python
self.linear1 = nn.Linear(...)
```

把线性层赋给`self.linear1`后，Module会把这个子模块登记到自己的树中。以后能顺着这个名字找到它的参数。

因此：

```python
for name, module in model.named_modules():
    print(name, type(module).__name__)

for name, parameter in model.named_parameters():
    print(name, tuple(parameter.shape))
```

能递归看到稳定 names：

```text
linear1.weight
linear1.bias
linear2.weight
linear2.bias
```

这些名字随后还会出现在保存的状态中。重命名成员后，旧文件就可能找不到对应位置。
这套名字和尺寸的约定称为schema（状态结构约定），§11再用真实加载错误观察它。

> 机制备注：普通属性赋值会经过`nn.Module.__setattr__`，由它识别并登记Module/Parameter。这解释登记如何发生；本课不展开Python特殊方法或元编程。

## 3. 为什么调用 `model(inputs)`，而不是直接 `forward`

你刚才已经用了正常入口：

```python
outputs = model(inputs)
```

它返回本次计算的Tensor，模型对象仍然保留，下一份输入可以继续调用。

`forward`只描述计算步骤。`model(inputs)`会先经过Module的调用入口，再执行这些步骤。
外层入口还负责hooks（钩子，例如调用前后执行的观察函数）。直接写`model.forward(inputs)`会绕过这部分机制；T14再使用hook观察中间shape。

这里的调用不会自动切换评估模式，也不会自动关闭求导记录。§7～§9分别设置这两个开关。

## 4. 一组固定缩放系数应该放在哪里

模型已经能计算。现在增加一个具体需求：**训练数据确定了一组固定缩放乘数，之后预测也必须用同一组数。** 这与你T7使用训练集预处理统计量是同一类需要；本课不重新估计它们。

比如4个特征使用`[1.0, 0.5, 1.0, 1.0]`，第二项先缩小一半，再进入线性层。

它跨多次预测保留，需要跟模型一起保存、一起移动设备；但它不是这次由梯度下降更新的weight。

我们需要把这份Tensor登记为**属于模型、但不属于训练参数的状态**。PyTorch提供的这种角色叫buffer（注册缓冲状态）。

回到原类的`__init__`，在`self.linear2`之后增加：

```python
self.register_buffer(
    "input_scale",
    torch.ones(input_dim, dtype=torch.float32),
)
```

`register_buffer`把这份Tensor按名字登记到当前对象，返回`None`。之后通过`self.input_scale`使用它；默认会进入保存状态，也会跟随模型的设备转换。

然后把原类的`forward`替换为下面这个版本，只增加入口缩放：

```python
def forward(self, inputs: torch.Tensor) -> torch.Tensor:
    scaled = inputs * self.input_scale
    hidden = self.activation(self.linear1(scaled))
    return self.linear2(hidden)
```

默认全1先保留原数值规则。创建model后，再设置本次固定的第二项乘数：

```python
model.input_scale[1] = 0.5
outputs = model(inputs)
assert tuple(outputs.shape) == (2, 3)
```

重新运行时，这个模型先缩放输入，再计算分数。后面保存和恢复时，`0.5`也必须保住；不能只恢复两层weight。

现在各角色有了具体区别：

- **parameter**：如linear1.weight，以训练参数身份登记，默认允许求梯度。
- **buffer**：如input_scale，是模型需要长期保留的固定数值，本课不让优化器更新它。
- **activation**：如scaled、hidden，是本次forward根据输入临时算出的中间值。

参数也可以通过`requires_grad=False`冻结求导；选择buffer是为了表达这里的职责，不是说框架禁止冻结参数。T14会再看到其他固定状态的用途。

## 5. Parameter、buffer 与普通 Tensor attribute

那我直接把Tensor赋给普通属性，能不能获得同样的登记效果？在已有model上增加一个只用来对照的属性：

```python
model.debug_tensor = torch.zeros(1)
```

它仍可通过`model.debug_tensor`读到。现在检查它有没有进入登记名单：

```python
parameter_names = dict(model.named_parameters()).keys()
buffer_names = dict(model.named_buffers()).keys()
state_keys = model.state_dict().keys()
```

应观察：

```text
linear weights/biases -> parameters + state_dict
input_scale           -> buffers + state_dict
debug_tensor          -> neither
```

若buffer只想随device移动、不想写入checkpoint，可在构造函数里采用下面的写法。value代指已有Tensor；这是可选示意，不加入本课固定模型：

```python
self.register_buffer("temporary", value, persistent=False)
```

Persistent（持久）只决定是否进入 `state_dict`；它不把 buffer 变成 parameter。

## 6. `state_dict` 是 named Tensor mapping

```python
state = model.state_dict()
for name, tensor in state.items():
    print(name, tensor.shape, tensor.dtype)
```

它保存 registered parameters 与 persistent buffers，key 来自 module tree path。

`state`是按名字索引Tensor的字典式映射，不是第二个模型对象。

接上你T9的总结：**返回另一个对象，不等于复制了底层数值。** `state_dict()`里的Tensor默认仍共享模型状态的存储。

因此，训练到第100步取得`state`后再继续更新模型，它通常不能保住第100步的旧值。外层映射取出来了，数值没有成为独立快照；这叫shallow mapping（浅层映射）。

可以像T9一样比较`state["linear1.weight"].data_ptr()`与`model.linear1.weight.data_ptr()`，把共享关系接回实际数据。

这正是你在T4处理过的快照问题。若要在内存中保留那个时刻的值，再深拷贝：

```python
import copy

best_state = copy.deepcopy(model.state_dict())
```

仅写：

```python
best_state = model.state_dict()
```

不能可靠表达“以后 parameters 更新也不影响这个 snapshot”。

# Part 2：Round2，分开模型行为与求导记录

## 7. `train()` / `eval()` 改变谁的 behavior

R1的线性层与ReLU在训练和评估时采用相同计算规则。为了亲眼看见模式的作用，现在才加入一个会改变行为的层。

**Dropout（随机丢弃）**在训练模式临时把部分中间元素置零，保留值按保留概率缩放；评估模式直接保留输入。本课先观察开关，正则化理由留T13。

继续修改原类：在`__init__`中增加这一行，不改变已有参数和buffer：

```python
self.dropout = nn.Dropout(p=0.25)
```

把`forward`更新为下面这个版本，在隐藏值与输出层之间加入它：

```python
def forward(self, inputs: torch.Tensor) -> torch.Tensor:
    scaled = inputs * self.input_scale
    hidden = self.activation(self.linear1(scaled))
    hidden = self.dropout(hidden)
    return self.linear2(hidden)
```

重新运行脚本，创建带Dropout的新model。R1已经明确的参数名、buffer和state keys保持不变；只是多了一个没有参数的子模块。

Module 默认处于 training mode：

```python
model.training is True
```

```python
model.eval()
```

递归把 mode 切成 evaluation。真正改变 forward behavior 的是读取 `self.training` 的 layers，例如：

```text
Dropout
BatchNorm
自定义依赖 mode 的 Module
```

`Linear` 与 `ReLU` 通常在两种 mode 下行为相同。

先用一个完全确定的小例子看模式确实改变计算。这里刻意取`p=1.0`：训练时全部丢弃，eval时全部保留，因而不用赌两次随机mask恰好不同。

```python
probe = nn.Dropout(p=1.0)
ones = torch.ones(4)
probe.train()
torch.testing.assert_close(probe(ones), torch.zeros(4), rtol=0.0, atol=0.0)
probe.eval()
torch.testing.assert_close(probe(ones), ones, rtol=0.0, atol=0.0)
```

然后回到示例模型的`p=0.25`，观察真实随机行为：

```python
model.train()
train_a = model(inputs)
train_b = model(inputs)

model.eval()
eval_a = model(inputs)
eval_b = model(inputs)
```

在固定 state/input 下：

```text
train_a 与 train_b 可能不同
eval_a 与 eval_b 应相同
```

训练模式的两次输出允许相同，不把“它们一定不相等”写成断言；随机抽样不提供这种保证。模式差异的确定性证据来自刚才的独立probe。

## 8. `inference_mode()` 控制 autograd-related execution

T8的训练由你自己算gradient。PyTorch还可以记住forward的计算来路，以便后来自动求梯度，这套能力叫autograd（自动求导）。T11再展开。

现在只处理预测请求，不需要为本次计算保留这些求导记录：

```python
with torch.inference_mode():
    outputs = model(inputs)
```

`inference_mode()`提供的是`with`中的执行环境；真正产生outputs的仍是`model(inputs)`。
在这个环境中，本次计算不记录反向求导所需的操作，并减少相关跟踪开销。

先读`outputs.requires_grad`观察结果。模型的训练/评估状态仍由`train()`与`eval()`控制。

同样：

```python
model.eval()
```

不会自动关闭 autograd recording。

正常 inference boundary：

```python
model.eval()
with torch.inference_mode():
    outputs = model(inputs)
```

两者分别回答：

```text
eval：Module 应采用哪种行为
inference_mode：本次 execution 是否需要 autograd metadata
```

## 9. 四种组合亲自跑一次

现在两个开关都已经有用途：一个改Dropout的数值规则，一个决定本次计算是否记录求导关系。对同一model/input，各运行下面四种设置，参数不更新：

```text
train + grad enabled
train + inference_mode
eval  + grad enabled
eval  + inference_mode
```

记录：

```text
model.training
output.requires_grad
相同 input 重复两次是否 exact equal
```

它会直接证明 mode 与 gradient recording 不是同一个开关。

本例的预期读法是：

| 调用设置 | `model.training` | output的`requires_grad` |
|---|---|---|
| `model.train()`，普通执行 | True | True，因为模型参数需要梯度 |
| `model.train()`，放进`inference_mode()` | True | False |
| `model.eval()`，普通执行 | False | True |
| `model.eval()`，放进`inference_mode()` | False | False |

先调用`train()`或`eval()`设置模型行为，再选是否进入`with torch.inference_mode():`执行forward。`with`中的设置只管其缩进范围；退出后，外面的求导模式恢复，model的train/eval状态则保留，直到你再次切换。

# Part 3：Round3，保存状态再重建模型

## 10. Save：保存 state，不保存本次 activation

现在把这份按名字组织的状态写进文件：

```python
checkpoint_path = "tiny_classifier.pt"
torch.save(model.state_dict(), checkpoint_path)
```

文件记录这次传入的参数和持久buffer数值。`torch.save`完成写盘，返回`None`；原model仍可继续使用。

本次只传入state_dict，所以输入、hidden和模型构造参数不会自动写进去。重建模型的代码与尺寸配置还要另行保留。

因此 model architecture/config 必须来自：

```text
代码版本
明确 config
artifact metadata
```

## 11. Load：先构造 compatible object

```python
loaded_model = TinyClassifier(
    input_dim=input_dim,
    hidden_dim=hidden_dim,
    class_count=class_count,
)

state = torch.load(
    checkpoint_path,
    map_location="cpu",
    weights_only=True,
)
loaded_model.load_state_dict(state, strict=True)
loaded_model.eval()
```

`torch.load`返回从文件读出的状态映射，数值先按`map_location="cpu"`放在CPU侧。它没有替你创建TinyClassifier。

`load_state_dict`再把这些数装入已经构造好的loaded_model。它返回装载诊断，而不是新的模型对象。

`strict=True`要求参数和持久buffer的名字对齐，尺寸也必须兼容。保存时输出3类，改用输出4类的新对象加载，最后一层weight/bias就会尺寸冲突并抛`RuntimeError`。

这就是§2提到的schema：保存的名字和尺寸要与新对象对应。

## 12. Round-trip evidence

在保存前先得到reference（用于比较的参考输出）。这里复用T9的clone：为本次输出留一份独立数据。

```python
model.eval()
with torch.inference_mode():
    expected = model(inputs).clone()
```

加载 fresh object 后：

```python
loaded_model.eval()
with torch.inference_mode():
    actual = loaded_model(inputs)

torch.testing.assert_close(actual, expected, rtol=1e-5, atol=1e-6)
```

这个 evidence 证明：

```text
当前 architecture/config 可重建
state_dict keys compatible
parameter/buffer values 恢复
相同 mode/input 下 output 对齐
```

它不证明 artifact 在另一 PyTorch version、另一 operator backend 或任意 hardware 上 bitwise identical。

## 13. `Module.to` 与 `Tensor.to` 的重要差别

**T9的Tensor.to要接住返回值，为什么模型代码却常直接写model.to(...)？** 现在用同一类转换需求比较两种对象。

先沿用你已总结的Tensor规则：接住返回值，原对象不一定改变。

```python
converted = inputs.to(dtype=torch.float64)
```

本例converted是float64，原inputs仍为float32。目标类型和设备本就相同时，也可以返回原对象。

现在换成Module。另建一个专用模型观察，避免改变后面保存恢复实验的float32基线：

```python
probe_model = TinyClassifier(4, 6, 3)
probe_model.debug_tensor = torch.zeros(1)
returned_model = probe_model.to(dtype=torch.float64)
assert returned_model is probe_model
assert probe_model.linear1.weight.dtype == torch.float64
assert probe_model.input_scale.dtype == torch.float64
assert probe_model.debug_tensor.dtype == torch.float32
```

**Module.to原地转换已注册的参数与buffer，返回模型自身。** 你没有得到第二个独立模型。

普通debug_tensor没有登记为参数或buffer，因此没有跟着转换。这正是重要状态需要正确注册的原因。

这组区别只用CPU和dtype就能观察，不需要GPU。原model与inputs继续保持float32。

# Part 4：Round3收口与资料

## 14. `module_inference.py` 的完整顺序

保留已经完成的R1对象/状态检查和R2四种组合。现在使用加入input_scale与Dropout后的**同一个TinyClassifier类**，继续同一固定输入，不新建一套训练程序。

T9的最终整理由原实验与笔记等效覆盖。这一课真正新增的是保存后重建模型，因此**同一输入的保存/加载输出比较仍要实际运行**，不能只写API定义。

R3只增加下面的收口：

1. 在eval + inference_mode下保留参考输出，再保存state_dict。
2. 创建全新对象并strict load；确认input_scale的第二项也恢复成0.5。
3. 对同一输入比较新对象输出，使用§12的容差。
4. 另建不兼容class count的对象，确认strict mismatch；用§13的独立probe比较两种to，不改变主model的float32基线。
5. 正常完成打印：

```text
T10 MODULE INFERENCE PASS
```

第4步只在故意不兼容的load_state_dict周围捕获RuntimeError；没抛错就判检查失败。其他意外异常保留原错误和非零退出码。

正常浮点对照使用`rtol=1e-5, atol=1e-6`。shape、名字集合和mode布尔值精确比较；用普通Python运行，`assert`检查不在`-O`模式下执行。

```bash
python3 -B module_inference.py
```

## 15. Input 与 output contract

固定输入已经在§1创建：CPU、float32、shape为(2,4)，两行各代表一条输入。继续使用它。

本例的尺寸：

```text
input_dim=4
hidden_dim=6
class_count=3
output shape [2,3]
```

Assertions：

```text
output shape/dtype/device exact
all output finite
state keys exact
round-trip output close
eval repeat deterministic
inference output requires_grad == False
```

不需要 pytest、benchmark 或训练 loop。今天验证的是 object/state/inference boundary。

“output有限”直接检查`torch.isfinite(outputs).all()`：每个输出都应是普通有限数，出现NaN或正负Inf就让检查失败。这里检查的是本次固定输入的计算结果，不让你为模型新增一整套T8式外部输入校验。

## 16. Save/Load 的安全边界

序列化就是把状态编码进文件，反序列化是从文件恢复对象或数据。本课只加载自己保存的文件，并显式使用`weights_only=True`限制加载方式；它缩小风险，不等于任意来源的文件都安全。不要为本课下载陌生模型或执行任意pickle对象。

后续部署还需管理模型版本、配置、输入约定和文件校验等信息。这是未来的artifact管理范围，不要求本课另写管理系统，也不把它们全部塞进state_dict。

## 17. 与 AI Infra 的连接

假设服务启动时加载一次文件，随后用同一个model处理多份输入。参数和buffer跨请求保留；每次计算产生的activation属于该次执行。

这把T9的“数据在哪里、是否独立”推进到模型层：一份模型状态由哪些Tensor组成，哪些要常驻，哪些只在请求期间存在。

### 17.1 数值规则与记录开销分别设置

评估模式让Dropout按预测时的规则工作。inference_mode则关闭本次不需要的求导记录。
二者解决不同问题；四种组合实验已经给出了证据。

### 17.2 文件要能装回正确的对象

服务加载时，需要对应的模型配置和状态名称。改成员名或层的尺寸，旧文件就可能无法直接装回。
本课用strict mismatch（严格装载时发现不匹配）的失败实验观察这个问题，不实现通用版本迁移。

### 17.3 后续服务会把启动步骤接起来

```text
artifact bytes
-> checksum/version validation
-> CPU deserialize
-> construct compatible Module
-> strict state load
-> device/dtype placement
-> eval
-> warmup（正式接请求前的预热运行）
-> ready
```

T10只验证构造、状态装载、执行模式和输出比较。后续才安排并发、batching与服务生命周期；Mini Redis主线不接入这个模型。
