# Part 1：Round1，让模型与状态有名字

## 0. 从一个部署问题出发

**今天把模型的计算和参数装进一个对象，保存它，再让一个全新对象加载后算出同样的结果。** 这份程序叫`module_inference.py`，本课验证“模型能被重新使用”，不再训练一遍T8分类器。

**T10不新增神经网络理论。** 今天沿用你在T8已经会的多分类线性模型，只学习怎样把计算和状态组织、保存与恢复。

T9里，你已经用`describe()`读出三个Tensor的信息，用`view(-1)`观察预期失败，再用NumPy修改看见共享与复制的区别。你现在能区分：**拿到另一个对象，不一定拿到独立数据。** 这些实验不重做。

今天把问题向前推一步：几个Tensor共同组成一个模型，怎样把它们作为一份有名字的状态管理？

T8的`train()`返回W、b，`predict()`再使用选中的参数。另一个进程要接着预测时，首先得保存这组数，还得知道各自的名字、shape，以及怎样接回计算。

先沿用你已经会的计算。暂时不用`nn.Module`，它就是一个普通函数：

```python
import torch

def forward(inputs, weights, bias):
    return inputs @ weights + bias
```

输入每行是一条数据，返回每行是这条数据的各类别分数。**今天换的是W、b的管理方式，计算目标仍是同一个线性分类器。**

现在希望把选定的参数交给另一个进程预测，就要回答：

```text
weights、bias怎样与这套计算放在一起，供下一次调用继续使用？
每个Tensor在checkpoint（保存模型状态的文件）中叫什么名字？
加载时怎样知道哪份数值是weight、哪份是bias？
把 model 移到另一个 device 时，哪些 Tensors 要一起移动？
```

只有W、b时当然可以手工维护。不过保存、恢复和转换设备都需要找到同一组状态。我们希望把名字与所属关系交给模型对象管理，调用者只需把输入交给它。

因此我们需要一个对象同时保存两类信息：

```text
计算结构：forward 应按什么顺序执行
持久状态：哪些 Tensors 属于这个结构、叫什么、怎样保存和移动
```

PyTorch把这个对象叫`nn.Module`（可组合的模型单元）。State（状态）在这里首先指W、b这些需要跨多次调用保留的数。把名字和Tensor登记到模型，才能统一找到、保存和移动它们；写进磁盘文件则是后面的保存步骤。

先不用记新的结构名。今天始终拿着同一个分类器，依次解决三件事：**找全它需要的数值；确定预测时怎样调用；把数值交给一个新对象，检查结果是否一致。** 每个API都在这条过程真正需要它时出现。

今天造一个小 Module，然后完整走一遍：

```text
构造模型
-> 查看已登记的参数与其他状态
-> 输入算出分数
-> 观察训练/评估行为
-> 取出按名字组织的状态并存盘
-> 构造全新对象并加载
-> 同一输入的输出对照
```

分三轮完成同一份`module_inference.py`：

| 读到哪里 | 本轮得到的能力 | 何时暂停 |
|---|---|---|
| R1，§0～§6 | 创建模型，运行forward，分清哪些Tensor属于模型状态 | 对象、名字和共享关系能解释后，先检阅 |
| R2，§7～§9 | 用四种组合区分模型行为与求导记录 | 两个开关各自控制什么已经验证后，暂停核对 |
| R3，§10～§18 | 保存状态、重建对象、恢复后比较输出，再对照Module.to | 完成同一程序的最终收口 |

**这是三个能力闭环，不是三份程序。** 先走通当前一层，再加入下一层需要的角色；不会为了分轮隐藏必要语法，也不要求你独立发明PyTorch的登记机制。

## 1. 最小 Module 先长什么样

> 所以你可以把 **Linear layer（线性层）** 第一理解记成：
>
> **输入一组数字，乘一组权重，再加 bias，得到另一组数字。**
>
> “以前你手写 `X @ W + b`，现在 PyTorch 给你一个对象 `nn.Linear`，这个对象自己持有 W 和 b，并且调用它就执行这次计算。”

先把新的计算接口接回T8。`nn.Linear(D,C)`创建一个持有权重和偏置的线性层对象。

给它一行D个特征，会返回C个分数。数学仍是你会的线性映射，但它把权重存成`[C,D]`，计算时转置：

$$
Z=X A^T+b,
\qquad X:[B,D],\quad A:[C,D],\quad Z:[B,C].
$$

T8的`weights[D,C]`与这里的`linear.weight[C,D]`排列不同，数学作用相同。

```python
import torch
from torch import nn

layer = nn.Linear(2, 3)
inputs = torch.tensor([[1.0, 2.0]], dtype=torch.float32)
print(tuple(layer.weight.shape), tuple(layer(inputs).shape))
# (3, 2) (1, 3)
```

接下来的示例使用4个输入特征、3个类别分数。3只是固定样例，类本身仍接收`class_count`，并不限制为三分类。

```text
4个输入特征 -> 一次线性计算 -> 3个类别分数
```

先只造能计算的最小模型。本课重点在运行和解释状态，不要求先独立设计一套模型。

Python的`self`是当前对象。`super().__init__()`先把父类`nn.Module`管理子对象和参数所需的内部记录准备好，下面才能往模型里放`linear`。
`self.linear`是当前模型持有的线性层对象，内部的weight和bias跨调用保留。

```python
import torch
from torch import nn


class TinyClassifier(nn.Module):
    def __init__(self, input_dim: int, class_count: int) -> None:
        super().__init__()
        self.linear = nn.Linear(input_dim, class_count)

    def forward(self, inputs: torch.Tensor) -> torch.Tensor:
        return self.linear(inputs)
```

现在就创建它，并给一份固定输入。后面的片段都接着使用这两个对象，最后再合到§14的同一个脚本中。

```python
torch.manual_seed(2026)
input_dim, class_count = 4, 3
model = TinyClassifier(input_dim, class_count)
inputs = torch.tensor(
    [
        [1.0, 2.0, 3.0, 4.0],
        [-1.0, 0.5, 2.0, -0.5],
    ],
    dtype=torch.float32,
)
outputs = model(inputs)
assert tuple(outputs.shape) == (2, 3)
```

`model`是持有计算结构与状态的对象。`outputs`是本次调用返回的分数Tensor。
一次调用不会训练这些参数；参数更新仍需要后续训练流程，本课不做训练。
这里的参数由`nn.Linear`初始化，尚未学会任何任务。检查只要求形状和状态关系正确，不要求随机初始化的分数给出正确类别。

Forward shape：

```text
inputs [B,input_dim]
-> linear [B,class_count]
```

此时你手里已经有三种具体对象：`model`是整个分类器，`model.linear`是它里面负责乘加的对象，`outputs`是这一次算出的分数。下一次调用仍用原来的weight和bias，但会产生新的结果Tensor。

**正常入口写`model(inputs)`，它会进入你定义的`forward`。** `forward`里的`self.linear(inputs)`再完成乘加。先沿这条调用使用即可，调用前后的观察机制放在文末选读，不在状态主线中展开。
§4和§7会继续修改**同一个类**，当场说明新增角色的用途。每次改类后从头重新运行脚本，让`model = TinyClassifier(...)`创建新版对象，不保留多个同名类，也不靠交互环境给旧实例补状态。

## 2. 保存之前，先问：模型究竟要管理哪些东西？

现在你可以沿对象访问它的数值：`model.linear.weight`得到权重Tensor，`model.linear.bias`得到偏置Tensor。将来保存时，当然可以手工把这两个名字写出来。

但我们希望模型能够自己列出要管理的参数。于是先问：**只要某个东西能用`model.xxx`访问，就都算模型要管理的状态吗？**

在创建`model`后，加一个调试用的普通属性：

```python
model.debug_tensor = torch.zeros(1)
print(model.debug_tensor)
# tensor([0.])
```

它确实属于这个Python对象的属性。可它没有参与分类计算，我们也没要求框架把它当参数保存。**“对象上挂着什么”，与“PyTorch正式管理什么”，需要分开。**

PyTorch为后者保留了专门的记录。就当前模型而言：

| 具体对象 | 谁记录它 | 记录的身份 |
|---|---|---|
| `model.linear` | 外层`model` | 名字为`linear`的子模块 |
| `model.linear.weight` | `linear`对象 | 名字为`weight`的训练参数 |
| `model.linear.bias` | `linear`对象 | 名字为`bias`的训练参数 |
| `model.debug_tensor` | 只有普通Python属性关系 | 没有登记为子模块或参数 |

**把对象按名字记入这类管理记录，就叫registration（注册，这里就是登记身份与名字）。** 这样框架才知道以后要遍历、保存或移动哪些东西，而不是把任意Python属性全部搬走。

你没有为weight和bias手工调用登记函数，因为`nn.Linear`在构造时已经把它们建立为**Parameter（以训练参数身份管理的Tensor）**。你写`self.linear = nn.Linear(...)`时，外层Module也会自动识别这个子模块并登记它。

这些参数仍可以按Tensor做计算。参数身份还表示“这份数值属于可供训练流程更新的模型参数”；当前没有训练，所以数值保持初始化后的状态。参数也可以冻结求导，并非登记成Parameter就会自动发生更新。

**接下来不靠记定义，我们直接让模型把这两份名单打印出来。**

## 3. 两次打印，分别在回答什么问题？

### 3.1 第一次：整个模型由哪些模型单元组成？

`named_modules()`给出“名字、模块对象”这一对信息，包含模型自身以及向下找到的子模块。给名字加`repr()`是为了让空字符串也清楚显示：

```python
for name, module in model.named_modules():
    print(repr(name), type(module).__name__)
```

在当前这个只有一个Linear的模型里，看到的是：

```text
'' TinyClassifier
'linear' Linear
```

第一行是**model自己**。空名字表示“从当前查询起点走零步”，不是一个没命名的成员。第二行对应`model.linear`；它的类型是`Linear`。

这就是你说“有点像打印成员”的来源。更准确地说，**这里列的是模块对象，不是全部成员**：weight和bias是参数Tensor，debug_tensor是普通Tensor属性，都不在这份模块名单里。

### 3.2 第二次：这些模块里面有哪些训练参数？

现在换一个查询：沿刚才的模块关系，找到已登记的参数。`named_parameters()`返回“参数名、参数Tensor”：

```python
for name, parameter in model.named_parameters():
    print(name, tuple(parameter.shape))
```

本例包含两项，后面检查时按名字集合核对，不依赖打印顺序：

```text
linear.weight (3, 4)
linear.bias (3,)
```

`linear.weight`是一条名字路径：**先进入model的linear，再找到linear的weight。** 它正是前面能够直接访问的`model.linear.weight`，不是打印时新复制出的一份权重。

可以直接用对象身份核对这件事：

```python
modules = dict(model.named_modules())
parameters = dict(model.named_parameters())
assert modules[""] is model
assert modules["linear"] is model.linear
assert parameters["linear.weight"] is model.linear.weight
assert parameters["linear.bias"] is model.linear.bias
```

### 3.3 现在再画“谁里面有什么”

```text
model                         模块：TinyClassifier
└── linear                    子模块：Linear
    ├── weight [3,4]          参数Tensor
    └── bias [3]              参数Tensor

model.debug_tensor [1]        普通属性，未进入上述管理名单
```

**本例的包含关系画出来像一棵树，所谓“注册树”指的就是这些已登记对象的层级关系。** Module首先是一个能保存状态、执行计算的对象；“树”是在描述本例中对象怎样组合，不是另一个需要你实现的数据结构。

这张图说明谁包含谁。计算怎样进行，仍看`forward`：本例把输入交给linear做一次乘加。登记一个子模块，并不会自动替你调用它。

现在已经能找全weight和bias。下一步再出现一种真实需要：**预测前还要乘一组固定缩放系数，它也要保留，但不是待训练的权重。放在哪里？**

## 4. 一组固定缩放系数应该放在哪里

模型已经能计算。现在增加一个具体需求：**训练数据确定了一组固定缩放乘数，之后预测也必须用同一组数。** 这与你T7使用训练集预处理统计量是同一类需要；本课不重新估计它们。

比如4个特征使用`[1.0, 0.5, 1.0, 1.0]`，第二项先缩小一半，再进入线性层。

它跨多次预测保留，需要跟模型一起保存、一起移动设备；但它不是这次由梯度下降更新的weight。

我们需要把这份Tensor登记为**属于模型、但不属于训练参数的状态**。PyTorch提供的这种角色叫buffer（注册缓冲状态）。

回到原类的`__init__`，在`self.linear`之后增加：

```python
self.register_buffer(
    "input_scale", # 输入缩放系数
    torch.ones(input_dim, dtype=torch.float32),
)
```

`register_buffer`把这份Tensor按名字登记到当前对象，返回`None`。之后通过`self.input_scale`使用它；默认会进入保存状态，也会跟随模型的设备转换。

然后把原类的`forward`替换为下面这个版本，只增加入口缩放：

```python
def forward(self, inputs: torch.Tensor) -> torch.Tensor:
    scaled = inputs * self.input_scale
    return self.linear(scaled)
```

默认全1先保留原数值规则。创建model后，再设置本次固定的第二项乘数：

```python
model.input_scale[1] = 0.5
outputs = model(inputs)
assert tuple(outputs.shape) == (2, 3)
```

重新运行时，这个模型先缩放输入，再计算分数。后面保存和恢复时，`0.5`也必须保住；只恢复weight和bias会漏掉这份预处理状态。

现在各角色有了具体区别：

- **parameter**：如linear.weight，以**训练参数**身份登记，默认允许求梯度。
- **buffer**：如input_scale，是模型需要**长期保留的固定数值**，本课不让优化器更新它。
- **本次计算的临时Tensor**：如scaled，由当前输入产生，不作为模型状态登记或保存。

参数也可以通过`requires_grad=False`冻结求导；选择buffer是为了表达这里的职责，不是说框架禁止冻结参数。T14会再看到其他固定状态的用途。

## 5. 缩放系数加进来后，再检查一次归属

修改类并重新运行脚本后，仍执行§2的`model.debug_tensor = torch.zeros(1)`。现在模型中同时有weight、bias、input_scale和debug_tensor，可以把两种登记名单摆在一起看：

```python
print("parameters:", sorted(dict(model.named_parameters())))
print("buffers:", sorted(dict(model.named_buffers())))
print("debug attribute:", model.debug_tensor)
```

预期输出：

```text
parameters: ['linear.bias', 'linear.weight']
buffers: ['input_scale']
debug attribute: tensor([0.])
```

`named_buffers()`和刚才的参数查询用法相同，只是现在询问登记的buffer。`input_scale`直接属于外层model，所以名字前面没有`linear.`。

你可以把当前计算中的四类东西放回各自的位置：

| 本例对象 | 它为什么存在 | 当前放在哪里 |
|---|---|---|
| weight、bias | 决定线性分类器的分数 | Linear里登记的参数 |
| input_scale | 每次预测都复用相同预处理乘数 | model里登记的buffer |
| debug_tensor | 仅供调试对照 | model的普通属性 |
| scaled | 这批输入乘过缩放系数后的中间结果 | forward中的局部变量 |

**input_scale和scaled尤其要分开。** 前者是反复使用的规则，后者是某一批输入应用这个规则后产生的数据。保存模型时需要带走前者，下一次预测再重新算出后者。

到这里，模型已经知道哪些是参数、哪些是buffer。接下来才需要新的动作：**把要保存的这些数值，按名字一次取出来。**

## 6. 把要保存的数值收成一份清单

`state_dict()`返回一份“名字 -> Tensor”的映射。对于当前模型，里面是weight、bias和默认需要保存的input_scale。它把分散在model和linear里的数值收集到一个可按名字访问的对象里：

```python
state = model.state_dict()
for name, tensor in state.items():
    print(name, tuple(tensor.shape), tensor.dtype)
```

本例有下面三项，顺序不是通过条件：

```text
input_scale (4,) torch.float32
linear.weight (3, 4) torch.float32
linear.bias (3,) torch.float32
```

这些名字刚才都出现过。`state["input_scale"]`可以取得缩放系数；debug_tensor和scaled没有进入这份保存清单。

现在“模型”和“模型状态”也分开了：model知道怎样执行forward；state只给出这些有名字的数值。**拿到state后，还没有创建第二个分类器，也没有写磁盘文件。**

### 6.1 清单拿到了，里面的数值独立了吗？

这正好接回T9：另一个对象可以继续共享同一份存储。`state_dict()`默认也如此。我们用不参与求导的input_scale观察，不需要先学训练或反向传播：

```python
import copy

state = model.state_dict()
snapshot = copy.deepcopy(state)
model.input_scale[1] = 0.25

print(float(state["input_scale"][1]))
print(float(snapshot["input_scale"][1]))
# 0.25
# 0.5

model.input_scale[1] = 0.5
```

改model以后，state跟着读到0.25；深拷贝得到的snapshot仍保留0.5。最后一行恢复本课原先的乘数，让后续实验继续使用同一基线。

**state_dict整理了名字，却没有自动复制底层数值。** 因此要在内存里保住某个时刻的模型状态，用深拷贝留下独立快照。将来训练时保存“目前最好的那组参数”，也是同一个问题。[官方状态映射说明](https://docs.pytorch.org/docs/2.14/generated/torch.nn.Module.html#torch.nn.Module.state_dict)

R1到这里完成了“找全并取出模型状态”。下一轮先确定比较输出时该采用什么运行方式；最后才把这份清单写盘、加载到新对象。

```bash

```

3. 能解释为什么缩放乘数属于模型状态，以及为什么state_dict映射不自动成为独立快照。

# Part 2：Round2，分开模型行为与求导记录

## 7. 要比较两次预测，先固定模型采用的计算方式

R1已经找全了要保存的数。后面准备做一次比较：原模型算出分数，保存后，新模型再算同一输入，两份结果应该对得上。

**比较之前，除了数值相同，还要让两次计算采用相同规则。** 你的当前Linear始终做同一套乘加，模式切换不会改变输出；所以仅拿它观察`train()`和`eval()`，会看不出开关的作用。

这一轮为观察开关，在同一个模型里临时加入一个会随模式改变行为的操作。它不是线性分类器运行的必要条件，也不代表你现在要学习新的神经网络模型。

**Dropout（随机丢弃）** 在训练模式临时把部分输入元素置零，保留值按保留概率缩放；评估模式直接保留输入。本课只用它观察train/eval，不要求先理解神经网络正则化；为什么训练中会用这种随机丢弃，留T13。

继续修改原类：在`__init__`中增加这一行，不改变已有参数和buffer：

```python
self.dropout = nn.Dropout(p=0.25)
```

把`forward`更新为下面这个版本，在缩放输入与Linear之间加入它：

```python
def forward(self, inputs: torch.Tensor) -> torch.Tensor:
    scaled = inputs * self.input_scale
    dropped = self.dropout(scaled)
    return self.linear(dropped)
```

重新运行脚本，创建带Dropout的新model。R1已经明确的参数名、buffer和state keys保持不变；只是多了一个没有参数的子模块。

新建Module默认处于**training mode（训练模式）**。`model.training`这个布尔值记录当前模式，初始为True：

```python
model.training is True
```

```python
model.eval()
```

这次调用把model及其子模块切到**evaluation mode（评估模式）**，对应的training标志变成False。本例的Dropout读取这个标志，决定丢弃还是保留输入；Linear仍使用相同乘加规则。`model.train()`则把它们切回训练模式。

**这两个调用只是切换行为，自己不会执行训练、更新权重或产生预测结果。** 真正算出分数的仍是随后那次`model(inputs)`。

```text
inputs -> input_scale -> Dropout -> Linear -> logits
```

现在仍只有一个线性分类器，没有增加多层模型的前置知识。

先用一个完全确定的小例子看模式确实改变计算。这里刻意取`p=1.0`：训练时全部丢弃，eval时全部保留，因而不用赌两次随机mask恰好不同。

```python
probe = nn.Dropout(p=1.0)
ones = torch.ones(4)
probe.train()
torch.testing.assert_close(probe(ones), torch.zeros(4), rtol=0.0, atol=0.0)
probe.eval()
torch.testing.assert_close(probe(ones), ones, rtol=0.0, atol=0.0)
```

然后回到示例模型的`p=0.25`，观察真实随机行为：

```python
model.train()
train_a = model(inputs)
train_b = model(inputs)

model.eval()
eval_a = model(inputs)
eval_b = model(inputs)
```

在固定 state/input 下：

```text
train_a 与 train_b 可能不同
eval_a 与 eval_b 应相同
```

训练模式两次随机选择可能恰好相同，因此不要求train_a和train_b必定不同。刚才p=1的小例子已经确定地证明了模式切换的作用。

到这里，原模型和新模型比较输出时，都应该先调用eval，避免本例Dropout继续随机改变输入。但预测时还有一类可以省掉的工作：为后面的求梯度保留计算记录。

## 8. 这次只要预测结果，还需要留下求导记录吗？

T8的训练由你自己算gradient。PyTorch还可以记住forward的计算来路，以便后来自动求梯度，这套能力叫autograd（自动求导）。T11再展开。

这些记录是为了回答“输出怎样依赖参数，梯度怎样算回来”。**只想返回分类分数时，这次用不到它们。** 可以在调用外面加一个明确的范围：

```python
with torch.inference_mode():
    outputs = model(inputs)
```

`inference_mode()`提供的是`with`中的执行环境；真正产生outputs的仍是`model(inputs)`。
在这个环境中，本次计算不记录反向求导所需的操作，并减少相关跟踪开销。

用`outputs.requires_grad`观察这次输出是否需要梯度。在默认求导开启、模型参数允许求导的条件下，普通执行的输出为True；放进上面的范围后，这次输出为False。T11才需要继续研究这些记录具体怎样形成。

刚才的eval处理的是Dropout用什么规则，**并不会替你关闭求导记录**。因此本课真正用于预测比较的完整调用是：

```python
model.eval()
with torch.inference_mode():
    outputs = model(inputs)
```

现在就能把两行逐句读出来：先把模型切成评估行为，再在不记录求导过程的环境里计算。下一节用四种组合验证它们确实各管一件事。

## 9. 只换一个开关时，另一个会不会跟着变？

现在两个开关都已经有用途：一个改Dropout的数值规则，一个决定本次计算是否记录求导关系。对同一model/input，各运行下面四种设置，参数不更新：

```text
train + grad enabled
train + inference_mode
eval  + grad enabled
eval  + inference_mode
```

记录：

```text
model.training
output.requires_grad
相同 input 重复两次是否 exact equal
```

例如，只调用eval后输出仍然requires_grad=True，就说明“评估行为”没有自动关掉求导记录；反过来，只进入inference_mode，model.training仍可保持True。

本例的预期读法是：

| 调用设置 | `model.training` | output的`requires_grad` |
|---|---|---|
| `model.train()`，普通执行 | True | True，因为模型参数需要梯度 |
| `model.train()`，放进`inference_mode()` | True | False |
| `model.eval()`，普通执行 | False | True |
| `model.eval()`，放进`inference_mode()` | False | False |

先调用`train()`或`eval()`设置模型行为，再选是否进入`with torch.inference_mode():`执行forward。`with`中的设置只管其缩进范围；退出后，外面的求导模式恢复，model的train/eval状态则保留，直到你再次切换。

### Round2 停止点：两个开关分别有证据

保留同一model/input，完成上面的四种组合。用`model.training`与`output.requires_grad`说明每个开关的作用，再保留p=1的独立Dropout对照。

**先停在这里核对R2，再继续保存/恢复。** 不用训练模型，也不要求两次随机输出一定不同；已有R1状态检查继续保留，不重新做一份。

# Part 3：Round3，保存状态再重建模型

## 10. 先留下参考输出，再把这组数值写进文件

R1已经收集好数值，R2已经明确预测方式。现在开始整课最后一条连续操作：**原模型计算一次 -> 保存 -> 新建模型 -> 加载 -> 再算一次并比较。**

先在原模型上计算参考输出。继续用原来的inputs和input_scale第二项为0.5的模型：

```python
model.eval()
with torch.inference_mode():
    expected = model(inputs).clone()
```

`expected`保留这次预测结果，后面用它检查加载是否正确。然后保存当前状态；这两个动作之间不修改模型参数或input_scale：

```python
checkpoint_path = "tiny_classifier.pt"
torch.save(model.state_dict(), checkpoint_path)
```

文件记录这次传入的参数和持久buffer数值。`torch.save`完成写盘，返回`None`；原model仍可继续使用。

这次传给save的就是R1打印过的三项：linear.weight、linear.bias和input_scale。Dropout没有参数或buffer，不会因为加入模型就多出一份数值状态。

文件中也没有TinyClassifier的类定义、forward代码、这批inputs或expected。**保存数值，和保存“怎样拿这些数值计算”的程序，是两件事。** 所以下一步需要你先按同一类定义和尺寸创建一个新对象，再把文件里的数值装进去。

## 11. 新对象先有对应的位置，文件里的数值才有地方装

继续使用带input_scale和Dropout的同一个TinyClassifier类。构造一个全新对象后，它最初有自己的随机权重和默认全1的input_scale；接下来用文件中的值覆盖这些状态。

```python
loaded_model = TinyClassifier(
    input_dim=input_dim,
    class_count=class_count,
)

state = torch.load(
    checkpoint_path,
    map_location="cpu",
    weights_only=True,
)
loaded_model.load_state_dict(state, strict=True)
loaded_model.eval()
```

这段代码按顺序只做三类动作：

1. 构造loaded_model，先建立linear、weight、bias和input_scale这些位置。
2. torch.load读回“名字 -> Tensor”的映射，先把数据放在主机内存一侧；本课始终使用CPU。
3. load_state_dict按名字把数值装入现有对象，然后eval切换预测行为。

具体看一项：文件里的`linear.weight`应装入`loaded_model.linear.weight`，尺寸都是`[3,4]`。`input_scale`应装入外层的同名buffer，第二项由新对象初始的1.0恢复为保存的0.5。

**strict=True要求该有的名字不能缺，也不能多出意外名字；对应Tensor的尺寸还必须匹配。** 这让你能及时发现“文件和所建对象不是同一种结构”，而不是继续带着漏装状态预测。

`torch.load`返回状态映射；`load_state_dict`返回装载诊断，模型仍是你刚才构造的loaded_model。最后的eval仍需明确调用，因为本课state_dict没有保存training这个模式标志。

## 12. 同一份输入交给新对象，能否得到相同结果？

此时expected来自保存前的原模型，loaded_model已经装入文件中的数值。给新对象同一份inputs，仍用相同预测方式计算：

```python
loaded_model.eval()
with torch.inference_mode():
    actual = loaded_model(inputs)

torch.testing.assert_close(actual, expected, rtol=1e-5, atol=1e-6)
```

这一对照检查的是**本例保存前后的计算结果是否一致**。再看状态本身，确认每个保存值都确实装回，而不是仅凭一次输出碰巧相同：

```python
restored = loaded_model.state_dict()
assert set(restored) == set(state)
for name in state:
    torch.testing.assert_close(restored[name], state[name], rtol=0.0, atol=0.0)
assert float(loaded_model.input_scale[1]) == 0.5
```

到这里，**原模型 -> 文件 -> 全新模型 -> 同一输入的输出**已经完整走通。它证明当前类定义、尺寸配置、数值状态和预测方式能够配合恢复；不推广成换任意硬件或框架版本也逐位相同。

### 12.1 成功以后，再故意创建一个不匹配的对象

保存时有3个类别，weight是`[3,4]`。如果构造一个4类对象，它需要的weight就是`[4,4]`，bias也由`[3]`变成`[4]`。**名字虽然相同，数值却放不进相同尺寸的位置。**

最后做一次这个边界检查：另建`TinyClassifier(input_dim, class_count + 1)`，用同一份state调用load_state_dict，预期得到RuntimeError。只在这个故意不匹配的调用周围捕获异常；若没有抛错，就让检查失败。

这就是名字与尺寸要配套的实际含义。有时会把这样的结构约定叫schema（状态结构约定）；先记住“文件里的每项数值必须能装进新对象对应的位置”即可。

## 13. `Module.to` 与 `Tensor.to` 的重要差别

保存恢复的主过程已经完成。现在回看R1的登记名单，还有一个已经计划好的用途：**如果要把整份模型的浮点状态改成float64，能否让weight、bias和input_scale一起变？**

能，但调用对象与T9不同。T9对单个Tensor转换时要接住返回值；这里把转换请求交给整个Module，让它沿已登记的关系处理状态。用一个独立模型观察，不影响刚才成功恢复的基线。

先沿用你已总结的Tensor规则：接住返回值，原对象不一定改变。

```python
converted = inputs.to(dtype=torch.float64)
```

本例converted是float64，原inputs仍为float32。目标类型和设备本就相同时，也可以返回原对象。

现在换成Module。另建一个专用模型观察，保留刚才保存恢复实验的float32基线：

```python
probe_model = TinyClassifier(4, 3)
probe_model.debug_tensor = torch.zeros(1)
returned_model = probe_model.to(dtype=torch.float64)
assert returned_model is probe_model
assert probe_model.linear.weight.dtype == torch.float64
assert probe_model.input_scale.dtype == torch.float64
assert probe_model.debug_tensor.dtype == torch.float32
```

**Module.to原地转换已注册的参数与buffer，返回模型自身。** 你没有得到第二个独立模型。

普通debug_tensor没有登记为参数或buffer，因此没有跟着转换。这正是重要状态需要正确注册的原因。

这组区别只用CPU和dtype就能观察，不需要GPU。原model与inputs继续保持float32。

## 14. `module_inference.py` 的完整顺序

保留已经完成的R1对象/状态检查和R2四种组合。现在使用加入input_scale与Dropout后的**同一个TinyClassifier类**，继续同一固定输入，不新建一套训练程序。

固定输入已经在§1创建：CPU、float32、shape为(2,4)，两行各代表一条输入。继续使用它。


| 你刚完成的动作 | 用什么结果判断 |
|---|---|

## 16. Save/Load 的安全边界

序列化就是把状态编码进文件，反序列化是从文件恢复对象或数据。本课只加载自己保存的文件，并显式使用`weights_only=True`限制加载方式；它缩小风险，不等于任意来源的文件都安全。不要为本课下载陌生模型或执行任意pickle对象。

后续部署还需管理模型版本、配置、输入约定和文件校验等信息。这是未来的artifact管理范围，不要求本课另写管理系统，也不把它们全部塞进state_dict。

## 17. 把刚才的程序放到推理服务里，会用在什么位置？

想象以后服务启动时，先按§11构造模型并加载文件，再设置好预测方式。**模型准备一次，随后反复处理不同输入。**

第一批请求来到时，用既有weight、bias和input_scale算出分数；第二批请求来到时，仍用这些状态，重新计算自己的scaled和输出。这就是模型的长期状态与单次请求数据的区别。

如果加载时发现尺寸不匹配，应该在开始接请求前暴露问题。若加载成功，再根据目标设备和dtype转换已登记状态，之后用eval与inference_mode执行预测。这些动作都是今天已经走过的过程，不需要另记一串部署名词。

实际服务以后还会加入文件版本校验，以及 **warmup（预热，即正式接请求前先做少量运行）** 等启动步骤；它们不是今天的编程任务。并发和批处理也留后续，当前Mini Redis不接入模型。

# 附录A：主过程走通后，按需回看的两个细节

### 正常调用为什么写model(inputs)？

`model(inputs)`先经过Module的调用入口，再执行forward。调用入口还支持**hook（钩子，在调用前后运行的观察函数）**。直接调用model.forward(inputs)会绕过这层入口；T14需要观察中间结果时再具体使用hook。这里知道正常入口怎么写即可。

### 登记的buffer能不能不写进文件？

本课input_scale必须保存，所以使用默认设置。另一些buffer只需跟随设备移动，不必保存数值，可以在构造函数中用`self.register_buffer("temporary", value, persistent=False)`，其中value是已有Tensor。

**persistent（持久保存标志）在这里决定buffer是否进入state_dict。** 它不会把buffer变成parameter；这个选项不加入当前固定模型。
