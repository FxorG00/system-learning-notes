# Part 1：服务加载的究竟是什么

## 0. 从一个部署问题出发

**今天把模型的计算和参数装进一个对象，保存它，再让一个全新对象加载后算出同样的结果。** 这份程序叫`module_inference.py`，本课验证“模型能被重新使用”，不再训练一遍T8分类器。

你在T8已经真正做过：`train()`返回W、b，验证集选择其中一组，`predict()`拿选中的参数处理新输入。现在设想另一个进程要用这组参数：参数不能只留在原函数的局部变量里，它需要知道参数叫什么、各是什么shape、怎样接回计算。

本课再加一层计算，让这种管理需求更明显。**先看为什么要管理状态，再看PyTorch怎样替你登记它们。**

先想象不用 `nn.Module`。一个两层 network 完全可以写成普通 function：

```python
import torch

def forward(inputs, w1, b1, w2, b2):
    hidden = torch.relu(inputs @ w1 + b1)
    return hidden @ w2 + b2
```

数学计算没有问题。可训练结束以后，我们准备把它交给另一个 process 做 inference，立刻要回答：

```text
w1、b1、w2、b2 中哪些是必须保存的 state？
每个Tensor在checkpoint（保存模型状态的文件）中叫什么名字？
加载时怎样知道它应回到哪一层？
把 model 移到另一个 device 时，哪些 Tensors 要一起移动？
```

只有四个 Tensors 时可以手工维护。真实 model 有成百上千个 layers 和 state，继续靠调用者传递一张无名 Tensor 清单，很快就会失控。

因此我们需要一个对象同时保存两类信息：

```text
计算结构：forward 应按什么顺序执行
持久状态：哪些 Tensors 属于这个结构、叫什么、怎样保存和移动
```

PyTorch把这个对象叫`nn.Module`（可组合的模型单元）。State（状态）在这里首先指W、b这些需要跨多次调用保留的数。把名字和Tensor登记到模型，才能统一找到、保存和移动它们；写进磁盘文件则是后面的保存步骤。

训练结束后，我们想在另一个 process 中继续得到相同 output。此时程序具体需要知道：

```text
model 由哪些 submodules 组成
哪些 Tensors 是 trainable parameters
哪些 Tensors 是持久 state，但不参与梯度
forward 怎样执行
哪些 state 要写入 checkpoint
inference 时哪些开关必须切换
```

`nn.Module` 把这些责任组织成一棵有名字的 object tree。今天不是背完它的 API，而是亲手走通这棵树怎样变成一个可保存、可重新构造的 inference object。

今天造一个小 Module，然后完整走一遍：

```text
构造模型
-> 查看已登记的参数与其他状态
-> 输入算出分数
-> 观察训练/评估行为
-> 取出按名字组织的状态并存盘
-> 构造全新对象并加载
-> 同一输入的输出对照
```

## 1. 最小 Module 先长什么样

先把唯一的新计算接口接回T8。`nn.Linear(D,C)`把一行D个特征变成C个分数，数学仍是你写过的线性映射，但它把权重存成`[C,D]`，计算时转置：

$$
Z=X A^T+b,
\qquad X:[B,D],\quad A:[C,D],\quad Z:[B,C].
$$

所以T8的`weights[D,C]`与这里的`linear.weight[C,D]`排列不同，数学作用相同。不要因shape相反误以为换了一种分类公式。

```python
import torch
from torch import nn

layer = nn.Linear(2, 3)
inputs = torch.tensor([[1.0, 2.0]], dtype=torch.float32)
print(tuple(layer.weight.shape), tuple(layer(inputs).shape))
# (3, 2) (1, 3)
```

接下来的示例对象使用`input_dim=4, hidden_dim=6, class_count=3`。中间6个数是hidden representation（隐藏表示），这层产生的中间Tensor也叫activation（激活值）。ReLU把负数置零、保留非负数；为什么这一步增加模型表达能力，T12再专门推导。

Dropout（随机丢弃）在训练模式临时把部分中间元素置零，并把保留值除以保留概率；评估模式保持输入。此刻只借它看见模式开关的效果，正则化理由和期望公式留T13。

```text
4个输入特征 -> 6个中间值 -> ReLU -> Dropout -> 3个类别分数
```

下面给出完整小类，是因为本课没有独立设计闸门，重点在运行、观察和解释状态。Python中的`self`是当前对象；`super().__init__()`先初始化父类的登记机制；`self.linear1`等成员在对象创建后会一直保留，局部变量`hidden`则每次调用重新产生。

```python
import torch
from torch import nn


class TinyClassifier(nn.Module):
    def __init__(self, input_dim: int, hidden_dim: int, class_count: int) -> None:
        super().__init__()
        self.linear1 = nn.Linear(input_dim, hidden_dim)
        self.activation = nn.ReLU()
        self.dropout = nn.Dropout(p=0.25)
        self.linear2 = nn.Linear(hidden_dim, class_count)

        self.register_buffer(
            "input_scale",
            torch.ones(input_dim, dtype=torch.float32),
        )

        self.debug_tensor = torch.zeros(1)

    def forward(self, inputs: torch.Tensor) -> torch.Tensor:
        scaled = inputs * self.input_scale
        hidden = self.activation(self.linear1(scaled))
        hidden = self.dropout(hidden)
        return self.linear2(hidden)
```

Forward shape：

```text
inputs [B,input_dim]
-> linear1 [B,hidden_dim]
-> ReLU [B,hidden_dim]
-> Dropout [B,hidden_dim]
-> linear2 [B,class_count]
```

先看到 concrete object，再命名：

- 整个 `TinyClassifier` 是 module（可组合模型单元）；
- `linear1` 等是 submodules（子模块）；
- `weight/bias` 是 parameters（由训练更新的注册 Tensor）；
- `input_scale` 是 buffer（随模型保存/移动、但不是 parameter 的 state）；
- forward 中的 `hidden` 是 activation（本次执行产生的中间值）。

`debug_tensor` 只是普通 Tensor attribute。它不会因为“挂在 Module 上”就自动获得 parameter/buffer 的全部行为。

## 2. Module 是一棵注册树

执行：

```python
self.linear1 = nn.Linear(...)
```

不是普通 assignment 那么简单。`nn.Module.__setattr__` 会识别被赋值的 Module/Parameter，并把它注册进当前 object。

因此：

```python
for name, module in model.named_modules():
    print(name, type(module).__name__)

for name, parameter in model.named_parameters():
    print(name, tuple(parameter.shape))
```

能递归看到稳定 names：

```text
linear1.weight
linear1.bias
linear2.weight
linear2.bias
```

这些名字也成为`state_dict`的schema（状态结构约定）的一部分。重命名成员可能让旧checkpoint找不到对应参数；它不只是代码外观变化。

## 3. 为什么调用 `model(inputs)`，而不是直接 `forward`

`forward`描述模型怎样计算。写`model(inputs)`时，PyTorch会经过Module的调用入口，再执行`forward`；这个入口也处理注册的hooks（钩子，在调用前后执行的观察函数等）。直接调`forward`会绕过这些外层调用机制。T14会用hook观察中间shape。

`__call__`不会自动替你切成eval，也不会自动关闭求导记录；这两项仍由§7~9的显式设置决定。

正常写法：

```python
outputs = model(inputs)
```

不要在业务代码中直接调用：

```python
outputs = model.forward(inputs)
```

后者可能绕过 framework 在 `__call__` 周围提供的机制。

## 4. 四类对象不要混在一起

### Module object

Python 侧的结构、submodules、names、mode 与 forward behavior。

### Parameter Tensor

以训练参数身份注册的Tensor，默认允许求梯度。它出现在：

```python
model.parameters()
model.named_parameters()
model.state_dict()
```

把某个parameter的`requires_grad`设为False可以冻结求导，它仍是注册parameter；“是否登记为参数”和“这次是否求它的梯度”是两件事。

### Buffer

登记为非parameter的Tensor，可随模型保存/移动，通常不由optimizer更新。本例是`input_scale`；T14会再看到BatchNorm保存的历史统计量。

### Activation

一次 forward 根据 inputs 与 state 临时产生。它通常不在 `state_dict`，training backward 可能暂时保存它，inference request 结束后即可释放。

Checkpoint（检查点）是持久化 artifact，常以 `state_dict` 为核心。它不是正在运行的 Module object，也不包含任意 Python control flow。

## 5. Parameter、buffer 与普通 Tensor attribute

对上面的 model：

```python
parameter_names = dict(model.named_parameters()).keys()
buffer_names = dict(model.named_buffers()).keys()
state_keys = model.state_dict().keys()
```

应观察：

```text
linear weights/biases -> parameters + state_dict
input_scale           -> buffers + state_dict
debug_tensor          -> neither
```

若 buffer 只想随 device 移动、不想写入 checkpoint：

```python
self.register_buffer("temporary", value, persistent=False)
```

Persistent（持久）只决定是否进入 `state_dict`；它不把 buffer 变成 parameter。

## 6. `state_dict` 是 named Tensor mapping

```python
state = model.state_dict()
for name, tensor in state.items():
    print(name, tensor.shape, tensor.dtype)
```

它保存 registered parameters 与 persistent buffers，key 来自 module tree path。

先想一个具体用途：训练到第100步时把`state`放进变量，随后继续更新模型，第100步的数还能保住吗？**只接住`state_dict()`返回的字典还不够，里面的Tensor默认仍共享模型状态的存储。** 这叫shallow mapping（浅层映射）：外面的容器取出来了，里面的数据没有都复制成独立快照。

这正是你在T4处理过的快照问题。若要在内存中保留那个时刻的值，再深拷贝：

```python
import copy

best_state = copy.deepcopy(model.state_dict())
```

仅写：

```python
best_state = model.state_dict()
```

不能可靠表达“以后 parameters 更新也不影响这个 snapshot”。

# Part 2：Mode 与 gradient recording 是两条轴

## 7. `train()` / `eval()` 改变谁的 behavior

Module 默认处于 training mode：

```python
model.training is True
```

```python
model.eval()
```

递归把 mode 切成 evaluation。真正改变 forward behavior 的是读取 `self.training` 的 layers，例如：

```text
Dropout
BatchNorm
自定义依赖 mode 的 Module
```

`Linear` 与 `ReLU` 通常在两种 mode 下行为相同。

先用一个完全确定的小例子看模式确实改变计算。这里刻意取`p=1.0`：训练时全部丢弃，eval时全部保留，因而不用赌两次随机mask恰好不同。

```python
probe = nn.Dropout(p=1.0)
ones = torch.ones(4)
probe.train()
torch.testing.assert_close(probe(ones), torch.zeros(4), rtol=0.0, atol=0.0)
probe.eval()
torch.testing.assert_close(probe(ones), ones, rtol=0.0, atol=0.0)
```

然后回到示例模型的`p=0.25`，观察真实随机行为：

```python
model.train()
train_a = model(inputs)
train_b = model(inputs)

model.eval()
eval_a = model(inputs)
eval_b = model(inputs)
```

在固定 state/input 下：

```text
train_a 与 train_b 可能不同
eval_a 与 eval_b 应相同
```

训练模式的两次输出允许相同，不把“它们一定不相等”写成断言；随机抽样不提供这种保证。模式差异的确定性证据来自刚才的独立probe。

## 8. `inference_mode()` 控制 autograd-related execution

T8的训练需要你自己算gradient。PyTorch可以在forward时记住计算的来路，以便后来自动求梯度，这套能力叫autograd（自动求导）。你准备处理一个纯预测请求时，不需要为这次执行保留这样的记录。

```python
with torch.inference_mode():
    outputs = model(inputs)
```

它让这段执行不记录反向求导所需的操作，并减少相关跟踪开销。T11会具体查看这些记录；现在先用`outputs.requires_grad`观察本次结果是否还要求梯度。`inference_mode()`不会自动调用`model.eval()`。

同样：

```python
model.eval()
```

不会自动关闭 autograd recording。

正常 inference boundary：

```python
model.eval()
with torch.inference_mode():
    outputs = model(inputs)
```

两者分别回答：

```text
eval：Module 应采用哪种行为
inference_mode：本次 execution 是否需要 autograd metadata
```

## 9. 四种组合亲自跑一次

现在两个开关都已经有用途：一个改Dropout的数值规则，一个决定本次计算是否记录求导关系。对同一model/input，各运行下面四种设置，参数不更新：

```text
train + grad enabled
train + inference_mode
eval  + grad enabled
eval  + inference_mode
```

记录：

```text
model.training
output.requires_grad
相同 input 重复两次是否 exact equal
```

它会直接证明 mode 与 gradient recording 不是同一个开关。

本例的预期读法是：

| 调用设置 | `model.training` | output的`requires_grad` |
|---|---|---|
| `model.train()`，普通执行 | True | True，因为模型参数需要梯度 |
| `model.train()`，放进`inference_mode()` | True | False |
| `model.eval()`，普通执行 | False | True |
| `model.eval()`，放进`inference_mode()` | False | False |

先调用`train()`或`eval()`设置模型行为，再选是否进入`with torch.inference_mode():`执行forward。`with`中的设置只管其缩进范围；退出后，外面的求导模式恢复，model的train/eval状态则保留，直到你再次切换。

# Part 3：Checkpoint round trip

## 10. Save：保存 state，不保存本次 activation

```python
checkpoint_path = "tiny_classifier.pt"
torch.save(model.state_dict(), checkpoint_path)
```

文件包含 named parameter/buffer payload。它不保存当前 input、hidden activation、optimizer（除非另行保存），也不自动保存 constructor arguments。

因此 model architecture/config 必须来自：

```text
代码版本
明确 config
artifact metadata
```

## 11. Load：先构造 compatible object

```python
loaded_model = TinyClassifier(
    input_dim=input_dim,
    hidden_dim=hidden_dim,
    class_count=class_count,
)

state = torch.load(
    checkpoint_path,
    map_location="cpu",
    weights_only=True,
)
loaded_model.load_state_dict(state, strict=True)
loaded_model.eval()
```

`map_location="cpu"` 让 artifact 先进入最通用 baseline device；服务再按部署配置显式移动。

`strict=True`要求参数与持久buffer的名字对齐，Tensor的shape也必须兼容。比如保存时输出3个类别，却拿输出4类的新对象加载，最后一层weight/bias尺寸会冲突并抛`RuntimeError`。Schema（结构约定）在这里就是这些名字与尺寸的对应关系。

## 12. Round-trip evidence

在保存前先得到 reference：

```python
model.eval()
with torch.inference_mode():
    expected = model(inputs).clone()
```

加载 fresh object 后：

```python
loaded_model.eval()
with torch.inference_mode():
    actual = loaded_model(inputs)

torch.testing.assert_close(actual, expected, rtol=1e-5, atol=1e-6)
```

这个 evidence 证明：

```text
当前 architecture/config 可重建
state_dict keys compatible
parameter/buffer values 恢复
相同 mode/input 下 output 对齐
```

它不证明 artifact 在另一 PyTorch version、另一 operator backend 或任意 hardware 上 bitwise identical。

## 13. `Module.to` 与 `Tensor.to` 的重要差别

Tensor：

```python
converted = tensor.to(dtype=torch.float64)
```

应接住返回值；转换时通常得到新 Tensor。

Module：

```python
model.to(device="cpu", dtype=torch.float32)
```

会原地转换 registered parameters/buffers，并返回 `self`。普通 `debug_tensor` 不会像 registered state 一样自动跟随。

这正是为什么 serving state 应正确注册，而不是把重要 Tensor 随便挂成普通 attribute。

## 14. `module_inference.py` 的完整顺序

沿用上面同一个`TinyClassifier`与§15固定输入即可。程序只有一个模型类和一个运行入口；展示名字、模式矩阵和恢复比较的辅助函数可以自行拆分，不要求另造框架或照着函数目录填空。

1. 固定 seed，构造 `TinyClassifier`。
2. 打印 module tree、parameter names、buffer names、state keys。
3. 证明普通 Tensor attribute 不在 registered state。

## 15. Input 与 output contract

固定 input：

```python
inputs = torch.tensor(
    [
        [1.0, 2.0, 3.0, 4.0],
        [-1.0, 0.5, 2.0, -0.5],
    ],
    dtype=torch.float32,
)
```

建议 dimensions：

```text
input_dim=4
hidden_dim=6
class_count=3
output shape [2,3]
```

Assertions：

```text
output shape/dtype/device exact
all output finite
state keys exact
round-trip output close
eval repeat deterministic
inference output requires_grad == False
```

不需要 pytest、benchmark 或训练 loop。今天验证的是 object/state/inference boundary。

“output有限”直接检查`torch.isfinite(outputs).all()`：每个输出都应是普通有限数，出现NaN或正负Inf就让检查失败。这里检查的是本次固定输入的计算结果，不让你为模型新增一整套T8式外部输入校验。

## 16. Save/Load 的安全边界

序列化就是把状态编码进文件，反序列化是从文件恢复对象或数据。本课只加载自己保存的文件，并显式使用`weights_only=True`限制加载方式；它缩小风险，不等于任意来源的文件都安全。不要为本课下载陌生模型或执行任意pickle对象。

生产 artifact 还应包含或关联：

```text
model/config version
input schema
dtype policy
class/token mapping
framework/build version
checksum
evaluation evidence
```

这些 metadata 不全都塞进 `state_dict`，但部署系统必须有地方管理。

## 17. 与 AI Infra 的连接

### Replica state ownership

多个 serving replicas 通常各自持有一份 loaded model state。参数 bytes、buffers 与 device placement 决定 baseline memory。

### Inference correctness

忘记 `eval()` 可能让 Dropout/BatchNorm 行为错误；忘记关闭 gradient tracking 会保存无用 metadata、增加 memory/cost。它们是 correctness 与 resource boundary，不只是 style。

### Artifact schema

`state_dict` key names 来自 module tree。Code refactor、module rename 与 shape change都可能造成 schema migration。

### Load pipeline

```text
artifact bytes
-> checksum/version validation
-> CPU deserialize
-> construct compatible Module
-> strict state load
-> device/dtype placement
-> eval
-> warmup（正式接请求前的预热运行）
-> ready
```

T10 的小程序覆盖其中核心 object/state steps。后续 inference project 会加并发、batching 与 lifecycle。

## 20. 压缩记忆

```text
Module 是 registered object tree
parameter 是 trainable registered state
```
