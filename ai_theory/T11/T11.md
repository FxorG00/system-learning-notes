# Part 1：PyTorch 怎样把 T4 的 chain rule 自动执行

## 0. 从一个三行计算开始

**今天让PyTorch替你执行一次已经会手算的求导，再查清它把计算记录和梯度分别留在哪里。** 最终程序仍是`autograd_inspect.py`，复用T4的数值检查思路，不再造一套求导框架。

T8里，你已经亲手写出`gradients()`，训练循环拿它返回的dW/db更新参数。换成更深的模型时，如果每种新运算都要手工连接整条梯度公式，容易漏路径或求和。我们希望只写forward，让框架沿这次实际用过的运算自动应用链式法则。

先用一条能手算的小链，看看这个需求怎样落地：

```python
import torch

x = torch.tensor(3.0)
w = torch.tensor(2.0, requires_grad=True)
b = torch.tensor(-1.0, requires_grad=True)

z = w * x + b
loss = (z - 4.0) ** 2
```

Forward values：

```text
z = 5
loss = 1
```

这三个动作依次是：先乘加得到预测，再减真实值，最后把误差平方。求导目标仍然是固定x和真实值时的loss对w、b的偏导，和T4同一问题。

```text
w -- 乘以固定x --> 中间乘积 -- 加b --> z -- 减真实值 --> 误差 -- 平方 --> loss
```

T4 手推：

$$
\frac{\partial L}{\partial w}=6,
\qquad
\frac{\partial L}{\partial b}=2
$$

现在执行：

```python
loss.backward()
```

PyTorch 会把这两个 gradients 写入 `w.grad` 与 `b.grad`。今天要解释的不是 API 口诀，而是它凭什么做到：

```text
forward 时记录 dependency
-> 每个 operation 提供 backward rule
-> scalar loss 给出 seed gradient 1
-> reverse traversal 累加 path contributions
-> leaf parameters 收到 .grad
```

## 1. Tensor 多出来的 autograd metadata

T9 已经把 Tensor 拆成：

```text
storage + dtype + device + shape + stride + offset
```

现在重新看这一行：

```python
z = w * x + b
```

若 PyTorch 只计算出数值 `5`，forward 结束后就只剩一个孤立结果；将来执行 `loss.backward()` 时，它无法知道 `5` 曾由 `w * x + b` 产生，更不知道应该把 gradient 送回 `w` 和 `b`。

因此当参与 operation 的 Tensor 需要 gradient 时，PyTorch 在算出 output value 的同时，还要留下一条最小的“来路记录”：

```text
这个 output 由哪一种 operation 产生
它依赖哪些前驱 values
反向经过该 operation 时需要哪条 derivative rule
```

这条来路记录会随着 forward 一站一站连接起来。到 `loss` 产生时，PyTorch 已经拥有一张只覆盖本次实际计算路径的 graph。

为了维护这张 graph，Tensor 还会关联一些 autograd metadata（自动求导元数据）：

```text
requires_grad
grad_fn
is_leaf
grad
```

这些名字后面逐个解释。此刻只抓住本质：**Tensor 一边携带 numerical value，一边保留 backward 找回前驱所需的关系。**

## 2. `requires_grad` 决定是否追踪关系

```python
w = torch.tensor(2.0, requires_grad=True)
```

表示后续由 `w` 参与、且处于 grad-enabled mode 的 operations 要被 autograd 记录，以便将来求 loss 对 `w` 的 gradient。

这是“以后需要算loss对w的梯度”的标记。创建时尚未求导，所以第一次backward前：

```python
w.grad is None
```

`.grad`是保存反向计算结果的位置，`None`表示目前没有存放梯度Tensor。一个普通Tensor也能要求梯度，不必先放进`nn.Module`。

## 3. Leaf 与 non-leaf 从哪里来

`w`、`b` 由用户直接创建，且不是某个 differentiable operation 的 result，因此是 leaf Tensors（叶子张量）。

`z` 与 `loss` 是 operations 的 result，因此是 non-leaf（非叶子）：

```python
w.is_leaf     # True
z.is_leaf     # False
loss.is_leaf  # False
```

默认情况下，backward把结果写到需要梯度的leaf的`.grad`。中间节点的梯度会参与计算和传播，但默认不长期保存在自己的`.grad`里。这里先分清“参与求导”和“保存结果的位置”。

若调试确实需要：

```python
z.retain_grad()
```

再 backward，`z.grad` 才会保留。不要为所有 activations 机械调用它；这会增加 memory。

## 4. `grad_fn` 表示怎样回到前驱

```python
print(z.grad_fn)
print(loss.grad_fn)
```

`grad_fn` 指向产生该 non-leaf result 的 backward node。它不是完整 graph 的漂亮可视化，但能说明：

```text
z 不是孤立 value
z 知道自己来自 multiply/add path
loss 知道自己来自 subtract/power path
```

PyTorch eager autograd 的 graph 是执行 forward 时动态建立的。Python control flow 这次走哪条 branch，graph 就记录哪条实际 path。

## 5. Scalar `backward()` 为什么隐含 seed 1

若 loss 是 scalar：

$$
\frac{\partial L}{\partial L}=1
$$

所以：

```python
loss.backward()
```

等价于从 final output 注入 scalar seed `1`，再反向传播。

这与 T4 完全相同。Autograd 自动化的是 chain-rule bookkeeping，不是发明另一套微积分。

## 6. 一次forward产生一批中间对象

`w`、`b`是你准备反复使用的参数对象。`z`、`loss`则来自刚才这次计算；下一次重写乘加和平方，会得到新结果以及新的一批求导记录。

R1会在**不更新参数**的前提下重新forward，再做一次backward。这样两次求的是同一点的相同偏导，可以专门观察结果保存处发生什么变化。复用旧loss是否还能反传，是另一件生命周期问题，放到§10单独实验，不把两种现象混在一起。

# Part 2：Round1，同一点的三路对照与两次新计算

## 7. 程序用途：让三条 gradient path 在同一点对质

文件：`autograd_inspect.py`

今天不是只调用一次 `.backward()`。完整程序让同一个 scalar loss 走三条彼此独立的路径：

```text
fixed x, y, w, b
        |
        +-> manual chain rule --------+
        |                             |
        +-> T4 finite difference -----+-> compare same dL/dw, dL/db
        |                             |
        +-> PyTorch autograd ---------+
```

三者角色不同：

| Path | 当前角色 | 是否依赖 PyTorch backward |
|---|---|---|
| manual derivative | 数学 reference | 否 |
| finite difference | 只重复 forward 的 numerical oracle | 否 |
| autograd | framework 的 chain-rule implementation | 是 |

这里求的是：

$$
\nabla_{w,b}L(w,b;x,y)
$$

也就是 loss 对 $w,b$ 的 gradient；$x,y$ 在这次检查中固定。`loss.backward()` 是被检查的 framework path，finite difference 是独立 oracle，manual result 则帮助定位到底是哪一条路径不一致。

对象地图：

```text
w, b：requires-grad leaf parameters，persistent values
x, y：fixed input / target
z, loss：本次 forward 产生的 temporary non-leaf Tensors
grad_fn / saved state：autograd 为本次 backward 留下的来路记录
w.grad / b.grad：backward 写入并默认累加的 leaf gradients
```

下面的 fixed case 是这张三路图共同使用的输入，不是第四套实验。

R1换一组值，避免照抄§0的手算答案。固定scalar（标量，只有一个数）case如下，使用float64减少数值差分的舍入影响：

```python
x = torch.tensor(-2.0, dtype=torch.float64)
w = torch.tensor(1.5, dtype=torch.float64, requires_grad=True)
b = torch.tensor(0.5, dtype=torch.float64, requires_grad=True)

z = w * x + b
loss = (z - 1.0) ** 2
```

数值检查用的目标函数是同一件事：给它一组候选w、b，返回这组参数下的scalar loss；x=-2、真实值1保持固定。一个普通NumPy/Python数值入口可以写成：

```python
def fixed_loss(parameters):
    w_value, b_value = parameters
    return float((w_value * (-2.0) + b_value - 1.0) ** 2)
```

把`[1.5,0.5]`交给你在T4已经通过的数值梯度检查器，沿原来的实际签名复用即可；无需重写差分循环。解析梯度由你手算，PyTorch结果来自`.backward()`，三者都比较同一点、同一个平方损失，不引入T7的半MSE系数。

运行前手写预测：

```text
w/z/loss 的 is_leaf
w/z/loss 的 requires_grad
w/z/loss 的 grad_fn 是否为 None
第一次 backward 后 w.grad、b.grad
不修改参数、不清理.grad，第二次重新forward/backward后.grad会怎样变化
```

# Part 3：把观察结果解释清楚

## 9. `.grad` 默认累加，不是覆盖

先核对R1：预测值为-2.5，误差为-3.5，loss为12.25。单次梯度是：

$$
\frac{\partial L}{\partial w}=2(-3.5)(-2)=14,
\qquad
\frac{\partial L}{\partial b}=2(-3.5)=-7.
$$

如果参数未改，第二次新的forward计算相同的loss与导数，但`.grad`变成28和-14。**计算的是同一个偏导，保存时却加到了已有值上。** 这叫gradient accumulation（梯度累积）。

Autograd 使用 addition 累积 gradient，原因是同一个 leaf 可能从多个 paths 收到 contributions；mini-batch accumulation 也可能故意跨多次 backward 汇总。

因此普通 training iteration 开头需要清理旧 gradients：

```python
optimizer.zero_grad(set_to_none=True)
```

或手工：

```python
w.grad = None
b.grad = None
```

当前先用`None`清理，再重新forward/backward，检查结果恢复为单次的14和-7。零Tensor也能清空数值，但在optimizer眼里“没有grad”和“grad恰好为零”可能采取不同更新路径；T13会用AdamW做精确对照，现在不额外扩写。

## 10. Gradient lifetime 与 graph lifetime 不同

现在才单独观察旧loss：新建参数，计算一次平方损失，调用backward后，**不要重新forward**，再对同一个loss调用backward。对本课这条平方链，第二次会抛`RuntimeError`，因为第一次默认释放了反传还要使用的已保存中间值。

`loss`这个Python对象和它的`grad_fn`仍可能被引用，并非所有图节点都凭空消失。真正失效的是再次反传所需的部分保存状态。某些不需要这些中间值的简单图甚至允许再次backward，所以错误实验必须固定本课这条链，不写成所有图都必然报错。

第一次 backward 后：

```text
forward graph 的一次性 saved state 通常释放
leaf .grad 仍然存在并继续累加
```

所以：

```text
“旧 loss 不能再 backward”
!=
“w.grad 已经消失”
```

这是两个 lifetime。T11 必须分别观察，不能把报错都归成“graph 没了”。

`retain_graph=True`能延长反传保存状态的使用时间，但这次并不需要它：正常训练每轮本来就要根据新参数重新forward。保留旧图是特定需求的工具，不是处理所有报错的默认动作。

## 11. Non-leaf gradient 计算了，但默认不保存

链式法则必须先算 $\partial L/\partial z$ 才能继续算 $\partial L/\partial w$，所以 `z` 的 gradient 确实存在于 backward computation。

但 backward 后：

```python
z.grad is None
```

通常仍成立，因为 non-leaf `.grad` 默认不 retain。调用：

```python
z.retain_grad()
```

只改变 observation/storage policy，不改变 chain-rule result。

## 12. Vector output 需要显式上游 gradient

若：

```python
x = torch.tensor([1.0, 2.0, 3.0], requires_grad=True)
y = x ** 2
```

`y` 不是 scalar。单写：

```python
y.backward()
```

没有唯一含义：你要对哪个 scalar objective 求 gradient？

先给这次求导一个明确目标。假设我们真正要优化的是这三个输出的加权和：

$$
F=y_0+0.5y_1-y_2.
$$

这是一个scalar，分别对三个输入求导可得`[2,2,-6]`。权重向量`[1,0.5,-1]`告诉反传：“最终目标对各个y分量的导数分别是多少。”它就是这次的upstream gradient（上游梯度）。

PyTorch允许直接把这个向量交给`y.backward`，等价于对上述加权和求导：

```python
v = torch.tensor([1.0, 0.5, -1.0])
y.backward(v)
```

Autograd 计算 vector-Jacobian product（向量-雅可比乘积）：

$$
v^T J
$$

本例：

$$
\frac{\partial y_i}{\partial x_i}=2x_i
$$

所以：

$$
\frac{\partial(v^Ty)}{\partial x}
=
v\odot 2x
$$

这解释了 framework 为什么不为大型 Tensor 显式 materialize 完整 Jacobian。

先能从这个加权和说清调用含义，再记VJP这个缩写。对照两种写法时分别新建输入Tensor，或清理梯度并重新forward，避免把累积误认为数值不同。

## 13. Dynamic graph 动态在哪里

```python
def branch(x: torch.Tensor) -> torch.Tensor:
    if x.item() > 0:
        return x * x
    return -x
```

输入不同，Python branch 不同，本次 forward 建立的 graph 也不同。Dynamic eager graph（动态即时计算图）意味着 graph 跟随实际 execution 建立。

它提供调试和 control-flow 灵活性，也意味着每次 forward 有 graph-construction overhead。Inference serving 常使用 `inference_mode`、compile/capture 或专用 runtime 减少这部分成本。

## 14. `no_grad`、`detach` 与 `inference_mode`

### `torch.no_grad()`

临时关闭 gradient recording：

```python
with torch.no_grad():
    output = model(inputs)
```

### `detach()`

返回与原 Tensor 共享 storage 的 Tensor，但切断当前 autograd history：

```python
detached = tensor.detach()
```

因为仍可能共享 storage，in-place mutation 风险没有自动消失。

### `torch.inference_mode()`

为纯 inference 提供更强的 autograd-related disabling/optimization：

```python
with torch.inference_mode():
    output = model(inputs)
```

它不替代 `model.eval()`；T10 的 mode boundary 仍成立。

## 15. In-place operation 为什么可能破坏 backward

Backward rule 有时需要 forward 的旧 value。若它在 backward 前被原地修改，gradient 可能错误。

Version tracking（版本跟踪）会记录已保存Tensor是否被原地修改；PyTorch据此检测许多这类问题并抛错：

```text
needed Tensor saved during forward
-> in-place mutation increments version
-> backward sees version mismatch
-> RuntimeError
```

用独立对象做一次，不污染R1参数：

```python
saved = torch.tensor([2.0], requires_grad=True)
square_loss = (saved ** 2).sum()
with torch.no_grad():
    saved.add_(1.0)
square_loss.backward()  # 本例故意触发RuntimeError
```

平方的反传需要原来的2，但存储已改成3。`no_grad`只让修改不被记录为新求导操作，并不让已保存的旧值恢复。实验只在最后这次backward周围捕获预期错误。

不要把所有 in-place operations 一律判死刑；但在训练 correctness 尚未证明时，不要仅为少一次 allocation 冒险。先让 profiler 证明它值得优化。

## 17. Failure discipline

Expected failures：

```text
复用已释放 graph 再 backward
non-scalar output 不给 upstream gradient
破坏 saved value 的 in-place mutation
```

只在上面故意失败的那一次调用周围捕获`RuntimeError`；确认错误属于该操作，不要求跨版本逐字匹配完整英文消息。若没有抛错就让检查失败，其他意外错误保持非零退出。三组错误都用独立新对象建立，不把前一次失败留下的状态带到下一次实验。

## 18. Training memory 为什么大于 parameter bytes

训练时 memory 不只有 parameters：

```text
parameters
gradients
optimizer states
saved activations
graph metadata
temporary operator workspace
```

Inference 通常不需要 parameter gradients、optimizer state 与 backward graph，因此 memory profile 不同。

Activation checkpointing（激活检查点）会少保存部分 activations，backward 时重新 forward 换 memory；这正是 graph lifetime 与系统成本的直接应用，当前只建立直觉。

## 19. 与 serving 的连接

Inference boundary：

```text
model.eval()
with torch.inference_mode():
    output = model(input)
```

其目的不只是“代码更快”：

```text
不建立训练 graph
不保留 backward activations
不产生 parameter gradients
明确 execution lifecycle
```

若 serving path 意外开启 gradient tracking，functional output 可能仍正确，但 memory、latency 与 lifetime 都会恶化。
