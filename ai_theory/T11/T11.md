# Part 1：PyTorch 怎样把 T4 的 chain rule 自动执行

## 0. 从一个三行计算开始

```python
x = torch.tensor(3.0)
w = torch.tensor(2.0, requires_grad=True)
b = torch.tensor(-1.0, requires_grad=True)

z = w * x + b
loss = (z - 4.0) ** 2
```

Forward values：

```text
z = 5
loss = 1
```

T4 手推：

$$
\frac{\partial L}{\partial w}=6,
\qquad
\frac{\partial L}{\partial b}=2
$$

现在执行：

```python
loss.backward()
```

PyTorch 会把这两个 gradients 写入 `w.grad` 与 `b.grad`。今天要解释的不是 API 口诀，而是它凭什么做到：

```text
forward 时记录 dependency
-> 每个 operation 提供 backward rule
-> scalar loss 给出 seed gradient 1
-> reverse traversal 累加 path contributions
-> leaf parameters 收到 .grad
```

## 1. Tensor 多出来的 autograd metadata

T9 已经把 Tensor 拆成：

```text
storage + dtype + device + shape + stride + offset
```

当 computation 需要 gradient 时，Tensor 还关联：

```text
requires_grad
grad_fn
is_leaf
grad
version / saved-tensor relation
```

这些 metadata 让同一个 Tensor 同时参与 numerical computation 和 derivative computation。

## 2. `requires_grad` 决定是否追踪关系

```python
w = torch.tensor(2.0, requires_grad=True)
```

表示后续由 `w` 参与、且处于 grad-enabled mode 的 operations 要被 autograd 记录，以便将来求 loss 对 `w` 的 gradient。

它不表示：

```text
创建时已经有 gradient
Tensor 一定是 model parameter
所有 downstream Tensor 都会把结果保存在 .grad
```

在第一次 backward 前：

```python
w.grad is None
```

## 3. Leaf 与 non-leaf 从哪里来

`w`、`b` 由用户直接创建，且不是某个 differentiable operation 的 result，因此是 leaf Tensors（叶子张量）。

`z` 与 `loss` 是 operations 的 result，因此是 non-leaf（非叶子）：

```python
w.is_leaf     # True
z.is_leaf     # False
loss.is_leaf  # False
```

默认情况下，backward 把 gradients 累积到 requires-grad leaf 的 `.grad`。Non-leaf gradients 会被计算并继续传播，但默认不长期保存在 `.grad`。

若调试确实需要：

```python
z.retain_grad()
```

再 backward，`z.grad` 才会保留。不要为所有 activations 机械调用它；这会增加 memory。

## 4. `grad_fn` 表示怎样回到前驱

```python
print(z.grad_fn)
print(loss.grad_fn)
```

`grad_fn` 指向产生该 non-leaf result 的 backward node。它不是完整 graph 的漂亮可视化，但能说明：

```text
z 不是孤立 value
z 知道自己来自 multiply/add path
loss 知道自己来自 subtract/power path
```

PyTorch eager autograd 的 graph 是执行 forward 时动态建立的。Python control flow 这次走哪条 branch，graph 就记录哪条实际 path。

## 5. Scalar `backward()` 为什么隐含 seed 1

若 loss 是 scalar：

$$
\frac{\partial L}{\partial L}=1
$$

所以：

```python
loss.backward()
```

等价于从 final output 注入 scalar seed `1`，再反向传播。

这与 T4 完全相同。Autograd 自动化的是 chain-rule bookkeeping，不是发明另一套微积分。

## 6. Forward graph 与 backward state 的生命周期

Autograd 为 backward 可能保存：

```text
operation dependencies
部分 forward activations
shape/dtype/device metadata
version information
```

第一次 backward 完成后，默认会释放一次性 graph state。对同一个 `loss` 再次：

```python
loss.backward()
```

通常抛 `RuntimeError`。

正常 training loop 每一轮重新 forward，得到新 graph，再 backward。`retain_graph=True` 只在确实需要重复使用同一 graph 时使用；它会延长 saved state lifetime，不应成为“报错就加”的默认修复。

# Part 3：把观察结果解释清楚

## 9. `.grad` 默认累加，不是覆盖

Autograd 使用 addition 累积 gradient，原因是同一个 leaf 可能从多个 paths 收到 contributions；mini-batch accumulation 也可能故意跨多次 backward 汇总。

因此普通 training iteration 开头需要清理旧 gradients：

```python
optimizer.zero_grad(set_to_none=True)
```

或手工：

```python
w.grad = None
b.grad = None
```

`None` 与 zero Tensor 都能表达“下一轮从空 gradient 开始”，但 allocation/behavior 细节不同。当前先使用 `None`，并用下一次 backward 的 exact values 证明清理有效。

## 10. Gradient lifetime 与 graph lifetime 不同

第一次 backward 后：

```text
forward graph 的一次性 saved state 通常释放
leaf .grad 仍然存在并继续累加
```

所以：

```text
“旧 loss 不能再 backward”
!=
“w.grad 已经消失”
```

这是两个 lifetime。T11 必须分别观察，不能把报错都归成“graph 没了”。

## 11. Non-leaf gradient 计算了，但默认不保存

链式法则必须先算 $\partial L/\partial z$ 才能继续算 $\partial L/\partial w$，所以 `z` 的 gradient 确实存在于 backward computation。

但 backward 后：

```python
z.grad is None
```

通常仍成立，因为 non-leaf `.grad` 默认不 retain。调用：

```python
z.retain_grad()
```

只改变 observation/storage policy，不改变 chain-rule result。

## 12. Vector output 需要显式上游 gradient

若：

```python
x = torch.tensor([1.0, 2.0, 3.0], requires_grad=True)
y = x ** 2
```

`y` 不是 scalar。单写：

```python
y.backward()
```

没有唯一含义：你要对哪个 scalar objective 求 gradient？

提供同 shape 的 upstream vector $v$：

```python
v = torch.tensor([1.0, 0.5, -1.0])
y.backward(v)
```

Autograd 计算 vector-Jacobian product（向量-雅可比乘积）：

$$
v^T J
$$

本例：

$$
\frac{\partial y_i}{\partial x_i}=2x_i
$$

所以：

$$
\frac{\partial(v^Ty)}{\partial x}
=
v\odot 2x
$$

这解释了 framework 为什么不为大型 Tensor 显式 materialize 完整 Jacobian。

## 13. Dynamic graph 动态在哪里

```python
def branch(x: torch.Tensor) -> torch.Tensor:
    if x.item() > 0:
        return x * x
    return -x
```

输入不同，Python branch 不同，本次 forward 建立的 graph 也不同。Dynamic eager graph（动态即时计算图）意味着 graph 跟随实际 execution 建立。

它提供调试和 control-flow 灵活性，也意味着每次 forward 有 graph-construction overhead。Inference serving 常使用 `inference_mode`、compile/capture 或专用 runtime 减少这部分成本。

## 14. `no_grad`、`detach` 与 `inference_mode`

### `torch.no_grad()`

临时关闭 gradient recording：

```python
with torch.no_grad():
    output = model(inputs)
```

### `detach()`

返回与原 Tensor 共享 storage 的 Tensor，但切断当前 autograd history：

```python
detached = tensor.detach()
```

因为仍可能共享 storage，in-place mutation 风险没有自动消失。

### `torch.inference_mode()`

为纯 inference 提供更强的 autograd-related disabling/optimization：

```python
with torch.inference_mode():
    output = model(inputs)
```

它不替代 `model.eval()`；T10 的 mode boundary 仍成立。

## 15. In-place operation 为什么可能破坏 backward

Backward rule 有时需要 forward 的旧 value。若它在 backward 前被原地修改，gradient 可能错误。

PyTorch 通过 Tensor version tracking 检测许多这种情况并抛 error：

```text
needed Tensor saved during forward
-> in-place mutation increments version
-> backward sees version mismatch
-> RuntimeError
```

不要把所有 in-place operations 一律判死刑；但在训练 correctness 尚未证明时，不要仅为少一次 allocation 冒险。先让 profiler 证明它值得优化。

## 18. Training memory 为什么大于 parameter bytes

训练时 memory 不只有 parameters：

```text
parameters
gradients
optimizer states
saved activations
graph metadata
temporary operator workspace
```

Inference 通常不需要 parameter gradients、optimizer state 与 backward graph，因此 memory profile 不同。

Activation checkpointing（激活检查点）会少保存部分 activations，backward 时重新 forward 换 memory；这正是 graph lifetime 与系统成本的直接应用，当前只建立直觉。

## 19. 与 serving 的连接

Inference boundary：

```text
model.eval()
with torch.inference_mode():
    output = model(input)
```

其目的不只是“代码更快”：

```text
不建立训练 graph
不保留 backward activations
不产生 parameter gradients
明确 execution lifecycle
```

若 serving path 意外开启 gradient tracking，functional output 可能仍正确，但 memory、latency 与 lifetime 都会恶化。
