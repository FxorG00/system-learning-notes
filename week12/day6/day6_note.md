## R3

**你抓到的是“异常处理的范围”问题。两条连接相互独立，但操作它们的代码属于同一个 Python 程序，而且目前是顺序执行的。**

你现在的 client 大致是：

```text
操作 A 时抛异常
→ 异常没有被捕获，退出 main()
→ Python 程序失败退出
→ 操作系统回收程序持有的 A、B 两个 socket
```

所以，**不是 A 的 socket 出错直接把 B 弄坏了，而是整个 client 停止运行，B 也失去了继续操作它的程序。** 共用代码本身没有问题。

你也发现了当前代码的一个细节：`a.close()`、`b.close()` 放在末尾，异常发生时确实可能执行不到。用 `with` 或 `try/finally` 可以保证异常路径也主动关闭连接。**但这只解决资源清理，不会让 B 自动继续执行。**

至于 B 应不应该继续，要看程序的用途：

- **当前验收 client**：任何一步失败，整组测试失败并退出，是合理的。它是在验证一个完整场景。
- **长期运行的业务 client**：如果要求 A 失败后 B 继续，就需要在 A 的操作范围内捕获异常、处理 A，然后继续执行 B 的逻辑。

你之前理解的“坏连接不能影响健康连接”，主要是服务器的处理目标：服务器处理完 A 的协议错误，仍然应该服务 B。**测试程序因发现失败而退出，与服务器错误地连带终止 B，是两件不同的事。**

因此，这份 R1 client 不必为了“让 B 继续”而修改；补上异常路径的确定性清理，是一个有价值的改进。

## 操作系统兜底清理

**对，但前提是整个进程已经退出。** 操作系统会回收这个进程持有的 socket 文件描述符，即使代码没执行到 `close()`。这是进程退出时的兜底清理。注释 1

**写程序时仍应该主动管理连接的生命周期。** 如果异常被捕获、程序继续运行，就不能靠“进程退出”及时释放资源。

Python 最方便的方式是 `with`：

```python
with socket.create_connection(("127.0.0.1", 6380)) as a:
    with socket.create_connection(("127.0.0.1", 6380)) as b:
        # 在这里操作 A、B
        ...
```

**无论正常结束还是异常离开代码块，`with` 都会调用对应 socket 的 `close()`。** 甚至创建 B 失败时，已经创建好的 A 也会被关闭。

可以这样记：**操作系统负责进程退出后的回收；`with` 负责代码作用域结束时的及时清理。** 这和 C++ 的 RAII 很像。
