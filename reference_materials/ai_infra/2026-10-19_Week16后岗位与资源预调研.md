### 本次多核对出的几个实际问题

**1. 代码短，不等于当前机器就能运行完整系统。** [nano-vLLM 的依赖文件](https://github.com/GeeeekExplorer/nano-vllm/blob/main/pyproject.toml)列出 PyTorch、Triton、FlashAttention 等；Mini-SGLang 的完整运行也有 GPU 软件栈要求。将来先核对驱动、设备、模型大小、依赖版本和实验成本，再决定运行哪一部分。这次没有安装包、下载模型或改 Python 环境。

**2. README 的环境要求要与构建文件对照。** 本次读取的 InfiniTrain README 写 CMake 3.13+，但读取的 [CMakeLists.txt](https://github.com/InfiniTensor/InfiniTrain/blob/master/CMakeLists.txt)写 `cmake_minimum_required(VERSION 3.28)`，并要求 C++20。两处页面展示不一致；本轮未固定同一 commit 构建，不判定哪个快照代表当前完整可用环境。真正采用前，要在同一固定版本下重新核对。

**3. 公开文章与完整项目是两种访问条件。** dlog 的[项目介绍](https://dlog.com.cn/posts/offer01/vllm%E4%BB%8B%E7%BB%8D/)说明完整项目需通过赞助等方式获取。公开文章可以参考；本轮没有访问完整私有项目，也没有据目录宣称所有版本均已验证。文章中的“入场券”说法是作者观点，不作为所有岗位的硬门槛。

**4. 教学通信实现不能直接等同生产算法。** nano-deepspeed README 将 stage 2 通信注明为教学式 `packed + all_reduce + local scatter-back`。后续若研究通信收益，需要对照官方 DeepSpeed 的对应版本和实际通信记录，而不能仅凭 stage 名称推断优化已经实现。

## 5. 简历样本学什么

本次查看了一份[作者自愿公开的 AI Infra 作品集](https://newmancai.github.io/)。可以参考的是表达结构：把任务、硬件、自己负责的实现、局部测量和端到端瓶颈分开说明。作者有不同的教育与实习经历，页面性能结果属于作者自述，本轮没有复现实验。

映射到用户未来的产出，可以沿这条证据链组织：

```text
Mini Redis：真实网络/状态/恢复问题 -> 自己的实现与正确性证据 -> 基线与分析
小型推理项目：模型怎样得到结果 -> 哪部分占时间/内存 -> 自己的一次可验证改动
```

这只是项目表达方向。Mini Redis 的 TTL、AOF、恢复、性能与最终文档仍按原 Week13~Week16 推进；本轮不前移文档任务，不要求马上启动推理项目。跑通他人的框架可以算学习实验，不能写成自己实现了该框架或取得了上游的性能结果。
