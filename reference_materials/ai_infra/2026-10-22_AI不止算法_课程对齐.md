## 3. 六块目录分别放在哪里

### 3.1 课程一：C++、INT8与CPU加速

这块围绕一个问题：模型算对以后，怎样在CPU上组织和加速计算。目录还含CNN实例，不能据此要求当前LLM路线提前学完CV。

| 目录主题簇 | 我们的落点与当前状态 | 采用的深度 |
|---|---|---|
| C++对象、内存、RAII、移动等基础 | Week1～8已有项目证据；对象模型缺口见[C++补缺规划](../../C++项目伴随补缺规划.md) | 抽查真实缺口，不重开C++课程 |
| PyTorch模型与归一化、线性计算 | T9已过；T10～T13待学，T14的CNN可延期 | 用已会的线性分类器接Module/autograd，CNN不前移 |
| INT8表示、刻度、按Tensor/通道处理、量化误差 | [理论规划T20](../../AI_Infra理论伴随线规划.md)已有分层入口 | 先理解一个数，再做CPU数值参考，最后才测低精度算子 |
| cache、矩阵乘、Roofline、CPU向量指令与C++扩展 | Gate B浮点组件正确后的定向补强，尚未验收 | 对一条线性层或归一化路径定位成本；需要时再接Python调用 |
| QAT及框架专门实现 | 后续可选分支 | QAT（量化感知训练）需要训练时考虑近似误差；仅在已有训练后量化不能满足质量目标时展开 |

SIMD（单指令多数据）和AVX（x86向量指令扩展）是CPU执行相关机制；拥有RTX 4060并不能说明CPU支持AVX-512。进入实验先查询实际CPU指令集，保留可运行的普通实现，不要求为目录升级机器。

Roofline（计算与访存上限模型）用来判断当前算子更可能受计算还是数据移动限制。它是分析工具，第一次使用时必须从自己的FLOPs与搬运字节估算推出来，不能只画一条线就宣布找到瓶颈。

### 3.2 课程二：从CUDA例子走向GPU机制

先让一份小计算在GPU上正确执行，再追问它为什么慢。我们保留这个顺序，接到总规划Gate C原有的基础kernel（计算内核）要求里。

| 目录主题簇 | 我们的落点 | 采用的深度 |
|---|---|---|
| Hello CUDA、线程编号、运行流程、能力查询 | Gate C入口，CPU闭环与环境就绪后 | 先跑通独立计算、检查尾部边界与错误，再谈优化 |
| 向量加法、访存、shared memory、warp与归约 | Gate C基础算子 | 对同一输入改一种访问/归约方式，先核对结果，再比较时间与访存证据 |
| FP16、GELU、softmax、LayerNorm等 | 基础归约站稳后，选择模型实际需要的算子 | 复用已有数学reference（独立正确性参照）；不要求把目录每个算子重写一遍 |
| GEMM/GEMV、分块、资源占用、融合与stream | Gate C向模型计算推进时 | GEMM（矩阵乘）与GEMV（矩阵向量乘）分别匹配不同输入规模；从自己的形状产生优化需求 |
| Nsight、Hopper专属特性等 | 性能分析随实验使用；架构特性按硬件另选 | 先有具体疑问再采集数据，不把高级硬件目录当入门门槛 |

第一批至少3个kernel的原出口保持。可沿向量加法、归约、矩阵计算取得证据，再在原项目里推进softmax/RMSNorm等模型算子；这是一条推进方向，不是本次新增六个同时必交的任务。

### 3.3 课程三：LLM的GPU推理引擎

它把模型中的小计算连成一次生成。我们先在T线看懂计算，再在同一后续推理项目里逐段替换或验证，避免只会孤立kernel。

| 目录主题簇 | 我们的落点 | 采用的深度 |
|---|---|---|
| 权重、shape、embedding、padding和mask | T15～T18建立对象链；Gate B/D接模型 | 同一输入逐层对照输出，不先抄整套引擎类结构 |
| RMSNorm（均方根归一化）、线性层、RoPE（旋转位置编码）、激活、采样与融合 | T16～T19讲计算用途；Gate C做选定算子 | 单算子正确以后再测融合，保留未融合的独立参照 |
| KV Cache、MHA/MQA/GQA（多头/多查询/分组查询注意力）与prefill/decode | T16～T22分层建立；Gate D对应真实路径 | 先有普通attention/KV参照，再解释共享K/V或改变布局解决什么问题 |
| GPU allocator、层封装、权重加载、Python/C++绑定和逐步调试 | Gate B/C能力齐备后的同一模型路径 | 从权重文件到一个生成结果走通；内存管理先讲生命周期，复用/池化由实际分配证据推动 |

这里的主要补强是**算子怎样接回模型**：一个单算子更快，不代表整次生成更快。后续先用同一小模型和固定输入核对逐层误差，再区分加载、首轮计算和逐步生成的时间；继续使用T21～T23已有的KV、调度与指标模型。

### 3.4 课程四：TensorRT与Triton Inference Server部署

它主要展示“训练好的模型怎样变成可接请求的程序”，截图中以YOLO等CV模型为实例。部署方法有参考价值，但CV模型本身不是我们当前LLM主线的必修前置。

| 目录主题簇 | 我们的落点 | 采用的深度 |
|---|---|---|
| ONNX、图检查、模型转换与TensorRT engine | Gate D可选部署对照 | ONNX（模型交换格式）描述模型计算；engine（编译后的执行产物）用于运行。需要该部署路线时才引入 |
| CUDA前后处理与TensorRT plugin | Gate C之后，且实际部署遇到算子支持或性能问题时 | plugin（自定义算子扩展）解决具体缺口，不为了用plugin而增加YOLO项目 |
| stream、CUDA Graph、内存搬运与端到端性能 | Gate C/D实测发现相应开销后 | 先用时间线找开销，再判断并行/复用执行图是否有效；不保证加上就更快 |
| Triton服务、并发请求与dynamic batching | Gate D可选服务路径 | dynamic batching（把多个请求合为一批执行）要同时检查排队、吞吐和延迟；不等同LLM按token迭代的连续批处理 |

TensorRT、Triton Inference Server与Triton算子编程语言分别处理编译/执行、服务请求和算子编写。**它们可以配合，也不是同一个项目。** 原有mini-sglang有限阅读、vLLM或SGLang窄路径对照继续保留，不要求再完整复刻一套TensorRT/CV服务。

### 3.5 课程5-1：LLM量化框架

这一块关心怎样产生可保存、可加载的低精度模型。T20先解决表示与误差，模型级方案在基础实验和Transformer计算站稳后再选。

| 目录主题簇 | 我们的落点 | 采用的深度 |
|---|---|---|
| 低精度格式、误差/质量、权重与激活的位数 | T20直觉；Gate B后数值参考 | 先走一个数和一张矩阵，不一次教完全部格式 |
| 校准数据、模型替换、配置与量化权重保存 | 后续模型级量化的共同基础，原规划需补实 | calibration（校准）用代表性输入观察中间张量的数值分布，帮助选择刻度等配置；说明数据来源与用途，和训练更新分开 |
| SmoothQuant W8A8、AWQ W4A16 | 真实低精度优化的候选路线，按问题选一种深入 | W8A8表示权重/激活各8位；W4A16表示权重4位、激活16位。位数标签不单独决定运算精度、布局或实际速度 |
| FP8、MoE、更多模型适配与KV量化 | 后续有模型/硬件需求再选 | FP8（8位浮点格式）与INT8不是一种表示，不把高级目录全部变为新门槛 |

PTQ（训练后量化）在已有训练模型上生成近似表示。它与QAT可先比较用途，不要求两套都实现。深入算法时，分别用[SmoothQuant原论文](https://arxiv.org/abs/2211.10438)与[AWQ原论文](https://arxiv.org/abs/2306.00978)核对机制；论文收益不能直接写成自己的4060结果。

### 3.6 课程5-2：低精度模型的运行时

量化文件变小以后，还需要有人读懂其布局、刻度并执行计算。runtime（运行时）在这里指加载这些状态、选择计算路径并完成推理的程序。

| 目录主题簇 | 我们的落点 | 采用的深度 |
|---|---|---|
| 量化权重加载、Python/C++接口、层替换 | 同一后续推理项目的低精度分支 | 复用原浮点模型，检查格式、shape、刻度与布局是否对应；不另造完整runtime |
| INT4解包/反量化、INT8/FP8 GEMM、CUTLASS与Tensor Core | 基础CUDA和低精度数值参考完成以后 | CUTLASS是NVIDIA矩阵计算模板库；Tensor Core是支持特定矩阵计算的硬件单元。先用适配库，再按瓶颈决定是否读/改kernel |
| 质量评估、kernel与端到端benchmark | Gate C/D原证据要求的具体化 | 同时比较输出质量、显存、算子时间与整次生成表现；把加载/转换等一次性成本单独报告 |

**量化格式、存储布局与执行kernel必须匹配。** 恢复成浮点再调用原线性层，可以验证误差，但不能称为低精度计算加速；只换文件或调用API，也不等于实现了量化运行时。

## 4. 真正落入规划的四处补强

这些是已有项目里的后续实验位置，**现在不要求执行，也不作为Week16首批试投的新前置**。实际范围和课次仍在Week16收口后确定。

### A. CPU：对一条真实算子路径做性能解释

先保留已经正确的浮点线性层或归一化算子。固定输入形状，分别看小规模和较大规模，记录输入、输出、编译参数、计时范围与正确性误差。

再依据数据决定检查循环顺序、cache或SIMD中的哪一处。一次只改一个主要因素，保留原实现对照；没有加速也要能解释。需要从Python调用时，可封装同一算子，不另写一套推理框架。

### B. CUDA：先能测，再解释为什么快或慢

沿原基础kernel逐步加入访存、归约和矩阵计算。每一项都有CPU/PyTorch正确性参照，并用包含非整块尾部的输入检查边界。

计时须区分GPU计算与含搬运的整段时间。Nsight Systems先看执行时间线；需要分析单个kernel时再用Nsight Compute。工具采集本身有开销，正式性能比较与诊断采集分开进行；不把profile运行时间直接当最终延迟。

### C. 模型：把选定算子接回同一个小模型

先得到固定权重、固定输入下的完整浮点结果，再接入一个选定算子或低精度线性层。逐层比对能够定位“第一处输出偏差”，避免只看最终文字是否像话。

模型接入正确后，再用可比输入区分prefill（处理已有输入序列）与decode（继续生成）的开销。内存复用、融合和CUDA Graph只在证据说明有相应成本时引入，不为目录完整而全部实现。

### D. 低精度：从数值参考走到一条可运行计算路径

沿T20之后的同一CPU数值参考保留原权重和输入。进入模型级量化时，明确校准数据、量化配置、刻度和权重打包方式，保存后重新加载并核对结果。

接下来只选一条硬件支持的方案，测量质量、实际显存和可比性能。第一次可从已有后端开始；是否手写解包或矩阵kernel由瓶颈决定。PTQ的一个方案、完整QAT和多种FP8路径不同时开工。

## 5. 4060与租卡怎样参与

硬件事实以[环境记录§2.1](../../ai_theory/ENVIRONMENT.md)为准：本机是RTX 4060 Laptop GPU、约8 GiB；当前SSH Ubuntu仍是CPU版PyTorch。基础CUDA和小模型优先本地，软件栈先单独验证。

GPU的compute capability（计算能力版本）影响可用指令。NVIDIA表中RTX 4060属于8.9；目录里的Hopper/SM90专门特性不是这台卡的能力。例如TMA（张量内存搬运单元）是Hopper引入的机制，不能把对应练习直接当4060必做项。[GPU能力表](https://developer.nvidia.com/cuda/gpus)、[Hopper官方指南](https://docs.nvidia.com/cuda/hopper-tuning-guide/index.html)。

FP8和某个CUTLASS示例能否运行，须继续核对**具体算子、版本、数据布局和目标架构**。不能笼统写成4060都支持或都不支持。完整模型还需估算权重、KV与临时显存，不能仅凭参数量承诺8 GiB能跑。

确实需要更大显存、特定架构或多卡时，再按实验问题确认租卡预算、时长、数据与关停方式。用户愿意租卡不等于本次允许开实例；现在没有下载模型、升级环境或租用硬件。

## 6. 后续生成教程时怎样使用

1. 先读当前Gate与本文件对应板块，找出当天真正需要的一项能力。
2. 核对作者当前公开版本；只选一份最有帮助的第二解释，不叠加同类课程。
3. 在本地正文从已有对象讲清问题、动作、结果和用途，再引入新术语/API；映射表不是教程正文。
4. 保留学生独立设计、正确性参照与性能判断；机械测试、采集脚手架可委托。
5. 更新后按Memory §1做全局对齐，不覆盖用户代码/笔记，也不把教材准备登记成学习通过。

完整课程目录的优点是把后续工作摊开；我们的做法是**在同一个项目需要它时再展开**。不因一个主题尚未学习，就把全部高级技术一起前移。
