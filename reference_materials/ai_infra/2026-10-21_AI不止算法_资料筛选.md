## 3. 哪些内容值得在对应阶段调用

| 已有阶段 | 可能有用的主题 | 使用方式与停止边界 |
|---|---|---|
| 当前Week13～16、T10～T13 | 暂无必须追加的内容 | 先走通现有教程，不补一套课程，不让未来kernel名词抢前置 |
| CPU推理框架阶段 | C++算子组织、Tensor与执行流程、模型导入、分发 | 对照自己遇到的一条调用链，择一处讲解；不把CPU课程整套复刻成第二个项目 |
| Gate C：CUDA入门与基础kernel | 访存、归约、矩阵乘、性能分析 | 先有自己的正确reference与可用GPU，再查一个性能问题；记录硬件、输入、计时与profile证据 |
| Attention/decoder基础完成后，按Gate推进 | LLM算子的shape、数据移动、融合及量化 | 先知道模型在算什么，再读kernel；不从目录直接跳到量化runtime或CUTLASS高级模板 |
| Gate D：在线推理系统与性能 | 框架开销、请求路径、服务批处理、TensorRT部署与系统级优化案例 | 用自己的执行链和测量对照；TensorRT是可选实现路线，不替换既有mini-sglang/vLLM选材规则 |
| Gate E：多卡条件满足后 | 多GPU相关调度与通信 | 当前不新增多卡课程；进入时重新核对公开内容与实际硬件 |

**Triton Inference Server（推理服务系统）与Triton算子编程语言是不同项目。** 前者组织模型服务、请求与后端，后者用于编写GPU算子。选课时必须看完整名称，不能把学过其中一个记成掌握另一个。

以上是按现有路线作的选材映射，不是Week17以后的实际周课表。完整Week16收口后，仍按当时岗位、硬件、精力与学习证据再安排。

## 4. 可以借鉴什么讲解方法

公开课程介绍将“模型怎样部署、算子在哪里参与、怎样分析加速收益”放在同一条工程路径里，这与我们的长期目标相关。

后续选用公开案例时，可以围绕一个问题组织：

```text
某个请求慢在哪里
-> 先定位耗时属于框架、数据搬运还是算子
-> 提出一个可检验的修改
-> 保持正确性与实验条件可比
-> 再判断延迟、吞吐或内存是否改善
```

这是我们采用的教学与实验组织方式，不是声称已从受限页面验证了作者全部课程。作者风格、具体技术准确性和每个实验的复现性，仍需在真正引用时逐篇检查。
